- Semantics notes:
  1. **Type mapping.** `Task WriteAsync(..., CancellationToken)` becomes a blocking fn (R0003) taking `&CancelToken`; `Action<Stream>` becomes
     `FnOnce(&mut dyn Write) -> io::Result<()>`; `ILog?` becomes `Option<&dyn Log>`. The two C# overloads are `write_atomic` (no override) and
     `write_atomic_with_temp`. `OperationCanceledException` is `AtomicWriteError::Canceled`; every other exception (I/O, payload) is `Io`; a
     non-I/O payload failure is expressed by the closure as `io::Error::other(..)` and comes back unchanged (same kind and message).
  2. **Order of effects** (doc comment of `write_atomic`): cancel check, create directory, create-new temp, payload, flush + close, cancel
     check, rename over, cleanup. A pre-cancelled token must not even create the folder (test).
  3. **Directory.** C# `Directory.CreateDirectory(Path.GetDirectoryName(cachePath)!)`: `std::fs::create_dir_all` on the parent. A path without a
     directory part (`""` parent) or a root path: `Err(Io(InvalidInput))` (C# `ArgumentException`). A parent that is an existing FILE: the
     `create_dir_all` error comes back (C# `IOException`); the golden `parent-path-is-a-file` only compares the family `IOException`.
  4. **Temp name.** `cache_path + "." + guid_n + ".tmp"` with `pr_core::io::physical::new_guid_n()` (32 lowercase hex). It must match `*.tmp`
     (W4-09's sweeper) and be in the SAME folder as the cache path (rename must not cross volumes). No other suffix.
  5. **Create-new ownership (R07).** `OpenOptions::new().write(true).create_new(true)` with share mode NONE (`share_mode(0)` via
     `std::os::windows::fs::OpenOptionsExt`, behind `cfg(windows)`). Set `created = true` only AFTER the open succeeded. If the open fails because
     the path exists, the pre-existing file is NOT deleted and its bytes are unchanged. The sequential-scan flag (`custom_flags(0x0800_0000)`) is
     optional; keep it, it mirrors C#.
  5b. **Temp override.** The override path is used verbatim; its folder is NOT created (C# only creates the folder of `cache_path`), so
     an override in another, missing folder fails with `Io(NotFound)` at create-new.
  6. **Buffering and flush.** `BufWriter::with_capacity(WRITE_BUFFER_SIZE, file)`; after the payload `flush()` explicitly (the error propagates; do
     not rely on drop) and drop it so the handle is closed BEFORE the rename (and on the payload-error path before the cleanup delete, so the writer is dropped first) (Windows cannot rename an open share-none file). No `sync_all`, no
     write-through (perf(cache) note in the C# source: a lost write is only a cache miss).
  7. **Rename.** `std::fs::rename(temp, cache_path)` replaces an existing destination on Windows (`MoveFileExW` with REPLACE_EXISTING), the same
     as `File.Move(.., overwrite: true)`. NO retry loop (unlike the settings write, D-05/S-65: this is a cache). A destination that is a directory
     fails (golden `target-is-an-existing-directory`); .NET reports `UnauthorizedAccessException` (access denied, NOT an `IOException`)
     and `std` an `io::Error` of another kind, so the Rust test accepts any `Io`
     and checks the outcome (directory intact, no temp left).
  8. **Cleanup.** (`TryDelete` catches only `IOException` and `UnauthorizedAccessException`; every `io::Error` is the Rust equivalent.)
     In every outcome after a successful create-new, `try_delete(temp)` (exists check, delete, errors logged `"Delete failed: {path}"`
     with the error through `log.error`, never propagated). After a successful rename the temp no longer exists, so it is a no-op. A cleanup
     failure must not mask the original error.
  9. **Cancellation.** Only the two C# points (before work, after the payload). The payload may observe the token itself (it captures a clone).
     A cancel that arrives during the rename is not honoured (the file is published, as in C#).
  10. **Not here.** No retry, no locking between concurrent writers of one cache path (last rename wins, both files complete), no eviction or
      size accounting (W4-09), no byte format (W4-08b).

## Golden package
- `oracle/W4-08a.cs`: command `atomic-cache-file` (dispatch line in the file header). Reaches the internal class by reflection. Each case runs its
  steps on one fresh real temp tree and reports each step's outcome plus the final tree (relative path to hex, or `<N bytes>` over 32 bytes;
  `*.<guid>.tmp` names normalised to `.<GUID>.tmp`). Outcome type names are collapsed to `OperationCanceledException`, `IOException` (also for
  `UnauthorizedAccessException`, which .NET throws for a rename onto a directory) or the raw name (`InvalidOperationException`).
- `golden-inputs/atomic-cache-file.json` (17 cases): new file with new folders, replace existing, empty and over-buffer payloads, cancel before /
  during with and without an old entry, payload throws (at once, after a partial write, with an old entry kept), pre-existing temp refused and
  untouched (also with a pre-cancelled token), pinned temp name, target is a directory, parent is a file, two targets in one folder.
- Rust mapping of a case: `write` => `write_atomic_with_temp(&root.join(target), closure, None, temp.map(|t| dir.join(t)).as_deref(), &token)`;
  payloads `ok` / `throw` / `throw_after_write` / `cancel_after_write` become closures (the cancel variant calls `token.cancel()` after writing;
  `cancel_before` cancels the token first). Expected `type` mapping: `OperationCanceledException` => `Canceled`; `IOException` => `Io` (any kind);
  `InvalidOperationException` => `Io` whose message is `boom`.

## Open questions
- **`std::fs` vs the `FileSystem` trait.** Recommended (used by the stub): `std::fs` directly in `pr-imaging`, matching C# (it also uses
  `FileStream` / `File.Move` without `IFileSystem`) and the W2-05 precedent; the trait has no create-new stream method. Cost: callers (W4-09,
  W4-08b) test with `TempRoot`, not `FakeFileSystem`. Alternative: add `FileSystem::create_new_for_write` plus `move_file_overwrite` with fake
  support; larger blast radius (counting wrapper, physical, fake), no behaviour gain. Lead decides.
- **`try_delete` ownership.** C# keeps it on `DiskCacheStore` (W4-09). The stub has a private copy so this unit compiles alone; if W4-09 merges
  first, call its public `try_delete` instead (identical semantics).
- **Non-Windows builds.** `share_mode(0)` and the sequential-scan flag need `cfg(windows)`; other targets use plain create-new (CI is
  `windows-latest`, this only matters for local Linux checks).
