- Semantics notes:
  1. **Constants.** `MINIMUM_BOX_LONG_SIDE = 1200`, `MAXIMUM_BOX_SIDE = 4000`, `BOX_QUANTUM = 128` (all `int` in C#). They are part of the cache
     key through the box, so they cannot change without a cache-version bump (INV-2 is not touched here: the box is only an input to the key).
  2. **Validation.** Four checks in this order: `viewportWidth`, `viewportHeight`, `dpiScale`, `qualityMultiplier`. Each fails when
     `!double.IsFinite(v) || v <= 0`, i.e. NaN, +-Infinity, zero (including `-0.0`) and negatives. Rust: `!v.is_finite() || v <= 0.0`.
     The error carries the C# parameter NAME (golden `param`): `"viewportWidth"`, `"viewportHeight"`, `"dpiScale"`, `"qualityMultiplier"`.
     The first failing argument wins (golden `error-order-*`).
  3. **Arithmetic, operation order is part of the contract.** `width = viewportWidth * dpiScale * qualityMultiplier` evaluated left to right,
     the same for `height`; `longSide = max(width, height)`; `if longSide < 1200 { scale = 1200 / longSide; width *= scale; height *= scale; }`.
     Do not pre-multiply `dpi * quality` (`a*(b*c)` differs from `(a*b)*c` in the last bit and the quantizer can step on it). Do not use
     `f64::mul_add` or any fused operation. `max` of two finite-or-NaN values: use `if width >= height { width } else { height }`-style or
     `f64::max`; they agree here because inputs are never NaN before the product (a product can become NaN only via `0 * inf`, see trap 3).
  4. **`quantize`.** `steps = max(1.0, ceil(side / 128.0 - 1e-9))`; `min(steps * 128.0, 4000.0)`; truncate to `i32`. The `1e-9` is subtracted from the
     QUOTIENT (not from `side`). Goldens `epsilon-boundary-just-inside` (1280.0000001279 => 1280) and `...-just-outside` (1280.0000001281 => 1408)
     pin the threshold; `float-noise-*` and `one-thousandth-above-multiple-steps` pin both sides of it.
  5. **Cap after quantize.** `3968.5` quantizes to 4096 and is then capped to 4000 (golden `3968.5-would-be-4096-capped`); 4000 is NOT a multiple of
     128, so a capped side breaks the quantum grid on purpose. Each side is capped independently (`cap-applies-to-long-side-only`).
  6. **Defaults.** C# `dpiScale = 1.0`, `qualityMultiplier = 1.0`. Rust has no default arguments: callers pass `DEFAULT_DPI_SCALE` /
     `DEFAULT_QUALITY_MULTIPLIER`. Golden case `defaults-omitted-use-1-1` is the same as passing `1.0, 1.0`.
- Traps checklist (docs/MULTI-AGENT-PLAN.md §7): item 3 (numeric conversions: `(int)` of a double), item 4 (floating point order and `ceil`),
  item 11 (default arguments). Specific traps:
  1. **`Math.Max` vs `f64::max`.** .NET `Math.Max(1, NaN)` returns NaN; Rust `1.0_f64.max(NaN)` returns `1.0`. In `quantize` the NaN case must
     therefore be handled BEFORE the `max`/`min` calls, not by relying on them.
  2. **`(int)double.NaN`.** In .NET (9+, saturating conversions) `(int)NaN == 0`, `(int)+Inf == int.MaxValue`, but `Math.Min(inf, 4000)` already
     removed infinity. Rust `NaN as i32 == 0` also; still write it explicitly: `if side.is_nan() { return 0; }` with a comment. Golden
     `nan-saturating-cast` pins C# = 0 (the oracle run is what confirms it; if it reports anything else the golden wins and this note is fixed).
  3. **NaN can come out of valid inputs.** All four arguments valid, but `1e-200 * 1e-200` underflows to `0.0`, then `longSide = 0`,
     `scale = 1200 / 0 = +inf`, `0 * inf = NaN`, `Quantize(NaN) = 0`, so the result is `DecodeBox(0, 0)` which the rest of the system reads as
     UNBOUNDED (full-size decode). Preserve this (golden `both-sides-underflow-to-zero-then-nan`: expect 0x0). Do not add a guard: it is a C#
     quirk reachable only with absurd inputs, but behaviour parity wins; record it in `docs/PARITY.md` notes as an accepted-as-is quirk.
  4. **Infinity.** `1e300 * 1e300 * 1.0 = +inf` => capped to 4000 (golden `overflow-to-infinity-is-capped`). Rust `f64` overflows to inf identically.
  5. **`ceil` result for negative or tiny sides.** `ceil(-1e-9)` is `-0.0`; `max(1.0, -0.0)` is `1.0`. Negative and zero sides give 128
     (goldens `zero-*`, `negative-*`). Do not `assert!(side > 0.0)`.
  6. **No integer arithmetic before the cap.** `steps * 128.0` is computed in `f64` so `1e300` does not overflow an `i32`; convert after `min`.
  7. **Only the Rust float parsing of golden inputs needs care**: the goldens encode NaN / Infinity / `-0` as the strings `"NaN"`, `"Infinity"`,
     `"-Infinity"`, `"-0"` (JSON has no literals); the test helper maps them. Numbers like `1e-320` are valid JSON numbers; `serde_json` parses
     the subnormal correctly (`1e-320` and `5e-324` round-trip), but the C# oracle writes `-0` only as the string.

## Open questions
1. **Where `DecodeBox` lives** (W4-01b vs here): recommended and used by this stub: W4-01b owns it; the stub carries a marked placeholder only so
   it compiles alone. If the lead merges W4-05a first, keep the placeholder and let W4-01b replace it (one-line import change).
2. **Return type** `Result<DecodeBox, InvalidPreviewArgument>` versus panicking: recommended `Result` (callers in the viewport pipeline pass
   user-driven sizes; a panic would take down the preview thread). The C# callers (`InitialViewportPredictor`, `MainWindow`) pass values already
   clamped to positive, so the App unit may `.expect(...)` at its single call site.
3. **The 0x0 underflow quirk (trap 3):** kept as-is (parity). If the lead prefers to treat it as a defect, the fix is a Rust-only guard returning
   `Err` for a non-finite product, but that diverges from the golden and needs a `PROPOSED-DECISIONS.md` entry first.
