## Semantics

1. Manual `workflow_dispatch` takes an **existing** Rust tag `vX.Y.Z`, with exactly the same three numeric components as `PHOTOREVIEW_RS_VERSION`; R2 verifies the exe resource. The chosen Rust rule is a normal semver release tag, independent of C#'s automatic `v2.0.N` sequence; see D-W10release-1. Validate ASCII digits and `\z`, resolve `refs/tags/<tag>` to a commit, and check out that exact tag. Refuse an existing release; no overwrite or `skip_ci_check` escape.
2. Query all check runs on the peeled commit and require the latest **`build-test`** run to be completed/success. That is the actual terminal check in this repo's `.github/workflows/ci.yml` lines 167 onward. If checks are absent or API fails, stop. Tag existence alone is insufficient: the C# CI backfill comment explains why.
3. `windows-latest`, pinned `actions/checkout` SHA copied from this repo's `.github/workflows/ci.yml`, `permissions: contents: write, checks: read`, `GH_TOKEN: ${{ github.token }}`, `concurrency: release-${{ inputs.tag }}`. No credential in tracked files. Run `cargo build --release --locked -p pr-shell`; `crates/pr-shell/Cargo.toml` names the bin `PhotoReviewRs`. Stage that exe, two verified DLLs, licence/source files and the new, reviewed C# `THIRD-PARTY-NOTICES.md` copy from R4. The proposed layout also has `Languages/en.json` and `Languages/vi.json` pending D-W10release-7. The zip has no .NET runtime or C# exe.
4. A `windows-latest` GitHub-hosted runner has a non-interactive session; `--smoke` creates a Direct2D window and may fail there. The workflow input `run_smoke` defaults to true; its guarded step has `continue-on-error: false`, an isolated `PHOTOREVIEW_RS_DATA_ROOT`, `PHOTOREVIEW_RS_ISOLATE_CONFIG=1` and a bounded wait. When CI cannot supply a usable desktop, select `run_smoke=false`, run the same smoke on the maintainer's machine and paste its result into the release notes through `smoke_result` (D-W10release-8). A failing enabled smoke fails the workflow.
5. Hash the exe, DLLs, and zip into `SHA256SUMS`; verify staged DLL/source/notice files, the measured exe size plausibility range (no invented bounds), `RT_GROUP_ICON` count >= 1, and absence of `PhotoReview.exe`, C# names and managed/WPF files before zip; list zip entries after zip. Generate release notes against the previous published version tag with GitHub's generate-notes API and prepend the R0002 coexistence/recovery warning, source-offer text and smoke result. Use `gh release create --verify-tag --notes-file` and upload both zip and `SHA256SUMS`.

## Traps and open questions

- `build.rs` and `res_writer.rs` are still stubs at HEAD; a successful build alone does not prove icon, manifest or version resources. R2's resource parser gate must pass first.
- Code signing is undecided: unsigned (recommended for first release, no secret handling), `signtool` with a protected certificate, or Azure Trusted Signing. D-W10release-2 records tradeoffs; do not invent a certificate or silently add one.
- Proposed lint: `tools/check-release-workflow.ps1` must reject literal `secrets.` and unpinned `uses:` and parse YAML if a parser is available; run `actionlint` when installed. Neither tool is an existing gate at HEAD. See `docs/drafts/release.yml` for the complete proposed workflow.
