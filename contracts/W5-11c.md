## Semantics notes
1. **Empty list.** `container_info.exif_blocks.is_empty()` gives `{ None, complete: true }` without touching the source (the C# test `NoBlocks` equivalent is a golden case; the `reads` list must be `[]`).
2. **Per block, in list order** (all arithmetic in `i64`, as C# `long`; `to_read` is narrowed to `i32` only after the `min`s, which keep it in `1..=4_194_304`):
   - Skip, with NO read and `complete` untouched, when `block.offset < 0 || block.offset >= source.length() || block.length <= 0`.
     (`offset == length` is skipped; `offset == length - 1` with `length 1` is read.) `source.length()` is queried per block (cheap; same as C# `source.Length`).
   - `to_read = min(min(block.length, MAX_BLOCK_READ_BYTES), source.length() - block.offset) as i32`. A block claiming to extend past EOF is therefore read to the end, a block longer than 4 MiB is
     clamped to exactly 4 MiB (golden `block-length-clamped-to-4-mib`: the recorded read has `count == 4194304`); `i64::MAX`, `i64::MIN`, `2^31` and `2^31 - 1` lengths must not overflow or wrap
     (golden `block-long-max-length`, `block-int-max-plus-one-length`, `block-length-long-min-is-skipped`). Do NOT compute `offset + length`.
   - `source.read(offset, to_read)`: `Err(_)` (any `RawHeaderError` variant: the C# `catch (InvalidDataException)` covers hostile data, exhausted header budget, wrapped I/O errors, the Rust twin
     of all of them is the single `Err`) sets `complete = false` and goes on with the NEXT block (it does not stop, golden `failure-on-first-block-still-tries-later-blocks`). Everything else the C#
     method does not catch is unreachable here: `ArgumentOutOfRange` needs a negative offset/count and `Canceled` needs a token, neither can occur, so `Err(_)` is a catch-all that never panics.
   - An empty slice is skipped (`continue`, `complete` untouched; unreachable with the real sources because `to_read >= 1`, but custom sources may do it).
   - Parse: `is_tiff_header` => `try_parse_tiff_block_with(span, block.ifd_is_exif)`; otherwise `try_parse_jpeg(span)` and `ifd_is_exif` is IGNORED (golden `jpeg-block-ifd-is-exif-flag-is-ignored`).
     `read` returns a slice borrowed from `source`: finish parsing before the next `read` (the parsed `ExifSummary` is owned, so this is automatic).
   - A parse result that is `None` or `is_empty()` changes nothing (no merge, no break, `complete` untouched).
3. **First non-empty summary** becomes `merged`; `date_from_exif_ifd = block.ifd_is_exif && summary.date_taken.is_some()`.
4. **Later non-empty summaries** (precise order, do not "simplify"):
   1. `prefer_later_date = block.ifd_is_exif && !date_from_exif_ifd && summary.date_taken.is_some()` computed BEFORE merging, from the new block's own summary.
   2. `merged = merge(merged, summary)`: per field `first.or(later)` for all eight (`date_taken, camera_make, camera_model, lens_model, iso, focal_length, f_number, exposure_time`), i.e. the FIRST
      block that has a value wins, `Some("")` counts as a value.
   3. If `prefer_later_date`: `merged.date_taken = summary.date_taken` and `date_from_exif_ifd = true`. Effect: CMT1 (plain block) carries `DateTime` (file change time), CMT2 (`ifd_is_exif`) carries
      `DateTimeOriginal` (capture time), so the capture time replaces the change time. Consequences pinned by golden cases (do not special-case, just port the three lines):
      an `ifd_is_exif` date never replaces an earlier `ifd_is_exif` date; an `ifd_is_exif` block WITHOUT a date does not set `date_from_exif_ifd`, so a later `ifd_is_exif` block with a date still replaces a
      date that came from a plain block in between (`exif-block-without-date-then-plain-date-then-exif-date-exif-date-replaces`); a plain block never replaces anything; when the FIRST adopted summary
      comes from an `ifd_is_exif` block with a date, `date_from_exif_ifd` starts true.
   4. The replaced date is applied even if `merged` was already complete before this block (it cannot be: the walk stops at completeness, see 5).
5. **Early stop.** After each adopted/merged summary (3 and 4) `if is_complete(&merged) { break }`. `is_complete` = all eight fields `Some`. A first block that is already complete ends the walk after ONE read
   (golden `first-block-complete-later-exif-block-not-read`: `reads` has one entry, so a later `ifd_is_exif` date cannot override, `RawExifMergeGapTests.TryReadExif_FirstBlockAlreadyHasEveryField_LaterBlocksAreNotRead`).
6. **Result.** `RawExifRead { summary: merged, complete }`. `complete` is `false` iff at least one `source.read` returned `Err`, even if the summary is complete or a later block succeeded
   (`failure-on-first-block-second-succeeds-complete-stays-false`). Skipped blocks (range checks, empty span, empty summary) never clear it. When the walk breaks early, errors that would have happened in the blocks never read
   do not count. The caller (RawDecoder, W5-12) must not cache a `None` summary with `complete == false` as "this file has no EXIF".
7. **Header budget.** Every block read is charged by the source (`InMemoryRawHeaderSource` / `SourceRawHeaderSource`: whole 64 KiB blocks, 8 MiB total, `RawContainerLimits.MAX_HEADER_BYTES`). With the
   4 MiB clamp, a container with 3+ distinct large blocks can exhaust the budget: that read returns `Err`, `complete = false`, the summary of the blocks before it is kept
   (golden `header-budget-exhausted-on-third-block`). This code does not count bytes itself.
8. **Never panics, never loops forever, never allocates from a length:** the only allocation is the parser's. No slicing/indexing at a computed index in this file (`merge` and `is_complete` use field access only);
   the loop is bounded by `exif_blocks.len()` (a hostile container reader can produce at most a few dozen blocks, but the code does not rely on it).
9. **Block order is meaningful:** iterate with `for block in &container_info.exif_blocks` (a `Vec`, input order), never a set/map.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- 3 Integer width: offsets/lengths are `i64`, `to_read` is `i32` ONLY after both `min`s (C# `(int)Math.Min(Math.Min(block.Length, Max), source.Length - block.Offset)`); no `usize` casts of block fields.
- 8/9 `Option` is C# `null`: `first.or(later)` (`Option::or`), not `later.or(first)`; `Some("")` stays `Some`.
- 10 Ordering: first block wins; the walk order is the list order; the date rule above is order dependent.
- 4/5 Exceptions as control flow: the C# `catch (InvalidDataException)` is `Err(_) =>` and must not also swallow a panic; `complete` is an extra output, not an error.
- `ExifSummary` has no C# `with` here: `ExifSummary { date_taken: ..., ..first.clone() }` or build field by field; `ExifSummary: Clone` (merged), no `Copy`.
- INV ids: none owned. INV-12 (decoder routing) and the RAW exif-cache rule ("incomplete => do not remember null") are consumed by W5-12/W4 caches: this unit only provides the flag.
- Hardening: golden cases with `i64::MAX`/`i64::MIN` offsets and lengths, 0/negative lengths, blocks past EOF, `fail_reads`, budget exhaustion, ORF magic fuzz bytes; `cargo test` must show no panic.

## Open questions
- **Q1 (header error type conflict between drafts).** W5-01a models `RawHeaderError { message, cause: Option<RawHeaderCause> }` in `formats.rs`; W5-01b models `enum RawHeaderError { InvalidData, ArgumentOutOfRange, Canceled }` in
  `contracts.rs`. This stub does not care: it only needs `RawHeaderSource::read(..) -> Result<&[u8], E>` and matches `Err(_)`. Its compile-check shim uses a unit-like `RawHeaderError`. The lead picks one type; no change here.
  The tests' `ThrowingSource` builds the error with whichever constructor survives (`RawHeaderError::invalid_data(..)` in 01b, `malformed(..)` in 01a).
- **Q2 (import paths).** The stub imports `crate::formats::limits::MAX_EXIF_BLOCK_BYTES` (01a) and `crate::{RawContainerInfo, RawHeaderSource}` (root re-exports from the 01a/01b `mod-lines.txt`). If the lead moves them, only the two `use` lines change.
- **Q3 (return shape).** `RawExifRead` struct vs `(Option<ExifSummary>, bool)`. Recommended: the struct (named fields, no positional mix-ups in `RawDecoder`). Mechanical to change.
- **Q4 (corpus tests and the strict switch).** Same open point as W5-03/05/06: provisioning of `tests/fixtures/raw-corpus` and the `PHOTOREVIEW_RS_RAW_CORPUS(_STRICT)` env names. This unit just calls `pr_test_support::RawCorpus` as proposed there.
- **Q5 (`ArgumentOutOfRange` swallowed).** C# would let an `ArgumentOutOfRangeException` from a source escape `TryReadExif` (only `InvalidDataException` is caught). It cannot happen with the guards above, so the Rust `Err(_)` catch-all is behaviourally
  identical for every reachable input; kept simple on purpose (documented, not tested).
