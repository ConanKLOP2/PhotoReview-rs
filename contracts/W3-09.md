## What is exercised together

`FileActionService` (W3-04) -> `JournalTransaction` + `OperationJournal` (W3-01) -> `UndoService` (W3-05, sharing the service's gate) /
`RecoveryRetryService` (W3-06) -> restart = brand-new objects over the surviving `FakeFileSystem` -> startup reconcile (W3-03).
Every scenario is run once per (numbered mutating call x applicable `FaultKind`): CrashBefore, CrashAfter, CrashPartial,
CrashMoveCopiedNotDeleted, FailOnce, FailPartial, FailUnauthorized (default matrix) or CancelAfter (cancel matrices).
After each run (`verify`, port of C# `VerifyAsync`):

1. what the code REPORTED is true on the disk (success effects; failed Move's `source_removed`; undo `restored_paths`, INV-5/6);
2. the scenario's extra check (undo stack truthful and retryable; dismiss truthful; permanent delete in scope; folders);
3. `check_state` right after the fault: no photo lost (folder, bin or intended permanent delete), nothing left its place or
   appeared without a journal line (INV-3: Prepared before the first mutation), every live verdict true;
4. restart + reconcile: nothing Prepared, `check_state` again, a second reconcile (same and new instance) appends nothing;
5. follow-ups: Retry of every Recovery item, `check_state`, reconcile no-op, then a same-named foreign photo moved into
   `sel` never overwrites or loses anything.

Second-order matrices: the startup reconcile interrupted at each of its own calls (CrashBefore/CrashPartial/FailOnce) after a
CrashBefore/CrashAfter of the action must reach the uninterrupted verdict; the Recovery retry interrupted after a real crash;
a double fault (crash, restart, the user acts again and that is faulted at every call by every kind).

`CrashMatrixTests` keep their own fake (`CrashPointFs`, port of `CrashPointFileSystem`): crash before every mutation of a
Move/Copy/Recycle/undo/retry, and a REAL torn append (half the bytes reach the file, the process lives on) at every append
position; the next append must start on a fresh line.

## Rust mapping

- `FaultRig` -> `Rig` (`restart()` re-arms the injector healthy, new `CancelToken`, new journal/service/undo); `Outcomes` ->
  `Vec<Outcome>` (`Action`, `Group`, `Undo`, `Dismiss`). C# async lambdas -> `Fn(&mut Rig) -> Result<(), String>`; `Err` = something
  escaped the code under test (only `Err(Canceled)` of `retry_move_or_copy` can), checked like the C# `catch (Exception) when (alive)`.
- `StepClock`: 2026-10-01T00:00:00Z + 1 s per read. Journal: `AppPaths(C:\Users\test\AppData\Local)`, no-op append retry delay,
  `NullLog` (never the real `FileLog`).
- `FaultBin`: send / restore / permanent delete numbered through `FaultInjectionFileSystem::mutate`. DIVERGENCE (P-13): a failed
  restore is `Err` (the Rust `RecycleBin::try_restore` contract) where the C# fake swallowed it into `false`.
- `CrashPointFs`: a dead process answers `false`/`None` from the non-failing signatures (`file_exists`, `get_file_stat`), as
  `FaultInjectionFileSystem` does (C# throws); `try_copy_new_with_proof` is the trait default (exists + one numbered copy).
- The 4 "guard" facts of the gap class (`CancelAfterPrepared_*`, `Unauthorized_*`, `PermanentDelete_NotOptedIn_*`) were already
  ported with hooks in W3-04 (`file_actions_service*.rs`); they are ported again here on the real fault rig.
