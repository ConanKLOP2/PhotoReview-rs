Compile-checked stub. The trait is `&self` with interior mutability because one instance is shared as `Rc<dyn OverlayTooltips>` by the overlay (`sync`), the message handler (`relay_mouse`) and the main window (`dispose`), and the control can be re-entered by nested messages.

## Semantics (C# is the spec)
1. **Control creation** (`NativeTooltipHost::new`): `owner == 0` -> `HostError::InvalidArgument { param: "owner", message: "A window handle is required." }` before any OS call. `comctl::common_controls::init_common_controls_ex(ICC_BAR_CLASSES)` (value 4; the C# name `IccWin95Classes` is NOT the 0xFF constant of `control_constants::ICC_WIN95_CLASSES`: trap T1), then `create_window_ex(WS_EX_TOPMOST, "tooltips_class32", None, WS_POPUP | TTS_ALWAYSTIP | TTS_NOPREFIX, CW_USEDEFAULT x4, owner, 0, get_module_handle(), 0)`; `0` -> `HostError::Win32 { operation: "Creating the tooltip control failed.", error: last error }`. The control is a popup OWNED by the shell window; it has no subclass on the owner (mouse arrives by `relay_mouse`).
2. **`sync`** (C# 68-113, exact order): `tip == 0` -> return. `dpi <= 0` -> `1`. `if dpi == self.dpi && same count && every element equal` -> return (NaN never equals the stored `NaN`, so the first call always builds). Else: for `i` from the LAST old tool to the first send `TTM_DELTOOL` with `Info(i, default bounds, 1, 0)` (id `i + 1`, `hwnd` owner); if `dpi != self.dpi` store it and send `TTM_SETMAXTIPWIDTH` with `round_ties_even(420 * dpi)` (C# `(nint)Math.Round`); store the new list; for each tool `TTM_ADDTOOL` with `Info(i, tool.bounds, dpi, text)` where `text` is a NUL-terminated UTF-16 copy that is freed right after the call (the control copies it). The pointer lifetime rule is T3.
3. **`Info`**: `cbSize = size_of::<TTTOOLINFOW>()` (72), `uFlags = 0` (a rectangle tool: no `TTF_IDISHWND`, no `TTF_SUBCLASS`), `hwnd = owner`, `uId = index + 1`, `rect = tool_rect_pixels(bounds, dpi)`: `left = floor(x * dpi)`, `top = floor(y * dpi)`, `right = ceil((x + width) * dpi)`, `bottom = ceil((y + height) * dpi)` (the box is rounded OUTWARDS; Rust `as i32` saturates and maps NaN to 0 where C# gives `int.MinValue`: documented, not reproduced), `lpszText = text`.
4. **`relay_mouse`**: nothing when `tip == 0` or no tools. Else `TTM_RELAYEVENT` with `MSG { hwnd: owner, message, wParam, lParam, pt.x = low word, pt.y = high word }` (signed 16 bit; `time = 0`). Messages relayed: `WM_MOUSEMOVE`, `WM_LBUTTONDOWN`/`DBLCLK`, `WM_LBUTTONUP` (15f decides which).
5. **`set_initial_delay(ms)`** = `TTM_SETDELAYTIME(TTDT_INITIAL, ms)`; `is_showing` = `is_window_visible(tip)`; `text_of(i)` = `TTM_GETTEXT` into a 512-`u16` buffer with `Info(i, default, 1, buffer)`, empty for an out-of-range index or after dispose. These exist only for tests (C# `internal`); keep them `pub` (integration tests live in `tests/`).
6. **`dispose`**: `tip.replace(0)`; if non-zero `destroy_window` (error ignored); clear the tools. Idempotent, also called by `Drop`. After it `sync` and `relay_mouse` do nothing and `tool_count()` is 0.
7. **`DeferredTooltips`**: `new(create, poster)` stores the factory and calls `poster.post(UiPriority::Background, job)` where `job` upgrades a `Weak<DeferredState>` and runs `create_now` (the job never keeps the state alive). `sync` before creation stores a COPY of the list and the DPI (latest wins, `pending_dpi` starts at `1`); after creation it forwards. `relay_mouse` before creation is dropped. `create_now`: return if disposed, already created or failed; run the factory (taken out of its slot, so a second job cannot run it again); `Ok(control)` -> store it, `control.sync(pending, pending_dpi)`, clear pending; `Err(_)` -> `failed = true`, no panic. `dispose`: set `disposed`, dispose and drop the control if any; a later `create_now` does nothing.
8. **Why deferred**: loading comctl32 v6 and creating the window costs about 3 to 4 ms (C# comment in `AttachOverlay`); it must not sit on the path to the first frame. The first `sync` normally arrives in the first `render`, long before the Background job; the pending list is what the control receives.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (constant naming): `ICC_BAR_CLASSES` is 4; do not use `control_constants::ICC_WIN95_CLASSES` (255) "because the C# says Win95": harmless but a different value; a test pins 4.
- T2 (DPI): bounds are DIP in, physical pixels out; `floor`/`ceil` outwards; the max tip width is `round_ties_even(420 * dpi)`; a `dpi` change alone rebuilds all tools (the pixel rectangles change) and re-sends the width.
- T3 (pointer lifetime): the `TOOLINFOW`, the `MSG` and the text buffer are locals that outlive the `send_message` call; `TTM_ADDTOOL` copies the text, so the buffer is dropped after the call; `TTM_GETTEXT` writes into a buffer that is at least `512` units. Every `send_message` has a `// SAFETY:` naming the message and the structure it passes.
- T4 (thread affinity): a window belongs to its creating thread: create, sync, relay and destroy on the UI thread. The type is `!Send` (`PhantomData<*const ()>`), because `HWND`s are plain integers here and nothing else would stop a cross-thread use. `Drop` on another thread is therefore impossible.
- T5 (comctl32 v6): the v6 control needs the 72-byte `TOOLINFOW`. A test executable has no manifest (the v5.82 control a manifest-less process loads accepts only the 48-byte size): native tests run inside `win32::activation_context::ActivationScope` with the crate's `shell.manifest` (D-W8B3-8), exactly as the C# test did. The app exe embeds the manifest (W8-20a).
- T6 (re-entrancy): `sync` is called from `render` inside a frame, `relay_mouse` from the message handler; neither holds a `RefCell` borrow across `send_message` (the control can send `WM_NOTIFY` to the owner during `TTM_ADDTOOL`/popup).
- T7 (deferral lifetime): the posted job holds a `Weak`; if the dispatcher outlives `DeferredTooltips`, the job is a no-op.
- T8 (error mapping): C# let `ArgumentException` (owner 0) escape `CreateNow` (only `Win32Exception`/`InvalidOperationException` are caught). In Rust every `Err` of the factory means "no tooltips" (Different-by-construction; the 15j factory passes a valid HWND, so the case does not arise).

## Safety rules (`// SAFETY:` per block)
`NativeTooltipHost`: (a) `create_window_ex` (class name is a static NUL-terminated string, `param = 0`, owner is a window handle the caller owns); (b) each `send_message` (the wrapper is `unsafe` per D-W8B3-4 because `lparam` may be a pointer): `TTM_ADDTOOL`/`TTM_DELTOOL`/`TTM_GETTOOLINFO`/`TTM_GETTEXT` pass `&mut TTTOOLINFOW` (live local, `cbSize` set, `lpszText` valid for the call), `TTM_RELAYEVENT` passes `&mut MSG` (live local), `TTM_SETMAXTIPWIDTH`, `TTM_SETDELAYTIME`, `TTM_GETTOOLCOUNT` pass integers. No `unsafe` outside `NativeTooltipHost`.

## Error mapping
| C# | Rust |
|---|---|
| `new NativeTooltipHost(0)` -> `ArgumentException` | `Err(HostError::InvalidArgument { param: "owner", .. })` |
| `CreateWindowEx` 0 -> `Win32Exception` | `Err(HostError::Win32 { operation: "Creating the tooltip control failed.", .. })` |
| `DeferredTooltips.CreateNow` catches `Win32Exception`/`InvalidOperationException` | any `Err` -> `failed`, silent |
| `TTM_*` message results | ignored (C# ignored them), except `TTM_GETTOOLCOUNT` and `TTM_GETTEXT` (tests) |
| null arguments | not representable |

## Open questions (recommended default in bold)
1. **`LocalPoster` seam** (cross-unit, W8-13g): `pr_core`'s `UiAction` is `Send`, but the deferred job must reach `!Send` state. The 13g stub (branch `wave8/b4-contracts-main`, `host::main_window::core`) already declares an identical `LocalJob`/`LocalPoster` and one implementation `UiLocalPoster` (thread-local FIFO per priority plus one `Send` wake job per job), shared by 15j, 15g, 16c, 16d, 16h (D-W8B4M-11). **Recommended**: when 13g is on master the lead replaces the trait here by `pub use crate::host::main_window::core::{LocalJob, LocalPoster}`; until then the local copy keeps 15g compilable and testable. Alternative: make `DeferredTooltips` `Arc<Mutex<..>>` with `Send` bounds on the control (rejected: `HWND` use from a wrong thread becomes possible).
2. **`ICC` class value**: **`ICC_BAR_CLASSES` (4)**, the C# value; alternative `ICC_WIN95_CLASSES` (0xFF) is a superset and harmless, but then the "pin 4" test goes.
3. **`TextOf`/`IsShowing`/`SetInitialDelay` visibility**: **`pub`** (integration tests); alternative `pub(crate)` plus unit tests inside the module.
4. **Tooltip text with embedded NULs**: C# `StringToCoTaskMemUni` would truncate at the first NUL; Rust **keeps the same truncation** (the buffer is NUL-terminated, the text is cut at the first `\0`); no tooltip text in the app contains one.
