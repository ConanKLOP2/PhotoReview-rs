- Semantics notes:
  1. **Why the split.** The C# file mixes one pure policy (`ReadMetadataValues`), one pure decode (`ReadVariant`, which only needs the memory the
     pointers refer to) and three COM calls. The stub keeps the first two `unsafe`-free and testable with fakes; the COM calls are behind three tiny
     traits so this unit does not depend on how W4-11a spells its wrappers (the W4-11a/W4-11c adapters `impl` the traits). All `unsafe` of this unit:
     `RawMemory` (five one-line reads: `CStr::from_ptr`, UTF-16 walk, three `read_unaligned`), `PropVariant::clear` (`PropVariantClear` from ole32,
     declared with `extern "system"` in this file; the W4-11a stub (reviewed) does NOT declare it, so it is this unit's single declaration), and nothing else.
  2. **`read_frame_metadata` flow.** (a) `frame.metadata_query_reader()`; `Err` => `MetadataRead { orientation: 1, exif: None }` (the C# catch-all,
     including when `read_orientation == false`). (b) one zeroed `PropVariant` for the whole read. (c) the query closure: `reader.get_metadata_by_name(name,
     &mut pv)`; negative HRESULT => `Ok(None)` (the C# `< 0 ? null`); otherwise `decode_variant(pv.as_bytes(), &raw_memory)`; in BOTH cases `pv.clear()`
     afterwards (the C# `finally`), which also zeroes the buffer for the next query. The closure never returns `Err` natively (the C# method is
     `PreserveSig`; the `Err` channel exists for the pure function and for tests). (d) `read_metadata_values(closure, ..)`. (e) drop the reader and the
     buffer (the C# `finally`: `PropVariantClear` once more is harmless on the zeroed buffer and may be skipped).
     `RawMemory::new` is called with a `// SAFETY:` that the addresses come only from `pv` between a successful query and its `clear`: decode happens
     BEFORE `clear`, and the decoded `QueryValue` owns its data (copies strings/elements), so nothing outlives the buffer.
  3. **`decode_variant` table** is in the stub doc. Points that are easy to get wrong (all pinned by `wic-exif-variant` cases):
     - the value is `vt` = first two bytes only; the three reserved WORDs (`reserved-bytes-ignored`) and the unused upper bytes of the union
       (`ui2-upper-bits-ignored`, `i4-upper-bits-ignored`, `ui1-upper-bits-ignored`) never matter: read exactly the width of the type
       (`u16::from_le_bytes([raw[8], raw[9]])`, `i32::from_le_bytes(raw[8..12])`, ...);
     - `VT_I2`/`VT_I4` give SIGNED `I16`/`I32`; `VT_UI1` gives `U8`; `VT_I8` gives `I64`, `VT_UI8` gives `U64`: `exif_query::as_rational` tells signed from unsigned
       by this variant, so mapping `VT_I8` to `U64` is a bug (mutation X06 of the C# run: "RATIONAL reads 32 bits");
     - `VT_LPSTR` is UTF-8 (WIC hands the EXIF ASCII bytes through unchanged, so non-ASCII camera strings arrive as UTF-8 or as raw Latin-1 bytes:
       invalid bytes become U+FFFD, `ansi-string-invalid-byte-is-replacement`, `ansi-string-latin1-high-bytes-are-invalid-utf8`); mutation X04 was
       "UTF-8 read as UTF-16". A NULL pointer is `None`, an empty string is `Some("")`;
     - only FOUR vector types are supported (`UI2`, `UI4`, `I8`, `UI8`), only the first element is read, element count is a SIGNED int32 and `<= 0` is
       `None`, a NULL element pointer is `None`; the element pointer lives at byte `8 + size_of::<usize>()` (16 on x64, not 12). Everything else is `None`:
       `VT_UI1` vectors (EXIF BYTE arrays), `VT_I2`/`VT_I4` vectors, `VT_LPSTR` vectors, `VT_ARRAY` and any extra flag bit.
       Mutation X05 was "UI2 vector gives null".
     - Vector results are the one-element array variants (`U16s`, `U32s`, `I64s`, `U64s`), NOT scalars: `exif_query::as_integer` reads element 0 of an array
       and `as_rational` of an `I64s`/`U64s`; scalars and one-element arrays are not interchangeable there (W4-04b trap 2).
  4. **`read_metadata_values` order and independence** (the oracle records `queried`):
     - orientation first (only when requested): query `/app1/ifd/{ushort=274}`; `as_integer`; when the value is not `Some(1..=8)` query
       `System.Photo.Orientation` (the C# overwrites `value` even with `null`); final `Some(1..=8)` is the orientation, anything else 1. Implement it by
       calling `pr_imaging::orientation::read_from_wic` with a closure that maps `query(name)` through `exif_query::as_integer` (W4-02a owns the rule; do
       not copy it). A query `Err` gives 1 (C#: the `catch` of `ReadFromWic`), and the EXIF half still runs.
     - then, when `exif_ifd_root` is `Some`, `exif_query::read(&adapter, root)`. `exif_query::read` takes `&dyn Fn(&str) -> Option<QueryValue>` and has no
       failure channel, so the adapter keeps a `Cell<bool> failed`: on the first `Err` set it, and from then on return `None` WITHOUT calling `query`
       (a C# throw aborts the interpreter: no later query is made, `exif-aborts-at-first-throw-no-later-queries`). After `read` returns, `failed` =>
       `exif: None` even if `read` produced a summary (`exif-throw-on-last-query-discards-the-rest`). `query` is `FnMut`: wrap it in a `RefCell`.
     - `exif_ifd_root == None` => `exif: None`, no EXIF query at all (`root-null-no-exif-even-with-tags`). `Some("")` is used verbatim.
     - `read_orientation == false` => orientation 1, orientation paths never queried, EXIF half unaffected.
  5. **Container choice.** `exif_ifd_root_for_container`: `19e4a5aa-5662-4fc5-a0c0-1758028e1057` (JPEG) => `"/app1/ifd"`, `163bcc30-e2e9-4f0b-961d-a3e9fdb788a3`
     (TIFF) => `"/ifd"`, every other GUID `None` (PNG, GIF, BMP, HEIF, WebP: no EXIF read). The GUID byte arrays use the .NET `ToByteArray` order of
     `pr_core::catalog::explorer_types::Guid` like W4-11b; the `constants` row of the golden pins both strings (the Rust test formats the `Guid` as "D").
     A failing `GetContainerFormat` is `None` (`catch (COMException)`); in C# any NON-COM exception would propagate, in Rust there is only the HRESULT.
  6. **No exceptions escape** (trap 9): `read_frame_metadata` and `read_orientation` return plain values. The only C# exception that is deliberately
     not swallowed is `OutOfMemoryException`; Rust has no equivalent, so there is no `catch` branch to port.

## Golden package
- `oracle/W4-11d.cs`: commands `wic-exif-values` (reflection on `WicExifReader.ReadMetadataValues`; throwing queries; records `queried`; last row
  `constants` with the two container GUIDs) and `wic-exif-variant` (real unmanaged 24-byte buffer, `WicExifReader.ReadVariant` by reflection; strings,
  scalars, vectors, unsupported vts). Needs `W4-04b.cs` (`W404bValue`, `W404bRational`). No WIC/COM call is made: the oracle runs wherever
  `PhotoReview.Imaging.dll` loads. Dispatch lines are in the file header.
- `golden-inputs/{wic-exif-values,wic-exif-variant}.json` (generated by `gen_inputs.py`), outputs in `golden-reference/`.
- Case design: orientation tag 0-9, 255, 65535, i32 -1 and every `as_integer` shape (array first element, empty array, negative `i16[]` CLR
  reinterpretation, string/u64/double not integers); Windows fallback for exif absent / 0 / 9; in-range EXIF never falls through; not-requested with
  throwing queries; each half failing alone, both failing, a throw in the middle/at the end/inside the date chain; JPEG, TIFF, null and empty roots.
  Variants: every supported scalar with upper-bit garbage and reserved bytes, every unsupported vt, strings incl. null/empty/non-ASCII/supplementary
  plane/invalid UTF-8, the four vectors plus count 0, -1, huge, no pointer, `VT_ARRAY`.
- Rust harness for `wic-exif-variant`: build `raw` from `vt` (LE u16 at 0), `reserved_hex` (bytes 2..8), `scalar` (`i64::to_le_bytes` at 8) or
  `count` (`i32` at 8) plus `pointer` (`usize` at 16, value `0x1000` when a payload exists and `pointer` is not `false`); the fake `VariantMemory`
  maps `0x1000` to the payload bytes (`utf8`: text or `bytes_hex` + NUL; `wide`: UTF-16LE + NUL; `u16/u32/i64/u64`: LE elements). Compare `type` and
  `value` exactly as the oracle prints them (decimal strings; 8/16-bit values too). Lone surrogates are not in the goldens (D5 divergence below).
- Rust harness for `wic-exif-values`: a `query` closure answering from `answers` (types of W4-04b's `W404bValue` plus `throw` => `Err(QueryFailed)`),
  recording `queried`; compare `queried`, `orientation`, `summary` like the W4-04b `exif-query` test.

## Open questions
1. `exif_query::as_integer` visibility. Recommended: W4-04b makes `as_integer` `pub` (one word) and the lead merges that with this unit. Alternative,
   if the lead wants W4-04b to stay closed: W4-02a gains `pub fn read_from_wic_values(query: &mut dyn FnMut(&str) -> Result<Option<QueryValue>, QueryFailed>) -> i32`
   that does the `as_integer` mapping itself (then `pr-imaging::orientation` depends on `exif_query`, which it logically does already).
2. The COM seam names. This unit defines three one-method traits instead of calling W4-11a types directly so that the contracts of W4-11a and W4-11d can be
   written in parallel. If W4-11a's final wrappers already expose `get_metadata_by_name`/`get_container_format` with compatible signatures, the porter
   may delete the traits and call the wrappers (keeping every public function signature otherwise); the tests then use W4-11a's fakes.
3. D5 divergence (UTF-16 text with a lone surrogate): C# `PtrToStringUni` keeps it, Rust `from_utf16_lossy` gives U+FFFD. The only consumer is
   `ExifSummary::create`, whose cache codec goes through UTF-8 where the C# also emits U+FFFD (same persisted bytes, W4-04b trap 3). Mark the line
   `// DIVERGENCE:`. Not covered by a golden.
4. Native-test fixture: the repo has no EXIF-bearing JPEG/TIFF under `tests/fixtures`. The native tests should create one at test time (hand-built
   JFIF + APP1 bytes with Make "JpegMaker" and orientation 6, and a TIFF with IFD0 Make "TiffMaker"); W4-03a's fixture builders may already provide that.
   Lead decides whether a binary fixture is added instead.
5. Duplicate container GUID constants. The W4-11a stub already has `interop::guids::CONTAINER_FORMAT_JPEG/TIFF` as `windows_core::GUID`
   (`from_u128`); this stub declares the same two values as `pr_core::catalog::explorer_types::Guid` byte arrays because the `DecoderContainer`
   seam returns that type. Both are pinned by goldens (`wic-interop-constants`, this unit's `constants` row), so drift is caught. Lead may
   instead have the W4-11a adapter convert `GUID` to `Guid` and keep only one list; either is behaviour-neutral.
6. (Review) Golden fix applied: the lens-model query in `gen_inputs.py` / `wic-exif-values.json` was tag 41012 (wrong); C# `TagLensModel` is
   `0xA434` = 42036. Regenerate the reference output with the oracle at wiring time.
