- Semantics notes:
  1. **Layout of an entry.** `[0..4)` `"PRVC"`; `[4]` version; `[5]` backend byte; `[6]` orientation; `[7]` alpha flag; `[8..24)` four `i32`
     little-endian (`width, height, original_width, original_height`). v7 only: `[24..26)` `u16` LE EXIF length `N`, `[26..26+N)` EXIF block
     (`exif_summary::codec::encode` output). Then the JPEG payload to end of file. v6: payload at 24, no length field. No checksum, no length.
  2. **Validation order of `parse_entry` (C# `Read`; keep it, the golden pins which message wins).**
     a. `len < 24` => `Io(UnexpectedEof)` (C# `ReadExactly` => `EndOfStreamException`; message free, callers treat it as corrupt).
     b. magic differs => `InvalidData("Preview cache entry has an invalid header magic.")`.
     c. version not 7 and not 6 => `"Preview cache entry is version {v}, expected 7."` (decimal, invariant).
     d. backend byte not defined (only 0..=3; `LibRaw = 3` IS accepted) => `"Preview cache entry has an invalid decoder backend byte."`.
     e. orientation outside 1..=8 => `"... has an invalid orientation byte."`. f. alpha = `byte != 0`.
     g. `width <= 0 || height <= 0` => `"... has invalid pixel dimensions."`. h. `original_width <= 0 || original_height <= 0` =>
        `"... has invalid original dimensions."`.
     i. v7 only: `len - 24 < 2` => `"... has no payload."` (so a 24- or 25-byte v7 file is "no payload", not EOF); read `n`;
        `n > 1024 || n > len - 24 - 2` => `"... has an oversized EXIF block."`; `n > 0` => `exif = codec::decode(block)` (malformed = `None`, never
        an error; `n == 1024` is accepted); `exif_block_size = 2 + n`.
     j. `payload_len = len - 24 - exif_block_size`; `<= 0` => `"... has no payload."`; `> i32::MAX` => `"... payload is implausibly large."`.
     k. `payload_len < 4 || payload[^2] != 0xFF || payload[^1] != 0xD9` => `"... payload is truncated (no JPEG end-of-image marker)."`
        (exactly 4 bytes `FFD8FFD9` passes this check and fails later in the decoder).
     All messages start with `"Preview cache entry"`. `file_bytes = len as i64`.
  3. **`read`.** Open `read(true)` with Windows share mode `FILE_SHARE_READ | FILE_SHARE_DELETE` (=5, `OpenOptionsExt::share_mode`, `cfg(windows)`),
     so the pruner can delete an entry that a reader holds. Read the file once (whole file into a `Vec`; observable behaviour equals C#'s
     header-first streaming). `parse_entry`, then `codec.decode_jpeg(payload, if has_alpha { Pbgra32 } else { Bgr32 }, width, height)`. The decoder
     error is returned as is (it is already `InvalidData`). No second open, no pooled buffer needed.
  4. **`build_entry_prefix` / `write_atomically`.** Always writes version 7, alpha byte 0 (JPEG never carries alpha; an opaque `Pbgra32` buffer is
     stored as opaque JPEG and read back as `Bgr32`), backend byte `backend.value() as u8`, orientation byte. `original_* <= 0` => the pixel
     size (each axis independently, goldens `original-width-zero-only`, `original-height-negative-only`). EXIF bytes =
     `codec::encode(exif)` (empty vec for `None` or an empty summary), length written as `u16` LE (never exceeds 1024).
     Written file = prefix + JPEG from `codec.encode_jpeg(pixels, 95, out)`. Validation order BEFORE any file is touched (the cache folder is
     not even created on refusal): blank/whitespace-only path => `InvalidArgument`; `!opacity_verified && !is_fully_opaque(pixels)` =>
     `InvalidArgument("Bitmaps with transparent pixels cannot be stored in the JPEG preview cache.")`; orientation outside 1..=8 =>
     `ArgumentOutOfRange`. Transparency is therefore reported before a bad orientation (golden
     `transparent-and-bad-orientation-reports-transparency-first`). `is_fully_opaque` is W4-16a: `Bgr32` is always opaque; `Pbgra32` scans
     every row for `A < 255` (stop at the first).
  5. **Atomicity (INV-2).** Delegate to W4-08a: temp file next to the target named `<cachePath>.<32 hex>.tmp` created with `create_new`, written,
     flushed, cancellation re-checked, `rename` over the target (replace allowed), temp removed in every failure path (only when this call created
     it). This unit adds no durability flush (disposable cache; a lost write is a miss). `cancel` is `pr_core::sync::CancelToken`
     (C# `CancellationToken`); `Canceled` and `OutOfMemory` are the only non-cache-entry failures (C# `IsCacheEntryFailure` excludes
     cancellation and `InsufficientMemoryException`: an entry whose decode ran out of memory is intact and is KEPT). The decoder (W4-11e)
     reports its WIC out-of-memory COM error as `OutOfMemory`; every other decoder failure is `InvalidData`.
  6. **Header fields are never trusted for allocation.** `decode_jpeg` gets the header size and must check it against the JPEG's own size BEFORE
     allocating (that is W4-11e's `WicCacheImageReader` contract); this unit only guarantees `width, height > 0`.
  7. **Decoded-image helpers.** `estimated_bytes = (width as i64) * (height as i64) * 4`; `downscaled = true`; the entry's orientation, backend,
     original size and EXIF are carried over. `write_decoded_image` always passes `opacity_verified = false`, so it re-scans.
  8. **Stability of other code.** `CURRENT_VERSION` is mirrored in the identity string `preview-v5-box|...` of `PreviewImageService.GetDiskCachePath`
     (D-06): the cache FILE NAME does not contain the version, so bumping it only invalidates entries by header. Do not change either.
- Traps checklist (docs/MULTI-AGENT-PLAN.md section 7): item 3 (every `i32` read is signed: `-1` and `i32::MIN` dimensions are rejected, not wrapped;
  use `i32::from_le_bytes`; `len` arithmetic in `usize`/`i64` with no underflow: check `len >= 26` before `len - 26`), item 8 (`None` exif vs empty
  block both mean no EXIF, both write length 0), item 9 (every C# `catch` class becomes one `PreviewCacheError` variant: the cache layer reacts
  differently to `Canceled`), item 1 not applicable (no strings compared). Specific traps:
  1. **v7 with 24 or 25 bytes is "no payload", not EOF** (the `len - 24 < 2` test is after the 24-byte header read).
  2. **EXIF bound uses the FILE length, not the payload:** `n > len - 26` is "oversized" even when `n <= 1024`; `n == len - 26` leaves no
     payload ("no payload"), and a 10-byte block in a 36-byte file is exactly that (goldens `exif-length-10-...`, `exif-length-11-...`).
  3. **v6 with EXIF bytes:** reading a v7 file with the version byte patched to 6 treats the EXIF block as payload (fails in the decoder, not
     in the parser; golden `v6-with-exif-bytes-misread-as-payload-fails-decode`). Do not "improve" this.
  4. **Alpha flag is any non-zero byte** (`0xFF` => Pbgra32), writer always 0.
  5. **Unknown backend byte rejects, even though the backend only labels the pixels.** `3` (LibRaw) is accepted.
  6. **The EOI check is `FF D9` at the last two bytes only.** A valid JPEG followed by one trailing byte is "truncated" (golden
     `trailing-byte-after-eoi`).
  7. **Native `PermissionDenied` on rename** (reader holds the target without `FILE_SHARE_DELETE`) is an `Io` error, not a panic.
  8. **No `unsafe` and no `windows` crate** in `pr-imaging`: share mode comes from `std::os::windows::fs::OpenOptionsExt`.

## Open questions
1. **Error type home.** `PreviewCacheError` lives in this module. W4-14/W4-09 will want one `is_cache_entry_failure` for entry, thumbnail and
   store errors; recommended: keep this enum (it is a superset of `InvalidDataException`/IO/argument), and let W4-09 define
   `DiskCacheError: From<PreviewCacheError>`. Lead decides when W4-09's contract is written.
2. **Atomic-write seam.** Shape of W4-08a's function is assumed (see Depends on). If W4-08a exposes a trait instead (to inject a failing rename in
   tests), `write_atomically` takes `&dyn AtomicFileWriter` as an extra parameter; the pure `build_entry_prefix` and `parse_entry` are unaffected.
3. **Whole-file read vs header-first.** The contract allows reading the whole file; C# reads the header first and rejects a bad entry
   without touching the rest. For the 4 GiB cache with entries of 0.5 to 1 MB this is not measurable; if a benchmark ever shows the whole-file
   read of a corrupt huge entry matters, switch `read` to header-first (no API change).
4. **`opacity_verified` and `write_decoded_image`.** C# `WriteAtomicallyAsync(IDecodedImage, ...)` has no `opacityVerified` parameter, and
   `PreviewImageService` (line about 307) calls the pixel overload with `opacityVerified: true` after its own check. Kept as is.
5. **Payload codec ownership.** The trait is defined here (the file format owns its payload contract); alternative is to put it in
   `decoder_traits` (W4-01c). Recommended: here, because only this module and `ThumbnailCache` (PNG, a different trait) use payload codecs.


## Review amendment (2026-10-23): whole-file read is not resource-equivalent on corrupt huge entries

See `docs/reviews/invariants-storage.md` M3 (Rust 809759d, C# 7eaee2a2), findings inferred from source, not executed.
