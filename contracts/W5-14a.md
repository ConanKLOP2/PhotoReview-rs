## Semantics notes (the algorithm; every line has a golden case)
1. **Argument checks, in this order** (golden `error-*`): layout first (`src.layout() != Bgr32` -> `SourceNotBgr32`; a Pbgra32 source with target `0 x 0` still reports the layout:
   `error-pbgra32-beats-bad-target`), then `target_width < 1`, then `target_height < 1`. Only the .NET type name is compared by the golden (the message text is .NET specific, not ported).
   The C# null check comes before all of them and has no Rust twin.
2. **Never upscales, per axis.** `tw = min(target_width, sw)`, `th = min(target_height, sh)` (i32 compare, so `i32::MAX` is fine: `int-max-target-keeps-source-size`). The output size is `tw x th`, not the
   requested size (`no-upscale-width-only`: 8x8 asked for 20x4 gives 8x4). The result is always `Bgr32`.
3. **Order of allocation and disposed sources.** C# allocates `dst` BEFORE any read of `src`, so a disposed source fails with `ObjectDisposedException` after the allocation (the temporary `dst` is disposed on the
   way out). Rust: `PixelBuffer::allocate(tw, th, Bgr32)?` first (allocation failure -> `Buffer(OutOfMemory)`), then every `src.get_row(y)?` maps `PixelBufferError::Disposed` to `Buffer(Disposed)`
   (`dotnet_type_name` = `ObjectDisposedException`, goldens `error-disposed-source-shrink` and `-same-size`). Do not pre-check `src.is_disposed()`.
4. **Same size = copy.** `tw == sw && th == sh`: copy each row (`stride` bytes, the FOURTH byte too, so a source alpha of 0 stays 0: golden `same-size-copy-keeps-source-alpha-0`), return. The result has a new `id`
   and independent memory. An oversized target that clamps to the source size takes the same path (`copy-via-oversized-target-keeps-alpha-0`).
5. **Averaging path** (everything else, `sw > tw || sh > th`). Every output channel is `(sum + total/2) / total` with integer division of non-negative numbers (round half up), where
   `total = sw * sh` and `sum` is the exact sum over source pixels of `value * overlap_x * overlap_y`, the overlaps being the integer lengths in the common `sw`/`tw` (and `sh`/`th`) refinement:
   - Horizontal footprint of output column `x` (`build_area_weights`): `lo = x * sw`, `hi = lo + sw` (both `i64`), `s0 = lo / tw`, `s1 = (hi - 1) / tw`; for `s in s0..=s1` weight =
     `min(hi, (s + 1) * tw) - max(lo, s * tw)`. The weights of one column sum to `sw` (property test). One flattened `weights` vector, `first[x] = s0`, `offset[x]` = start index, `offset[tw]` = len.
   - Per source row `sy` (streamed top to bottom, each row read once): horizontal pass gives, per output column, `(b, g, r)` sums `sum_k row[(first + k) * 4 + c] * weight[k]` (`i64`).
     Then `src_lo = sy * th`, `src_hi = src_lo + th`; the output rows it touches are `oy in oy0..=oy1` with `oy0 = src_lo / sh`, `oy1 = (src_hi - 1) / sh`, restricted to `oy < th`; each gets
     `rowSums * overlap` added to its accumulator with `overlap = min(src_hi, (oy + 1) * sh) - max(src_lo, oy * sh)`. The accumulator of `oy == output_row` is the current one, the other (only ever
     `output_row + 1`, because the image only shrinks) is the next.
   - When `src_hi >= (output_row + 1) * sh` the current output row is complete: emit it (`EmitRow`), swap current and next, clear the new next, `output_row += 1`.
   - `EmitRow`: bytes `d, d+1, d+2` = `(acc + half) / total` as `u8`, byte `d + 3` = `0xFF` always (the source fourth byte is ignored on this path: goldens `shrink-ignores-source-alpha-*`).
     `acc <= 255 * total`, so the quotient is at most 255 and `as u8` never truncates a real value; do not clamp, do not use floats.
   - Width-only or height-only shrinks (`tw == sw` or `th == sh`) go through the same code: `tw == sw` makes every weight 1 per column (`tw`) and `th == sh` makes every source row its own output row.
     Do not special-case them (the arithmetic is the contract, and golden `ratio-17x13-to-17x12` etc. pin it).
6. **Exactness, not approximation.** This is NOT bilinear, Lanczos, or a float area filter. The brute-force reference in the C# test is the specification; the `i64` pipeline above reproduces it exactly.
   Rust must produce the same bytes (golden `fnv1a64`), not "close" ones.
7. **No panics.** `tw, th >= 1` after the checks, so no division by zero; `sw, sh >= 1` is a `PixelBuffer` invariant. Slice indexing is within the row (`first[x] + count <= sw` by construction;
   `(first + k) * 4 + 2 < stride`). Use `usize` for indexes, `i64` for every product that mixes `x`/`y` with `sw`/`sh`/`tw`/`th`.
8. **Memory.** Working set is `3 * tw * 8` bytes times three (`row_sums`, two accumulators) plus the weights table (about `sw + 2 * tw` entries). Allocation sizes come from the buffers' own dimensions
   (the C# `new List<int>(sw + 2 * tw)` capacity hint is a pure optimisation: `Vec::with_capacity(sw + 2 * tw)` is fine; `sw + 2 * tw` cannot overflow `usize` on 64-bit).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- 3 Integer width (THE trap of this unit): C# promotes with `(long)x * sw`, `(long)sy * th`, `(long)(oy + 1) * sh`, `(long)(s + 1) * tw`. In Rust do all of these in `i64`; goldens `wide-100000x1-to-33333x1`
  (33333 * 100000 > 2^31), `wide-70000x2-to-65535x2`, `tall-*`, `big-100000x3-to-77777x2` fail on a 32-bit product. The sums are `i64` too (`255 * sw * sh` passes `i32` from about 2000 x 4000).
- 8 Null/empty: no null in Rust. 9 Exception to Result: only `?` and the mapping in note 3; there is no `catch` in the C# apart from the dispose-and-rethrow.
- 10 Stable order / determinism: single thread, no float, no `HashMap`; same input gives the same bytes on every run (the golden pins it).
- Also: no `unsafe` (buffer access is `get_row`/`get_row_mut`); the slice views over the native block are already inside `pixels.rs`.

## Open questions
1. **`ResizeError::Buffer(PixelBufferError)` vs one error per C# exception.** The stub folds `OutOfMemory`/`Disposed` into one `Buffer` variant to reuse `dotnet_type_name`; W5-14b (the decoder) must
   map `Buffer(OutOfMemory)` to its own `DecodeError::InsufficientMemory`-style result exactly as it maps the C# `OutOfMemoryException`. Lead decides the final mapping at W5-14b; the variant set here does not change.
2. **Visibility.** `resize` and `AreaWeights`/`build_area_weights` are `pub` (C# is `internal`) so the integration test and W5-14b can reach them (cross-crate/test visibility lesson of Wave 4). If the lead prefers a
   smaller surface they can become `pub(crate)` with the tests moved to a `#[cfg(test)] mod` in `area_resampler.rs` (then the porter owns that module too).
3. **Performance.** The C# inner loops are branch-light `long` arithmetic on spans. A faster Rust version (row-wise vertical accumulation with `chunks_exact`, `u32` partial sums, SIMD) is NOT part of this unit: bytes first.
   If W5-14b profiling shows the shrink dominating, open a separate perf unit that must keep `golden_pixel_area_resample` green (the benchmark for it is the `slow` case).
