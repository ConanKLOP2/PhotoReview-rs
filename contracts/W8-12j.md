## Why this unit exists (grounded in the ADR)
R0001 measured, on the unattended dev laptop (Core i7-9750H, Intel UHD 630 + RTX 2080 Max-Q), a windowed switch p50 of 5.3 ms but a p95 of 416..512 ms because 9..29 % of frames stall about 510 ms inside `EndDraw` (not in `Present`); the stall is absent with a target bitmap without swap chain (p95 0.66 ms) and with WARP, and present with the HWND
render target, the flip swap chain, activated or not, on both GPUs (about 300 ms on NVIDIA). The ADR's own next steps if the attended p95 stays above 10 ms: a waitable swap chain (`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`) and a DirectComposition visual.
Two facts found while writing the B3 contracts change the picture and make a cheaper first step possible:
1. The Rust SPIKE used `FLIP_SEQUENTIAL`, no waitable flag and no keep-warm; the production surface (W8-12d, D-W8B3G-3) uses the C# values: `FLIP_DISCARD`, two buffers, the waitable flag, `SetMaximumFrameLatency(1)` and a wait on the waitable object before drawing. The spike numbers therefore do not measure the production configuration.
2. The C# app solved the same symptom (WP21-STALL: 0.47 s blocks in `EndDraw`/`Present`, Intel UHD 630, first submission after more than about 25-33 ms of GPU idle) with a keep-warm thread (W8-12h). The Rust spike has no such thread (its `warm` step only pre-draws the next bitmap while the UI is idle, `crates/pr-shell/src/spike/viewer.rs`).

## Trigger (the unit does NOT start unless all hold)
1. W8-12d (production surface), W8-12e (draw context) and W8-12h (keep-warm) are merged, and the app (or the updated `r0001-spike` using the production surface) can run the measurement below.
2. An ATTENDED re-measure (display on, window in the foreground, laptop on AC power) was recorded in R0001 for: default adapter, adapter 1 (`PHOTOREVIEW_RS_SPIKE_ADAPTER=0|1|warp` of the spike, or `d3d11::create_device_on_adapter` in the app), keep-warm on (default) AND `PHOTOREVIEW_RS_GPU_KEEPWARM=0`, 24 MP fixtures (`r0001-spike <folder> --measure 100 --interval-ms 250`, 3 runs each).
3. The windowed p95 (arrow-handler start to `EndDraw` + `Present` returned) with keep-warm ON is **above 10 ms** (the ADR threshold; the acceptance target is under 8.5 ms). Between 8.5 and 10 ms: repeat three runs; recommended: do not start (D-W8B3S-11).
Result below the threshold: do NOT start; record the table in R0001, set its Status to Accepted when p95 < 8.5 ms, and close this unit as "not needed" in `task_on_progress.md`.

## Env switch and what it does
`PHOTOREVIEW_RS_SWAPCHAIN_EXPERIMENT` (R0002 prefix; read once when a window surface is created, by the 12d option struct; default/unset/unknown = `none`, which is exactly the production path with zero extra cost). Values (each isolates ONE change from production):
- `none`: production (`dxgi::window_swap_chain_desc`, waitable, latency 1).
- `sequential`: `DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL` (the spike's effect) with everything else production; separates DISCARD from SEQUENTIAL.
- `buffers3`: three buffers, `SetMaximumFrameLatency(2)`.
- `tearing`: `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` + `Present(0, DXGI_PRESENT_ALLOW_TEARING)` (needs the flag support that 11g Q2 left out).
- `composition`: `CreateSwapChainForComposition` (premultiplied alpha, `FLIP_DISCARD`, waitable) attached to a DirectComposition visual of the window (`DCompositionCreateDevice`, `CreateTargetForHwnd`, `CreateVisual`, `SetContent`, `Commit`). Needs the new `windows` feature `Win32_Graphics_DirectComposition` (lead adds it, versions untouched) and a window created
  with `WS_EX_NOREDIRECTIONBITMAP` (W8-13g option; otherwise the visual shows over the redirection surface).
No mode changes the Direct2D drawing code. Each mode is built by a pure descriptor function in a new file `render/swap_chain_experiment.rs` (`SwapChainExperiment::parse(&str)`, `experiment_swap_chain_desc(mode, width, height) -> DXGI_SWAP_CHAIN_DESC1`), so the values are unit-tested; the creation call in 12d gets ONE hook (one `match` at the call site).

## What is measured
Per switch (100 per run, 250 ms apart so the GPU idles between frames, the exact condition of the stall): `t_handler -> t_endDraw_returned` (the stalled call), `t_endDraw -> t_present_returned`, and optionally GPU completion (`gfx::d2d::read_pixels` of a 1x1 region after `Present`, the C# `DeviceResources.Synchronize` idea;
the ADR notes that `EndDraw` returns at submission, so completion is not otherwise visible). Reported as p50, p95, max (and the count of frames above 50 ms) in a table `mode x adapter x keep-warm` in the "Measured" section of R0001. The numbers come from the frame log (`PHOTOREVIEW_RS_FRAME_LOG`, W8-16a `frame_log`) or the spike's `--measure`;
no new timing infrastructure. No timing assertion in CI.

## What "done" means
1. The table for every mode that was run is in `docs/adr/R0001-ui-framework.md` (Measured + Reading updated), with the machine, adapter, power and display state.
2. If a mode reaches windowed p95 < 8.5 ms with no frame above 50 ms in 3 x 100 switches on both GPUs: it becomes the production default (`window_swap_chain_desc` or the 12d option default changes in the same PR, an ADR note records why), the other modes' code is DELETED (no dead experiments), the switch is removed or kept only for the winner's
   inverse as a diagnostic. R0001 Status -> Accepted.
3. If no mode helps: the experiment code is removed, the finding is recorded, R0001 stays Proposed and the lead asks the user (next options named in the ADR: other adapters or drivers, egui/Slint spikes, which were not run).
4. The 12d/12e native tests and the 11g hidden-window swap-chain test pass with the chosen default on a desktop (`--include-ignored`, result in the PR).
5. Time box: two working days. Over the box without a clear win: stop at (3).

## Tests (when started)
Pure, ordinary CI tests (hand-written): `parse` accepts the five names case-insensitively and trimmed, and maps empty/unknown to `None` (an unknown value is logged once, never an error); `experiment_swap_chain_desc` returns exact values per mode (`sequential`: `SwapEffect == FLIP_SEQUENTIAL`, `Flags == 0x40`; `buffers3`: `BufferCount == 3`; `tearing`: `Flags == 0x40 | 0x800`;
`composition`: `AlphaMode == PREMULTIPLIED`, `Scaling == STRETCH`; `none`: equals `dxgi::window_swap_chain_desc` field for field). Native `#[ignore = "native: needs desktop"]`: for each mode, a hidden `STATIC` window (as the 11g test), create, present twice, resize, present again, no HRESULT failure; `composition` only if the DirectComposition device can be created (skip with a message otherwise).

## Safety rules
DirectComposition COM calls are `unsafe fn` in windows-rs: each block has `// SAFETY:` naming the live owned interface, the valid HWND (UI thread) and that the visual/target/device are dropped before the window is destroyed (declaration order of the struct fields). No raw pointers stored. Everything is `!Send` (UI thread), like the surface.

## Open questions
1. **Is the attended session one the user can do soon?** It needs a person at the machine; recommended: run it right after W8-12d/12e/12h are merged (cheap, minutes), before anyone writes DirectComposition code.
2. **DirectComposition as the first step instead of the last?** Recommended: no; the order `sequential`, `buffers3`, `tearing`, `composition` goes from cheapest to costliest, and the first three need no new feature or window style.
3. **GPU-completion probe in production builds?** Recommended: only behind the experiment switch (it stalls the pipeline by design).
