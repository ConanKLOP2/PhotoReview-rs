## Semantics (C# is the spec; items that tests pin)
1. **Press/release** exactly as the grounding above. `pressed` is an `OverlayButton`; `is_pressed` is written on the element (`toolbar.buttons_mut()[i]` or `status.view_list_mut()`). A press on a disabled button or a panel sets `pointer_down` and swallows, but leaves `pressed = None`. `pointer_up` clears `is_pressed` BEFORE `dispatch_click` (a command that re-enters the overlay sees a released button). The click requires the topmost hit at the release point to still be that same button (`hit_button(point) == Some(button)`).
2. **`dispatch_click(button)`**: `OpenFolder` -> `commands.open_folder()`, `Settings` -> `show_settings()`, `Fit` -> `fit()`, `Tools` -> `show_tools_menu()`, `ViewList` -> `show_skipped_files()`. The command object is in its own `RefCell`; it is borrowed with `try_borrow_mut` and NO state borrow is held. A re-entrant click (a command that causes another click through nested messages) fails the `try_borrow_mut` and is dropped; the Tools menu has the same rule through `tools_open`. `ButtonElement::click(&self, on_clicked: &mut dyn FnMut(&str)) -> bool` (W8-15c) is the gate: the overlay passes a sink that records the id; the button gives `false` and no command when it is disabled, hidden or at opacity 0 (C# `Click()` gate: `IsEnabled && IsVisible && Opacity > 0`). Use `click` for the keyboard path as well.
3. **`key_down`** (C# 393-425), order: disposed -> `false`; `note_info_activity()`; `VK_TAB`: when auto-repeat return `toolbar.has_keyboard_focus()` WITHOUT moving, else `toolbar.move_focus(!shift)` (result ignored: the focus may leave the toolbar), `apply_toolbar_visibility()`, `request_render()`, return `true` (also when the focus left: Tab is always swallowed unless repeating, a C# quirk the test `Keyboard_TabWalksTheButtonsAndLeavesAfterTheLast` pins by ignoring the return of the last Tab); `VK_SPACE`/`VK_RETURN` with `toolbar.focused_button()` `Some`: click it unless auto-repeat, return `true` (auto-repeat also returns `true`); anything else `false`.
4. **`wheel`**: `note_activity()` (even when disposed it is a no-op) then `hit_test(point)`. True means the wheel does NOT reach the image (WPF: panels above the ScrollViewer take it).
5. **`show_tools_menu`**, in order (C# 518-572): return if `tools_open` or no menu host. `bar = tools button box`; `origin = client_origin_on_screen_dip()` or `(0,0)`; anchor `(origin.x + bar.x, origin.y + bar.y + bar.height)` in SCREEN DIP; `tools_open = true`; `Tools.is_checked = true`; `apply_toolbar_visibility()` (the toolbar is held visible and its timer stopped); `menus.show(&tools_menu::build(has_images), anchor)` with no borrow held (modal: the window keeps pumping messages, including `WM_MOUSEMOVE` to the overlay); then in every case (C# `finally`): `tools_open = false`, `is_checked = false`, `apply_toolbar_visibility()` (this restarts the hide countdown from now: the test expects the toolbar to hide 1500 ms AFTER the menu closed), `request_render()`. `Err(e)` -> `on_menu_failed(&*e)` or else `on_command_failed("Tools menu", &e.to_string())`, treated as nothing chosen. `Ok(Some(id))` and not disposed -> `tools_menu::execute(Some(&id), &mut commands, has_images)`.
6. **Command failures (Q1, D-W8B4O-9)**: the C# `RunGuarded`/`ObserveFailure` (a command that throws or whose `Task` faults is reported with its menu name; `OperationCanceledException` is not a failure) have no counterpart because `OverlayCommands` is synchronous and returns `()`. A failure inside a command is reported by the command's own implementation (15j: `ViewModelOverlayCommands` -> `OverlayViewModel::report_action_failed`). The three C# tests (`FailedAsyncCommand_...`, `CancelledCommand_...`, `SynchronouslyThrowingCommand_...`) and `ToolsMenu_WhenACommandThrowsSynchronously_...` are re-targeted: the first three become 15j tests of `ViewModelOverlayCommands` with a failing fake view model, the fourth becomes `show_tools_menu` calling `execute` and propagating nothing (`on_command_failed` is not called by the overlay). Rows go to the PARITY `Different` list only if the lead rejects Q1.
7. **`render`**: see paint.rs docs. `render` takes `&self` and short-borrows: `arrange` (mut), `host.render(dc)` (shared), release, `sync_tooltips()`. `dc` is `&mut dyn DrawContext`; opacity push/pop balance is the elements' (15a).
8. **`collect_tooltips`**: exactly the C# conditions; the toolbar check uses the toolbar's `is_visible`, `is_hit_test_visible` and `opacity() > 0`; a toolbar that is fading out but already click-through gives NO tooltips although its opacity is still 1 (test 482). Texts come from `ButtonElement::tool_tip` (localized by 15e), the EXIF text from `model.exif_text`, the badge from `CapturePairBadge::tool_tip()`. Ids: the button element ids, `ExifInfoText`, `CapturePairBadge`.
9. **Drawing order and z order versus the image**: `render` is called by 15j after the image layer inside the same `BeginDraw`/`EndDraw`. Inside the overlay the roots draw `InfoOverlayHost` then `ToolbarPanel` (test: the zoom text index is smaller than the Fit text index in the recorded draw list).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (mouse capture, with 15f): `pointer_down` returning `true` with `is_pointer_down()` true is what makes the handler capture; `pointer_cancel` is called on capture theft and is NOT guarded by `disposed`; `pointer_up` after a cancel returns `false` (no press).
- T2 (modal menu re-entrancy): `show_tools_menu` holds no `RefCell` borrow during `menus.show`; the 15i test `ToolsMenu_ReentrantClickIsIgnoredWhileOpen` clicks the Tools button from inside the fake `while_open` closure and expects one `show`. A second test sends `pointer_moved` from inside `while_open` and expects no `BorrowMutError`.
- T3 (hit testing with DPI): DIP only; the anchor of the menu is `origin + box`, both in screen DIP (the 15j origin helper divides physical pixels by the window's DPI).
- T4 (fade vs click-through): a toolbar fading out is `is_hit_test_visible == false` from the start, so `pointer_down` over it returns `false` and the image gets the click; `wheel` likewise.
- T5 (tooltip deferral): `render` calls `sync_tooltips` every frame; `OverlayTooltips::sync` is cheap for an unchanged list (15g), so the call is unconditional like C#.
- T6 (order of effects): `is_pressed = false` before the click; `tools_open` restored before `execute`; `request_render` after the state change and before the command.
- T7 (focus leak): `pointer_down` over the image calls `clear_keyboard_focus` (the toolbar focus ring disappears and the hide rule re-evaluates).
- T8 (no `async`): see item 6.
- T9 (identity): compare `OverlayButton` values, not element addresses; `hit_button` uses the id of the deepest hit.

## Open questions (recommended default in bold)
1. **Command failure channel** (D-W8B4O-9): **none in the overlay; the command implementation reports** (it already must, because commands are fire-and-forget on a worker). `ShellOverlayOptions::on_command_failed` stays for the menu. Alternative: change `OverlayCommands` (a W8-15e file) to return `Result<(), CommandError>` and keep `RunGuarded` semantics; rejected: touches a merged contract and the C# cancel rule needs a variant.
2. **`OverlayMenuHost` seam instead of the 14e `IPopupMenuHost` port** (D-W8B4O-6): **seam now, with the exact signature of 14e's `PopupMenuHost` (read from the `wave8/b4-contracts-input` branch: `show(&self, &[MenuItemModel], PointD) -> Result<Option<String>, Box<dyn Error>>`)**; when 14e is on master the lead replaces the trait by `pub use` or adds `impl<T: PopupMenuHost + ?Sized> OverlayMenuHost for T`. No behaviour change.
3. **Modal menu while the overlay is borrowed** is solved by the no-borrow rule, not by a queue; if a native test shows `WM_MOUSEMOVE` really arrives inside `TrackPopupMenu`'s loop for our window, the `while_open` fake already covers it.
4. **Tab on the last button returns `true`** (C# quirk) : **keep**; alternative: return `has_keyboard_focus()`; would change the image's Tab behaviour (it would get the Tab) and needs a `Different` row.
5. **Native draw test needs 12e and 12i merged** (`D2dDrawContext`, `DWriteTextRenderer` are implemented on master): **yes**; the pure tests do not.
