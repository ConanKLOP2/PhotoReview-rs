- Semantics notes:
  1. **Order of yields in `Build`** (exact; the scheduler consumes it front to back):
     a. none at all if `center < 0 || center >= count`;
     b. `dir = direction < 0 ? -1 : 1` (so `direction == 0` is forward); `lead = clamp(lead, 0, count)`;
     c. travel window: `center + dir*offset` for `offset = lead+1 ..= lead+forward`;
     d. skipped burst images: `center + dir*offset` for `offset = 1 ..= lead`;
     e. small window behind: `center - dir*offset` for `offset = 1 ..= backward`;
     f. each of c-e only when the index is in `0..count` (out-of-range indices are SKIPPED, not stopped at: the loops still run to their bound);
     g. `if !full_folder` stop; else far ahead: from `center + dir*(lead+forward+1)` step `dir` while in range; then far behind: from
        `center - dir*(backward+1)` step `-dir` while in range (these two `for` loops DO stop at the first out-of-range index).
  2. **No duplicates in range** for `forward >= 1`, `backward >= 0`: the groups partition the line. Do not add a dedup set; it would hide a port bug.
  3. **`PreloadWindow::DEFAULT` is (32, 8), but C# `default(PreloadWindow)` is (0, 0).** Rust: no `impl Default for PreloadWindow` on purpose (a derived
     Default would be (0,0) and an implemented one would silently differ from C# `default`). `PreloadOptions::default()` is the C# parameterless ctor,
     so it uses `PreloadWindow::DEFAULT`.
  4. **`PreloadOptions` defaults are fallbacks, not the product defaults**: `worker_count = 8` (equals `perf::PRELOAD_WORKER_COUNT` by value only),
     `memory_load_limit = 0.80` (the product `perf::PRELOAD_MEMORY_LOAD_LIMIT` is 0.90: do NOT reference that constant), `reserve_bytes = 2 * 1024^3`,
     `full_folder_threshold_bytes = 16 * 1024^3`. Both byte values are `i64` (they overflow `i32`); write them as `2_i64 * 1024 * 1024 * 1024`.
  5. **`image_count`** is `forward + backward + 1` with no clamp; use `wrapping_add` to mirror unchecked C#. `(500, 500)` gives 1001.
  6. **`from_settings` does not clamp or validate** (the normalizer already ran). `9999/9999` flows through unchanged (golden `settings-unclamped-9999-9999`).
- Traps checklist (docs/MULTI-AGENT-PLAN.md §7): item 3 (numeric conversions / overflow), item 9 (lazy sequences), item 11 (default values). Specific:
  1. **C# `IEnumerable` is lazy; the scheduler pulls from it over time** (`PreloadScheduler.cs:526`, `GetEnumerator()` kept in a field). The stub returns an
     eager `Vec<i32>` (open question 1). Eager is safe for the order itself: it is a pure function of its arguments and a 100k-image folder is 400 KB.
  2. **Unchecked `int` arithmetic.** `center + dir * offset`, `lead + forward`, `lead + forward + 1`, `center - dir * (backward + 1)` can wrap for absurd
     windows (`forward` near `i32::MAX`). Use `wrapping_*` everywhere so a debug build does not panic where C# wraps. With a wrapped `lead + forward`
     (negative) the first loop yields nothing, as in C#. A window with `forward` so large that the loop counter itself would pass `i32::MAX`
     (`offset <= lead + forward` always true) is an infinite loop in C#; unreachable because `SettingsNormalizer` clamps to 500. Do NOT test it.
  3. **Negative `backward` is a real quirk, not a guard case.** With `backward = -1` and `full_folder`, the far-behind loop starts at
     `center - dir*0 = center`, so the CENTER is yielded (goldens `QUIRK-backward-minus-1-*`). With `forward = -3` the far-ahead loop starts at
     `center + dir*(lead-2)`, possibly at or before the center. Unreachable from the product (normalizer: forward in [1,500], backward in [0,500]) but the
     function is public and the goldens pin it; keep the formulas literal. Do NOT add `assert!`/`max(0)`.
  4. **`Math.Clamp(lead, 0, count)` throws when `count < 0`** (min > max). Unreachable: `center` in `0..count` already implies `count >= 1`, and the
     range check runs first. In Rust use `lead.clamp(0, count)` AFTER the early return (a Rust `clamp` panics on `min > max` as well).
  5. **`direction < 0` test, not `== -1`.** Any negative number is backward, any non-negative (0 included) is forward (goldens `direction-*`).
  6. **Loop order matters across groups, not only membership**: the property test checks group order and nearest-first inside each group; the golden
     pins the exact sequence for 37 cases. Compare the whole `Vec<i32>`.
  7. **`PreloadWindow` is a value with structural equality and hashing** (record struct): derive `PartialEq, Eq, Hash`; it is used as a cache/state key by
     the scheduler (`seenShape`-style change detection compares windows).

## Open questions
1. **Eager `Vec<i32>` vs a lazy iterator.** Recommended: `Vec<i32>` (stub). A lazy `impl Iterator` is possible, but a `todo!()` stub cannot return one in
   edition 2021 and the order is cheap. If the scheduler unit wants laziness for 100k+ folders it can wrap the vector or switch to a small struct iterator
   with the same yield order (the golden stays valid).
2. **Free function name** `build_preload_order` (C# `PreloadOrderService.Build`). A module-level `build` is also fine; the stub name wins unless the
   scheduler unit's stub already fixed another (D28).
3. **Negative-window quirks** (trap 3): kept literal for parity. If the lead prefers to forbid them, validate in `PreloadWindow::new` (Rust-only) with a
   `PROPOSED-DECISIONS.md` entry first; that would diverge from the golden cases named `QUIRK-*`, which would then be removed, not changed.
4. **Settings lookup path**: `from_settings` takes `&AppSettings` from `pr-core`. If W4 decides `pr-imaging` must not see the whole settings struct, the
   scheduler unit can instead call `PreloadWindow::new(settings.preload_forward_count, settings.preload_backward_count)` (identical result) and this
   method is dropped; the golden `settings_cases` then move to the App wave.
