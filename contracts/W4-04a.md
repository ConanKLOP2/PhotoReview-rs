- Semantics notes:
  1. **`ExifSummary::create`** (never throws): `date_taken = parse_date(raw)`, `make/model/lens = clean_text(raw)`,
     `iso` kept only when `1..=10_000_000` (then narrowed to `i32`), each rational kept only when BOTH parts are > 0. If every
     field ends up `None` the result is `None`. `Some("")` or whitespace text is `None` after cleaning. Note the asymmetry:
     a summary built with a struct literal is NOT sanitised and `is_empty` is false for `make: Some("")`.
  2. **`clean_text`**, in this order: `None`/empty -> `None`; cut at the first NUL (`"\0abc"` -> `None`); every control character
     (Unicode category Cc: U+0000..U+001F, U+007F..U+009F; Rust `char::is_control`) becomes a space; stop after
     `MAX_TEXT_LENGTH` = 64 **UTF-16 code units** (C# counts `char`s: an emoji costs 2, a combining mark costs 1; do NOT use
     `chars().count()` or bytes); trim whitespace (both ends; C# `char.IsWhiteSpace`, equal to Rust `str::trim` for the
     characters that can survive the control replacement: NBSP, U+2028/2029 and U+3000 ARE trimmed, U+200B and U+FEFF are NOT);
     a character that does not fit the cap is dropped whole (C# drops the half surrogate pair, then `TrimEnd`s again: the same
     result as truncating first and trimming once); empty -> `None`. Lone surrogates cannot occur in a Rust `&str`, so the C#
     "cut in the middle of a pair" case is exactly "the next char is a non-BMP char that would exceed 64 units".
  3. **`parse_date`**: `clean_text` first (so NUL padding, tabs and edge spaces are tolerated), then `TryParseExact`,
     invariant culture, `DateTimeStyles.None`, against exactly these formats in order: `yyyy:MM:dd HH:mm:ss`,
     `yyyy:MM:dd HH:mm`, `yyyy-MM-dd HH:mm:ss`, `yyyy:MM:dd`. Write a strict hand parser, no `chrono`: year exactly 4 ASCII digits
     in `0001..=9999`, month/day/hour/minute/second exactly 2 ASCII digits, real calendar days (leap years), hour 0..=23,
     minute and second 0..=59, a single literal space between date and time, no trailing text, no zone, no fraction, no
     AM/PM. `0000:00:00 ...` and `dd` out of range give `None`. Dash dates need the full `HH:mm:ss` (`2024-05-01` alone is
     `None`). Whether .NET accepts non-ASCII digits (fullwidth, Arabic-Indic) is pinned by golden cases
     `fullwidth-digits` and `arabic-indic-digits-date-only`; follow the golden. The result is a camera wall-clock time
     with `DateTimeKind.Unspecified`: store its ticks in `DateTimeUtc` (`from_ticks`), never apply a zone. Days-from-civil
     arithmetic is private to this file (`DateTimeUtc` exposes only ticks; see Open questions).
  4. **Codec layout (persisted, little-endian, byte-identical to C#).** `[0]` = `FORMAT_VERSION` (1), `[1]` = presence mask,
     then only present fields in mask-bit order: `DATE`(1) = i64 ticks (8 bytes); `MAKE`(2), `MODEL`(4), `LENS`(8) = 1 length
     byte + UTF-8 bytes; `ISO`(16) = i32 (4 bytes); `FOCAL`(32), `F_NUMBER`(64), `EXPOSURE`(128) = u32 numerator + u32
     denominator (8 bytes). `encode(None)` and `encode(Some(summary))` with `is_empty()` give `[]`.
  5. **Encode quirks.** The mask byte is patched in after the fields are written. A text is written whenever it is `Some`
     (including `Some("")` -> bit set, length byte 0). UTF-8 longer than 255 bytes is cut at exactly 255 BYTES, possibly in the
     middle of a sequence (unreachable for a `create`d summary: 64 UTF-16 units are at most 192 UTF-8 bytes). `iso` and rationals
     are written raw, with no validation (negative ISO, `0/0` are written and dropped again by `decode`). The date is
     written as its ticks regardless of kind. Pre-size the buffer (96).
  6. **Decode** (never panics, no allocation beyond the output): length < 2 or `data[0] != 1` -> `None`. Mask bits are read
     in order; any field that does not fit in the remaining bytes -> `None`; after the last field `pos` must equal
     `data.len()` (one trailing byte is malformed). Date ticks outside `0..=DateTime.MaxValue.Ticks` -> `None` (the exact
     edges `0` and `3155378975999999999` are accepted). Texts are decoded as UTF-8 **lossy** (`String::from_utf8_lossy`: one
     U+FFFD per maximal invalid subsequence, the same as .NET Core 3.0+ `Encoding.UTF8.GetString`; pinned by golden
     `make-invalid-utf8` and the 255-byte cut cases). Then everything except the date is re-sanitised through
     `ExifSummary::create(None, make, model, lens, iso, focal, f_number, exposure)`, so a zero-length text, `iso <= 0`,
     `iso > 10_000_000` and a rational with a 0 part are dropped silently. The date is attached afterwards WITHOUT
     `parse_date` (it is a number, not text): if `create` returned `None` but a date was present the result is
     `ExifSummary { date_taken, ..Default::default() }`; if neither survives the result is `None` (e.g. `[1, 2, 0]`).
  7. **`ExifRational::value`**: `numerator as f64 / denominator as f64`, `0.0` when the denominator is 0 (so `0/0` and `5/0` give 0).
  8. **Equality** is field-wise on ticks (C# record equality ignores `DateTimeKind`); derive `PartialEq`, no custom impl.
  9. **Performance.** Decode runs on every preview-cache hit (HotPath). Parse straight from the slice with a small cursor,
     return early, no `Vec` of intermediate fields, no regex, no `format!`.

## Golden package
- `oracle/W4-04a.cs`: commands `exif-summary-create`, `exif-summary-text`, `exif-summary-date`, `exif-summary-encode`,
  `exif-summary-decode`. Needs `W2-00.cs` (class `W2Util`) and a reference to the baseline `PhotoReview.Imaging.dll` in
  `tools/oracle-cs/OracleCs.csproj` (wiring step); the internal members are reached by reflection (a custom delegate type
  handles the `ReadOnlySpan<byte>` parameter). Dispatch lines are in the file header. Not run in this draft.
- `golden-inputs/{exif-summary-create,exif-summary-text,exif-summary-date,exif-summary-encode,exif-summary-decode}.json`,
  outputs go to `golden-reference/` and `tests/golden/`. Long texts use `{key}_repeat` (`{"text","count"}`) plus optional
  case-level `prefix`/`suffix`; the Rust replay must expand them the same way. Rationals are `[numerator, denominator]`.
- Output shape (per summary): `{is_null}` or `{is_null:false, date_ticks, date_text, make, model, lens, iso, focal, f_number,
  exposure, is_empty, encoded_hex}`; `encoded_hex` is upper-case. The Rust replay checks the fields AND `encoded_hex`
  (encode determinism).
- Case design: date formats (4 accepted, near-misses, calendar edges, leap/century rules, digit width, zone/fraction/AM-PM
  suffixes, NUL/tab/NBSP inside, non-ASCII digits); text cleaning (NUL, Cc controls incl. DEL and C1, Unicode whitespace that is
  and is not trimmed, 63/64/65-unit caps, surrogate pair on the cap, combining marks, `\0` after the cap); `create` (every ISO
  boundary incl. i32 and i64 edges, each rational with a zero part, all-invalid -> null, dirty texts); `encode` of unsanitised
  summaries (empty-string text, 255-byte cut for 2-, 3-byte and ASCII text, raw ISO and rationals); `decode` of hand-built
  blocks (every malformation class, date edges, invalid UTF-8, trailing byte, wrong version, mask-order).
- Not representable in JSON goldens: lone surrogates (serde_json cannot hold them). The C# behaviour for them
  (`CleanText` keeps them, `Encode` would write U+FFFD for each) is unreachable from Rust input and is NOT ported.

## Open questions
- `DateTaken` type: this stub reuses `pr_core::time::DateTimeUtc` as a tick container for a zone-less wall-clock time (same tick
  range 0..=DateTime.MaxValue, same equality). The name says UTC but nothing here converts zones. Alternative: a dedicated
  `ExifDateTime(i64)` newtype. Lead decides; the codec bytes and goldens are the same either way.
- Civil-date helpers: `time.rs` keeps days-from-civil private. Either this unit carries a small private copy (the stub assumes
  so), or the lead exposes `DateTimeUtc::from_civil(y, m, d, h, mi, s)` in `pr-core`. Either way W4-04b's `ExifQueryInterpreter`
  does not parse dates itself (it calls `create`).
- `RawExifTags` replaces the eight positional arguments of C# `Create` (clippy `too_many_arguments`). If the lead prefers eight
  parameters, add `#[allow(clippy::too_many_arguments)]`; nothing else changes.
- `iso` is `Option<i32>` in the summary but `create` takes `Option<i64>` (C# `long?`): WIC/parser callers hold wider integers.
- Non-ASCII digits in dates (see semantics 3): if the oracle shows .NET rejects them (expected, ASCII only), the porter writes
  an ASCII-only parser and the two golden cases pin it.
