## Semantics notes (C# is the spec)
1. **Shared state** (an `Arc<Shared>` between the object and the thread): `interval_ms: i32` (clamped), `clock: TickClock`, `until_ticks: AtomicI64` (initial 0), `ticks: AtomicI64`, `idle_waits: AtomicI64`, `stop: AtomicBool`, `failed: AtomicBool`, `blocked: AtomicBool`,
   the wake event `Mutex<bool> + Condvar` (an auto-reset event: `set` stores `true` and notifies one; `wait` loops `while !signaled { wait }` then stores `false`), and a `done` flag `Mutex<bool> + Condvar` that the thread sets as its LAST act. The `gate` `Mutex` holds the `JoinHandle` option
   (`has_thread` = `is_some()`); all atomics use `SeqCst` (the C# used `Volatile`/`Interlocked`; simplicity over speed, this is a 20 ms loop).
2. **`activate(until)`**: if `stop || failed` return (lock-free fast path). Lock the gate; re-check `stop`; `until_ticks.fetch_max(until)` (never shortens; `activate(1)` after `activate(1500)` changes nothing); if no thread yet, spawn it with `thread::Builder::new().name(THREAD_NAME)`; a spawn error sets
   `failed` and returns (never panics, never propagates); unlock; then `wake.set()` (outside the lock, like C#). Every call wakes the thread exactly once.
3. **Thread body** (`run`), wrapped in `catch_unwind` so that a panic of the work behaves like the C# `catch (Exception)`: sets `failed`; the order is C#'s:
   a. `open_work()`: `Ok(None)` or `Err(_)` or a panic -> `failed = true`, finish (no timer, no work). b. `WaitableTimer::new()`; an `Err` leaves `timer = None` (sleeps with `thread::sleep`). c. `set_thread_priority_below_normal()` when requested (one `unsafe` block, see Safety).
   d. `while !stop { idle_waits += 1; blocked = true (under the wake mutex); wake.wait(); blocked = false; while !stop && clock() < until_ticks.load() { if work.touch().is_err() (or panics) { failed = true; break 'outer }; ticks += 1; sleep_interval(&timer) } }`.
   e. Finally (always): drop the timer, drop the work (on this thread; a panic in `drop` is swallowed), then set `done` and notify. `ticks` is incremented only AFTER a successful touch (a failing touch leaves `ticks == 0`).
4. **`sleep_interval(timer)`**: `Some(t)` and `t.set_relative_ms(interval_ms)` is `Ok` -> `t.wait(interval_ms as u32 + 100, false)` and return; otherwise `thread::sleep(Duration::from_millis(interval_ms as u64))`. The wait is not interruptible by `stop`/`dispose` (at most `interval + 100` ms, at most 1.1 s): hence the 3 s join bound.
5. **`dispose()`**: lock the gate; if `stop` already, return; `stop = true`; take the `JoinHandle`; unlock; `wake.set()`; if a handle exists, wait for `done` for at most `DISPOSE_JOIN_TIMEOUT_MS` (Condvar `wait_timeout`), then `join()` ONLY if `done` was reached (a thread that
   missed the bound stays detached; never block forever). Because `done` is set after the work is dropped, a return from `dispose` means the work object has been dropped on its own thread (test `dispose_stops_the_thread_and_disposes_the_device`). `Drop` calls `dispose`.
6. **`is_disabled()`** = `failed || stop`; **`has_thread()`** = a thread was spawned (stays true after the thread ended); **`is_blocked()`** = `has_thread && blocked`. `blocked` is set while holding the wake mutex immediately before `Condvar::wait` and cleared when `wait` returns, so
   `idle_waits >= n && is_blocked()` is a coherent "went to sleep on the event for the n-th time" observation. `wait_blocked(n, timeout)` (NEW, tests/diagnostics) waits for exactly that condition on a second `Condvar` (the thread notifies it each time it sets `blocked`), replacing the C# polling (D-W8B3S-9) (spurious Condvar wakeups loop inside `wait` and do NOT increment `idle_waits`). `is_blocked` is narrower than C# `WaitSleepJoin` (it is false during the interval sleep); the tests only use it on the event.
7. **`monotonic_ticks()`** is nanoseconds since a process-wide `Instant` stored in a `OnceLock` (never negative). W8-16d computes `monotonic_ticks() + ticks_from_ms(window_ms)`. `ticks_from_ms(ms) = ms.saturating_mul(1_000_000)` (i.e. `TICKS_PER_SECOND / 1000` per ms). `activate(i64::MAX)` must work (an "open forever" window in the tests).
8. **`clamp_interval_ms(v)`** = `v.clamp(1, 1000)`: `-5` and `0` -> 1, `60_000` -> 1000. The C# comment: the clamp keeps a bad option from becoming a busy loop (1 ms floor) or a never-touching thread (1 s ceiling).
9. **`open_hardware_work(create)`**: `create()?` (a failing device creation is `Err`, which the thread treats as "failed"); `device.is_warp()` -> drop the device and return `Ok(None)`; else a private `HardwareWork` implementing `KeepAliveWork` over `device.touch_gpu()`. The production caller passes
   `|| DeviceResources::create_offscreen(16, 16, 1.0, false).map(|d| Box::new(d) as Box<dyn KeepAliveDevice>)` (W8-12b/12c). The device is created on the keep-warm thread because `open_work` runs there.
10. **Why a separate thread with its own device** (so nobody "optimizes" it): the keep-warm device must NOT be the window's device (the stall is on first submission to the GPU; any device on the same adapter wakes it, and a separate thread means the UI thread never waits). Do not share the `ID2D1Factory` (single-threaded) and do not
    move the work to another thread after creation.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (idle waits are per loop, not per wake-up): `idle_waits` increments once per outer iteration BEFORE blocking, so the first `activate` gives 1 (the event is already set; the wait returns at once), the first deadline pass gives 2. `AfterTheDeadline_TheThreadSleepsInsteadOfSpinning` asserts exactly 2 then exactly 3
  after a stale `activate(1500)` with the clock at 2000 (one wake-up, no touch). A `Condvar` loop that counts spurious wake-ups, or a poll with a timeout, breaks it.
- T2 (never shortens): `fetch_max`, not `store`.
- T3 (lost wake-up): the event must be a latch (`Mutex<bool>`), not a bare `Condvar::notify_one`; an `activate` that lands before the thread reaches its wait would be lost. `stop` must also set the latch, or `dispose` blocks until the join timeout.
- T4 (ordering of dispose): `stop = true` BEFORE `wake.set()`; the thread re-checks `stop` after waking, before touching.
- T5 (work lifetime): `open_work` runs on the thread, `touch` runs on the thread, the drop runs on the thread; `dispose` must wait for the drop (via `done`), or `touch_failure_disables_and_drops_the_device_on_the_background_thread` and the leak tests become racy.
- T6 (failures never escape): a panic in `open_work`, `touch` or the work's `Drop` must not unwind out of the thread; none of them may panic the process. `catch_unwind(AssertUnwindSafe(..))` around the body and around the final drop.
- T7 (timer is per thread): `WaitableTimer` is `!Send` (D-W8B3G-4); create it inside `run`. Do not create it in `new`.
- T8 (`i64` due time): the timer call is `set_relative_ms(interval_ms as i64)` (11f converts with `* 10_000` in `i64`); passing an `i32` product overflows at about 214 s, not an issue at <= 1000 ms but keep the type.
- T9 (clock injection): the loop condition is `clock() < until_ticks` (strict `<`): at equality the window is closed.
- T10 (no environment here): see C# source. The three variable names are constants of W8-16d.

## Safety rules (every `unsafe` block gets a `// SAFETY:` comment; the lint `undocumented_unsafe_blocks` is on)
- Exactly one `unsafe` block, in a private `fn lower_current_thread_priority()`: `SetThreadPriority(GetCurrentThread(), THREAD_PRIORITY_BELOW_NORMAL)` (both are `unsafe fn` in windows 0.62.2). SAFETY: `GetCurrentThread` returns a pseudo-handle that needs no closing and is valid only on the calling thread, which is where it
  is used; the call has no pointer arguments. A failure is ignored (priority is a courtesy).
- Thread affinity: `GpuKeepAlive` is `Send + Sync` by its `Arc<Shared>` + `Mutex`es (callable from the UI thread); `KeepAliveWork` objects and the `WaitableTimer` live only on the keep-warm thread. Nothing here touches a window or the UI thread.
- Locking: the gate and the wake mutex are never held while calling `open_work`, `touch`, the clock or `join`; the clock is a user closure and may block.
- The keep-warm thread: one per `GpuKeepAlive`, started lazily, named `"GpuKeepAlive"`, background (never joined at process exit), stopped by `dispose`.

## Error mapping
Nothing is propagated to the caller: `GfxError` from `open_work`/`touch` and panics all end in `failed = true` (`is_disabled()`). `GfxError` is logged by the thread through `pr_perf`/the app log ONLY if W8-16d passes a logger later; this unit has no log dependency
(C# swallowed silently). `activate` and `dispose` return `()`.

- **D-W8B3S-8 Ticks are nanoseconds of a monotonic clock, not `QueryPerformanceCounter` units.** The unit is private to `monotonic_ticks`/`ticks_from_ms`/`TICKS_PER_SECOND`; no consumer may assume `Stopwatch.Frequency`.
- **D-W8B3S-9 `wait_blocked` is added** (no C# twin): the one test hook, so the tests observe 'parked on the event' without polling.
- **D-W8B3S-4** (shared): `KeepAliveDevice` is a placeholder for W8-12b/12c `DeviceResources`.

## Open questions
1. **Shape of 12b/12c `DeviceResources`** (concurrent contract): assumed `create_offscreen(w, h, dpi_scale, prefer_warp)`, `is_warp()`, `touch_gpu()` and `Drop`. If `touch_gpu` returns the HRESULT instead of `Result`, wrap it with `com::check`. Recommended: keep the `KeepAliveDevice` trait so the production work stays testable with a fake device.
2. **Priority API.** Recommended (taken): `SetThreadPriority(BELOW_NORMAL)` on the keep-warm thread itself. Alternative: `std::thread::Builder` has no priority; `windows-threading` crate (already in the lockfile as a transitive dependency); rejected, a new direct dependency for one call.
3. **Logging a disabled keep-alive.** C# is silent. Recommended: silent here; W8-16d logs `is_disabled()` once through the app log after an `activate`. Alternative: a `Fn(&str)` logger parameter; rejected for scope.
4. **`activate` cost on the UI thread.** `Mutex` lock + one latch set per call; W8-16d calls it per interaction (key repeat 30 Hz). Recommended: accept (microseconds). Alternative: skip the lock when the thread exists and `until` did not grow (`fetch_max` only, then `set`); a possible micro-optimisation for the porter if the lock shows in a profile; the tests cover both paths.
5. **Is keep-warm still wanted?** The R0001 stall (300-510 ms in `EndDraw`) looks like the same pathology as WP21-STALL (0.47 s, Intel UHD 630, first submission after idle) and the Rust spike has NO keep-warm. Recommended: the attended re-measure for W8-12j runs with this unit merged and with `PHOTOREVIEW_RS_GPU_KEEPWARM=0` for contrast.
