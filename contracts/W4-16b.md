- Semantics notes:
  1. **Allocation.** C# `NativeMemory.AlignedAlloc(byteCount, 64)`. Rust: `std::alloc::alloc_zeroed(Layout::from_size_align(n, 64))`, `n = byte_count as
     usize`. Order of checks is the C# order: `byte_count <= 0` => `InvalidSize` (C# `ArgumentOutOfRangeException`); `byte_count as u64 > usize::MAX as
     u64` => `CannotAddress` (C# `InsufficientMemoryException`, only reachable on a 32-bit build; keep the branch, it is a plain comparison); then the
     allocation: `Layout` error or null pointer => `OutOfMemory` (C# `OutOfMemoryException`). NEVER call `handle_alloc_error` (it aborts the process):
     the C# contract is a catchable failure and INV-12 wants the app to keep running. Golden `huge-refused-*` pins both refusal shapes
     (1 << 62 asks the allocator; `i64::MAX` cannot form a `Layout`: both are `OutOfMemory`, as `OutOfMemoryException` in C#).
  2. **Zeroed, not uninitialised.** C# documents the contents as uninitialised ("no zeroing cost"). Rust must not hand out `&[u8]` over
     uninitialised memory (UB), and `alloc_zeroed` is `calloc`-like: for blocks of image size the OS supplies zero pages lazily, so the cost is
     near zero. Decoders overwrite everything anyway. Callers must still not RELY on zero (W4-16a documents it as unspecified). See Open
     question 1 for the fully safe alternative.
  3. **Exactly-once free.** The pointer lives in an `AtomicPtr<u8>`; the release path does `ptr.swap(null, AcqRel)` and frees only a non-null result,
     then `LIVE_COUNT.fetch_sub(1)`. `dispose(&self)` and `Drop` both call it, so double `dispose`, `dispose` then drop, and two threads racing all
     free once and decrement once. The `closed` flag is set (`Release`) by the first `dispose` also for the unallocated block (C# `IsClosed` is true
     after `Dispose` of any `SafeHandle`). The live count is incremented AFTER the pointer is stored (no failure path between), as C#.
  4. **Free uses the allocation's own `Layout`.** `dealloc(ptr, Layout::from_size_align_unchecked(byte_count as usize, 64))` is only sound with the
     SAME size and align: `byte_count` is immutable after construction, store nothing else. Never free a block through any other API.
  5. **Live count.** `LIVE_COUNT: AtomicI64`, `Ordering::SeqCst` (test visibility is worth more than the nanoseconds; it is not hot). It counts
     successful `allocate` calls minus released blocks; `unallocated()` and failed allocations never touch it. It is process-wide: tests that read
     deltas must not run next to other allocating tests (trap 5).
  6. **`GC.AddMemoryPressure` / `RemoveMemoryPressure`.** No Rust twin and nothing replaces it: memory is freed deterministically at drop. Not
     ported, not an accepted behavior difference (it only tuned the .NET GC).
  7. **`address()` / `as_mut_ptr()`.** `DangerousGetHandle` equivalents: 0/null for an unallocated or released block. `as_mut_ptr(&self)` takes
     `&self` on purpose (decoders write through it; W4-16a wraps it in a type that hands out `&mut [u8]` rows under its own `&mut self` or
     unsafe contract). This unit never creates a slice over the block, so it has no aliasing obligation beyond `Send + Sync` being automatic
     (`AtomicPtr`, `AtomicBool`, `i64` are all `Send + Sync`: do NOT add `unsafe impl Send/Sync`).
  8. **`PixelBufferImageCodec`.** `image_from_pixels(pixels)`: `pixels.is_disposed()` => `Err(DecodeError::Disposed { message })` with the .NET text
     `"Cannot access a disposed object.\r\nObject name: 'PhotoReview.Imaging.Pixels.PixelBuffer'."`; else `Ok(Arc::new(pixels) as PlatformImage)`.
     No copy, no dispose (ownership moves into the Arc). `to_pixels(&platform_image)`: `(**platform_image).downcast_ref::<PixelBuffer>()`;
     `None` => `Err(DecodeError::InvalidArgument { message })` with `"Expected a PixelBuffer, got a foreign platform image."` (C# prints the
     runtime type name; `dyn Any` has none: not asserted by any test, only the error KIND is part of the contract); `Some(b)` with
     `b.is_disposed()` => `Err(Disposed)`; else `Ok(PixelLease::borrowed(b))`. The returned lease borrows from the `&PlatformImage` argument
     (explicit `'a`, see Open question 2).
  9. **`ReadOnlyMemoryStreamFactory`.** C# returns a `MemoryStream` over the SAME array, `writable: false`, position 0, length = count; the
     fallback (`ToArray()` copy for a non-array-backed memory) exists only for memory shapes decoders do not produce. Rust: the bytes are always
     `Arc<[u8]>` (`SourceBytes`, W4-01b) or `&[u8]`, so there is exactly ONE shape and it never copies. `create(&SourceBytes)` =
     `Cursor::new(Arc::clone(bytes))` (`Arc<[u8]>: AsRef<[u8]>`), `create_from_slice(&[u8])` = `Cursor::new(bytes)`. Read-only is by type
     (no `Write` impl); `CanSeek` is `Seek`; `Position` 0; `Length` = `get_ref().len()`. Decoders needing `Read + Seek` take `impl Read + Seek`.
  10. **Where `unsafe` is allowed.** The plan row says "unsafe with SAFETY" in `pr-imaging`; AGENTS.md says every `unsafe` block has `// SAFETY:`
      and "FFI only". `std::alloc` is not FFI: see Open question 1. Max unsafe surface of this unit: the `alloc_zeroed` call and the `dealloc`
      call, one block each, plus `from_size_align_unchecked` (avoidable: store the `Layout`, 16 bytes, and reuse it; RECOMMENDED so the free
      path has no `_unchecked`).

## Open questions
1. **Is `std::alloc` "unsafe" allowed in `pr-imaging`, and zeroed or not?** AGENTS.md: "Every `unsafe` block has a `// SAFETY:` comment (FFI
   only: ...)"; the task rules say "unsafe only in pr-platform-win"; WAVE-4-PLAN says W4-16b is `pr_imaging::pixel_memory` "unsafe with SAFETY".
   This draft follows the plan row (2 blocks: `alloc_zeroed`, `dealloc`). Fully safe alternative (no `unsafe` in this unit at all): a
   `Vec<Block64>` with `#[repr(align(64))] struct Block64([u8; 64])` and `address = vec.as_ptr() as usize` (alignment guaranteed by the
   type, free by `Drop` of the Vec, `Send + Sync` automatic); it zero-fills (`vec![Block64([0; 64]); n]`: a real memset, slower than
   `calloc` for 20+ MB frames) and the size is rounded up to a multiple of 64 (harmless; `byte_count` keeps the asked size). The cost of
   "no unsafe here" is that `PixelBuffer` (W4-16a) then needs `unsafe` or a `bytemuck`-style cast to view the blocks as `&mut [u8]`, so the
   unsafe just moves. Recommended: keep `std::alloc` here (one place, two blocks), and have the lead record in AGENTS.md that
   "pr-imaging::pixel_memory" is the second allowed unsafe site (P-22 text says pr-platform-win only).
2. **`PlatformImageCodec::to_pixels` signature in the W4-01c stub.** It is written
   `fn to_pixels(&self, platform_image: &PlatformImage) -> Result<PixelLease, DecodeError>`. Two problems found by compiling it: (a) with
   `PixelLease<'a>` (W4-01b's draft has a lifetime) rustc elides the output lifetime to `&self`, not to `platform_image`, so the lease would
   borrow the codec, which is wrong and makes `shared().to_pixels(&img)` leases outlive nothing useful; (b) `-D warnings` rejects the hidden
   lifetime (`mismatched_lifetime_syntaxes`). The correct form, used by this stub, is
   `fn to_pixels<'a>(&self, platform_image: &'a PlatformImage) -> Result<PixelLease<'a>, DecodeError>`. W4-01c must change to it (one line),
   or both 01b and 01c switch to the `Arc<PixelBuffer>` form 01c's Open question 2 recommends (then `PixelLease` has no lifetime and
   `image_from_pixels` returns the `Arc<PixelBuffer>` it already built; the downcast becomes `Arc::downcast::<PixelBuffer>()`, which
   needs `Arc<dyn Any + Send + Sync>` clone: cheap). Lead decides before porting; the codec part of this unit is a 3-line change either way.
3. **`PixelBuffer::dispose` takes `&self`?** The codec checks `is_disposed()` on a buffer that may be shared through `Arc<dyn Any>`;
   a buffer that can only be disposed by consuming it (`drop`) can never be observed disposed through an `Arc`, which would make the
   `Disposed` branches unreachable (and the `ToPixels_DisposedBuffer_*` tests impossible). This unit provides `NativePixelMemory::dispose(&self)`
   (atomic, idempotent) so W4-16a CAN offer `PixelBuffer::dispose(&self)`; if 16a decides otherwise, drop the two `is_disposed` branches and
   their tests and note it in PARITY as an accepted difference (use-after-dispose is then impossible by ownership).
4. **Stream type.** `Cursor<Arc<[u8]>>` vs a named wrapper type implementing `Read + Seek`. Recommended: the plain `Cursor` (std, no new type);
   decoders take `impl Read + Seek`. A named type is only needed if W4-11c wants `len()` without `Seek`: `Cursor::get_ref().len()` covers it.
