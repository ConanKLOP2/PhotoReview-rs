## Design (why the API is not a port of `Task<bool>`)
C# `RunQueuedAsync(Func<Task> work)` returns a `Task<bool>` that completes `true` after the whole async work, and the gate stays held across every `await` of the work. Rust has no futures here (D-W8-2), so:
- the work is `FnOnce(GateTurn)`; the **turn** is the C# "work task is not complete yet". The gate stays held until the turn is finished or dropped. The work moves the turn into its own completion step (the callback that runs on the UI
  thread after the worker finished, after the sink calls `on_catalog_changed`, `present`, ...) and finishes it there. A synchronous work just drops it.
- the C# return `bool` becomes `bool` (`run_exclusive`) or `QueuedOutcome` (`run_queued`). The C# task result (exceptions, cancellation) is the work's own business: it reports through its own channel (a result slot, a sink call).
  The queue is NOT stopped by a failure: the turn ends anyway.
- the C# `TaskCompletionSource turnDone` chain (`_tail`) becomes the `pending` FIFO plus a `running` flag; the C# `RunContinuationsAsynchronously` becomes "post through the `UiScheduler`".
- `WhenReleasedAsync` becomes `when_released(waiter) -> bool`.

## Semantics notes (each from `FileActionGate.cs`)
1. **Held.** `IsHeld = _held != 0 || _queueLength != 0` under the lock. `_queueLength` counts accepted queued actions that have not finished (the running one and the waiting ones). It is incremented under the lock at submission,
   decremented in the `finally` of the action. Therefore a successor that is posted but not started yet still counts: the gate never looks free between two queued actions.
2. **TryEnter / Exit.** `TryEnter` fails when held by either mechanism; `Exit` clears the exclusive flag unconditionally (harmless when free) and wakes the waiter if the gate is now completely free (`!held && queue_length == 0`).
3. **RunExclusive.** `false` and the work not run when `TryEnter` fails. Else the work runs in the caller's thread; the gate is released in a `finally` (here: the turn's end, also on panic).
4. **RunQueued.** Under the lock: exclusive holder gives `Rejected`; else `queue_length += 1` and the action takes its slot (published BEFORE any user code, RV-A01). The user work never runs under the lock.
   Idle gate: the work starts synchronously in the caller (no dispatcher hop, so a confirmation dialog in its prefix shows at once). A submission made while an action is running, including from that action's own synchronous prefix
   (a modal dialog's nested message loop), waits for its turn: FIFO, one at a time (INV-4).
5. **Successor start.** When an action ends, the next waiting one is not started inline on the finishing stack (C# `RunContinuationsAsynchronously` on `turnDone`); it is posted through the scheduler and receives its own `GateTurn`.
6. **Failure isolation.** A failing, panicking or cancelled action ends its own turn and does not stop the actions behind it.
7. **Waiters.** `WhenReleasedAsync` is already complete when `_held == 0 && _queueLength == 0`; otherwise one shared `TaskCompletionSource(RunContinuationsAsynchronously)` completes when the gate is next completely free. All waiters are
   woken, each through the scheduler (not inline). A waiter registered concurrently with the final release is never lost: both happen under the lock (stress test).
8. **Lock rules.** The lock protects only the four fields; no user callback, no scheduler call and no waiter runs while it is held (RV-A01: another thread calling `is_held`/`try_enter`/`when_released` must not block behind a modal in a work prefix).

## Traps checklist (INV-4 caller side; the gate is the last line of defence against two file actions interleaving)
- **T1 INV-4: hold the gate across the WHOLE action.** The turn must be finished only after the action's completion has been applied on the UI thread (catalog/undo/status updated and the next image presented), not when the worker call
  `IFileActionExecutor::execute` returns. Finishing early lets the next queued Move start against a catalog that the previous one has not updated yet (INV-3/INV-5). Document it in the PR; W8-07c and W8-08e own the call sites.
- **T2 Slot before work.** `queue_length` and `running` are updated under the lock before the user work is called. A re-entrant `run_queued` from the work's prefix must see the slot and wait. Reversing the order lets action B run inside A.
- **T3 No work under the lock.** Never call the work, the scheduler or a waiter while holding the mutex (deadlock with a modal prefix and with a waiter that calls `is_held`).
- **T4 Never inline successor.** Posting through the scheduler is the C# guarantee `RunContinuationsAsynchronously`. With `ImmediateUiScheduler` a test would run it inline, so the "does not run inline" test uses a recording scheduler.
- **T5 Release on every path.** `GateTurn::drop` releases when `finish` was not called; a panic inside the work releases the gate (unwinding drops the turn) and the next action still runs. A leaked turn blocks the gate forever: the
  `#[must_use]` message and the doc say so; `std::mem::forget` is not used anywhere.
- **T6 Queue cannot be overtaken by an exclusive holder.** `try_enter` and `run_exclusive` fail while `queue_length != 0` even if the head has not started (posted successor).
- **T7 Exclusive vs queued asymmetry.** `run_queued` rejects only on `held`; `run_exclusive` rejects on `held || queue_length != 0`. Do not unify them.
- **T8 Wakeups.** The waiters are taken under the lock only when `!held && queue_length == 0`, then posted after the lock is released. A waiter taken while the queue is not empty would fire too early (test `when_released_with_queued_actions_waits_for_the_queue_to_drain`).
- **T9 Send/Sync.** `FileActionGate`, `GateTurn` and the queued work are `Send`; finishing a turn from a worker thread is allowed and must give the same state as finishing it on the UI thread (the scheduler hop is internal).
- **T10 No time-based waits** in the implementation or the tests (AGENTS.md): barriers, channels and a recording scheduler only; bound every blocking test wait with `recv_timeout` / `join` on a thread that cannot hang.
- **T11 Name clash.** `pr_core::file_actions::undo::FileActionGate` is a trait; `composition::factories` imports it by that name. Import this type by module path (`file_action_gate::FileActionGate`) or alias one of them.

## Open questions (each with a recommended default; the stub follows the default)
- **O1 Futures were the draft's answer.** The first draft exposed `GateOperation`/`GateReleased: Future`. Recommended (used): the turn handle above. An async runtime is not authorised (D-W8-2, R0003).
- **O2 Scheduler injection.** `new(scheduler)` takes `Arc<dyn UiScheduler>` (from `pr_core::abstractions`), so that "never inline" is observable in tests and the production gate uses the UI dispatcher (W8-13d). Alternative: a bare
  `fn post` closure; rejected for no gain. If W8-13d's `UiDispatcher` is the object handed over, it already is a `UiScheduler` (supertrait).
- **O3 The turn must outlive the action.** The compile-time `#[must_use]` cannot prove the caller keeps the turn long enough (T1). Recommended: the call sites in W8-07c / W8-08e keep the turn inside the completion closure and each
  PR states it; add an integration test in W8-08e where the second Move starts only after the first one's catalog update.
- **O4 `when_released` runs the waiter inline when free.** It matches the C# completed task (an `await` on a completed task continues synchronously). If a caller must never see re-entrancy, it can post the work itself.
- **O5 Counting `queue_length` for posted-but-unstarted successors.** Required by the C# semantics (note 1); the draft's `GateState { exclusive, queue_len }` also had it. Kept.
