- Semantics notes:
  1. **`has_headroom`** (C# `HasHeadroom`): `total <= 0` => `true` (an unknown total never refuses, even for an `i64::MAX` estimate or a huge
     load); else `estimated <= total - max(0, load)`. `<=`: an exact fit passes. With `total > 0` and `max(0, load) >= 0` the subtraction cannot
     overflow `i64`. A load above the total gives a negative budget: a non-negative estimate is refused, a negative estimate that is `<=` the
     budget still passes (golden `has-load-above-total-negative-estimate-*`; this matches C#, do not "fix" it).
  2. **`output_has_headroom`** (C# `OutputHasHeadroom`): `buffer < 0 || buffer > i64::MAX / OUTPUT_PEAK_FACTOR` => `total <= 0` (NOT unconditionally
     false: with an unknown total even the overflow case counts as "fits"); else `has_headroom(buffer * 2, total, load)`. The boundary is
     `i64::MAX / 2 = 4_611_686_018_427_387_903`: that value is evaluated (peak `i64::MAX - 1`), one more takes the overflow branch. Never compute
     `buffer * 2` before the check (debug-build panic) and do not use a `checked_mul` shortcut that changes the `total <= 0` answer.
  3. **The 128 MiB threshold is the caller's job.** `GUARD_THRESHOLD_BYTES` (`128 * 1024 * 1024` = 134 217 728) is only a published constant: the
     C# guard functions do not test it, the decoders do (`if (bufferLength < GuardThresholdBytes) return;` BEFORE reading memory, so a small decode
     never queries the OS; `WicDirectDecoder` additionally requires `>= 0` so a wrapped-negative length is NOT skipped). Do not move that check
     into `has_headroom`.
  4. **The OS seam (`ReadGcMemoryInfo`).** C# `GC.GetGCMemoryInfo()` returns `TotalAvailableMemoryBytes` (physical RAM, or the container / GC hard
     limit) and `MemoryLoadBytes` (memory in use as of the LAST GC, so it can lag). There is no direct Rust equivalent; it becomes the
     `MemoryInfoSource` trait, so decoders take `&dyn MemoryInfoSource` where C# takes `Func<(long,long)> MemoryInfo`. The production
     implementation belongs to `pr-platform-win` (no `unsafe` and no `windows` dependency in `pr-imaging`): `GlobalMemoryStatusEx` =>
     `total_available = ullTotalPhys`, `load = ullTotalPhys - ullAvailPhys` (clamped `>= 0`, both saturated to `i64`). Failure behaviour: see
     Open question 1.
  5. **No caching, no time.** The source is read at every guard check (as C# does); no static state, no `OnceLock`.
  6. **Types.** Everything is `i64` like the C# `long`; callers convert `usize` sizes with saturation (`i64::try_from(n).unwrap_or(i64::MAX)`), as
     `OutputByteLength` does in the WIC unit. This unit adds no conversion helper.

## Open questions
1. **Failure semantics of the production source.** C# `GC.GetGCMemoryInfo` cannot fail, so `HasHeadroom` has no failure mode; a Win32 query can.
   Recommended: the Windows source returns `MemoryInfo { total_available: 0, load: 0 }` on failure (= "unknown": the guard does not block a decode,
   and the decoders keep their own absolute limits), while `WindowsMemoryProbe` (P-10, preload) stays fail-closed separately, as PARITY states.
   Alternative: fail closed with `total_available = 1` (every big decode refused). Lead decides when the pr-platform-win memory unit is cut; this
   unit is unaffected.
2. **Where the production reader lives.** Recommended: a small struct in `pr-platform-win` next to `WindowsMemoryProbe` (one shared
   `GlobalMemoryStatusEx` call) implementing `MemoryInfoSource`. Alternative: derive it from `pr_core::abstractions::MemoryProbe::get_snapshot`
   (`load_percent`, `available_bytes`) inside `pr-imaging`: gives available but not total RAM, so the total would have to be reconstructed
   (`available * 100 / (100 - load_percent)`), which is lossy. Not recommended.
3. **GC lag.** C# `MemoryLoadBytes` is as of the last GC and can be stale; a live `GlobalMemoryStatusEx` is fresher, so Rust is slightly more
   accurate. It can only change a borderline accept/refuse decision, never an on-disk byte; accepted as a documented difference (note it in
   docs/PARITY.md when porting).
