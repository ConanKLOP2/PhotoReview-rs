2. **Laziness and the settings read order (D-W8B6-154, the load-bearing rule).** `SharedServices::build` creates nothing. Each accessor creates its service on the FIRST call (a `OnceLock` cell) and returns the same `Arc` afterwards, from any thread. The C# graph read the settings at these moments and the Rust one must too: (a) at the FIRST resolution of `source_bytes_policy`, `preview_service` (capacity, RAM percent, preload window, `use_source_bytes_cache`, `source_bytes_capacity_bytes`: "applies after a restart", Q-AR6/Q-R19), `decoder_factory` (through the policy); (b) at EVERY call of: the journal durability provider, `is_libraw_needed`, `raw_support_enabled`, `webp_heic_support_enabled`, the preview state closures, the recovery retry's permanent-delete flag, the scheduler factory (a NEW scheduler reads the settings at its creation, i.e. at `create_main_view_model`, RV-I13). The settings are LOADED by W8-17d's worker AFTER the graph is built; therefore (a) must not run before `load`: that is why `previews` and `DialogServices::decoder_factory` are lazy wrappers (S1) and why item B1 exists. Test: `settings_dependent_services_read_the_settings_when_first_resolved_not_at_build`.
3. **Thread safety.** `SharedServices` is `Send + Sync + Clone` (cells in an `Arc`): the early decode resolves the preview service on a worker; preload threads use the policy and the decoders. Everything that holds an `Rc` or a `RefCell` (the view model, the adapters of S1 except `LazyPrewarmPreviews`/`LazyDecoderFactory`) is built on the UI thread by S4. A cell initialiser never calls back into the SAME cell (no cycle exists in the C# graph either).
4. **`IFileSystem`** is `CountingFileSystem(PhysicalFileSystem, metrics)`: every metadata query is counted into `ReviewMetrics` (the diagnostics and benchmark reports read it). `LocalizationService` is built over a PLAIN `PhysicalFileSystem` on purpose (catalog reads must not count in the read budgets).
5. **The decoder factory** keeps the C# shape exactly (`SharedServiceRegistration.cs` 122-142): one `webp_heic` WIC decoder created at resolution, the provider list of 09a, and a decorator that wraps EVERY created decoder (Wpf slot and the rest) in `FormatRoutingDecoder(WebpHeicRoutingDecoder(standard, webp_heic, ..), RawDecoder, raw_support_enabled)`. `inputs.decoder_wrapper` is applied last (the C# test override replaced the registration).
6. **`create_main_view_model`** (doc in `main_view_model.rs`, steps 1 to 7). The transient objects are fresh per call; the singletons are shared. `bind_to_current_thread` happens on the calling thread, which MUST be the UI thread.
7. **Preload entries feed (D-W8B6-155).** The scheduler's `EntriesSnapshotFn`/`SnapshotVersionFn` are `Send + Sync` closures called on the caller's thread when a run starts (the UI thread), but the `ReviewCatalog` is owned by value by `MainViewModel` and is `!Sync`. A `CatalogFeed` (Arc'd cell: version + `Arc<[CatalogEntry]>`) is what the closures read. It is filled by `publish_if_changed(&catalog)` called through the new defaulted trait method `IPreloadController::catalog_changed(&self, &ReviewCatalog)` (amendment A12, below) immediately before each of the four `preload_around` call sites. Without A12 every preload would see an empty list.
8. **Wake and the window.** `MainViewModelHost::wake` is `view_model_wake(inputs.dispatcher.clone())`; it works before the window exists (13h doc), so the view model is built before `MainWindow`.
9. **The Rust-only bridges (S1).** `SharedDialogService`, `SharedClipboard`, `Win32SinkFactoryAdapter` exist because of the orphan rule and because 16i still has its own `SinkCallbacks` struct (D-W8B4V-11): the adapter moves the five closures of `MainViewModelSinkCallbacks` into it field by field. When 16i implements `PresentationSinkFactory` itself the adapter is deleted (amendment A11, finished).
10. **R0002.** `PlatformServices::production` uses `pr_core::identity::INSTANCE_PREFIX` (`PhotoReviewRs`) for the live-operation registry; `paths` comes from `AppPaths::from_environment()` unless overridden; nothing reads `%LOCALAPPDATA%` when `GraphOverrides::paths` is `Some`; the shell integration verb is `PhotoReviewRs`; `PHOTOREVIEW_RS_DATA_ROOT` / `PHOTOREVIEW_RS_ISOLATE_CONFIG` are honoured by `AppPaths` only.

- **B2. ## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (laziness): a service constructor that reads the settings must run at first resolution, not in `build` (Semantics 2). A test that saves a setting between `build` and the first resolution pins it.
- T2 (re-entrancy and cells): a `OnceLock` initialiser may resolve OTHER cells (journal needs the live registry and the settings) but never its own; no lock of the registry is held while user callbacks run (the scheduler factory takes no lock across `PreloadScheduler::with_thresholds`).
- T3 (`Rc` cycles and leaks): `MainViewModelHost` closures capture `Rc`s of host services; none may capture the view model or `ShellServices` strongly (the bridge replaces the C# `vm` capture). `FeedPreloadController` owns the scheduler `Arc`; `dispose` releases the workers.
- T4 (never the real bin or user data in tests): `PlatformServices` of the tests is built from fakes (`FakeRecycleBin` or the 20b `TempFolderRecycleBin`), `AppPaths::new(&TempRoot, ..)`; the production `WindowsRecycleBin`, `WindowsShellIntegration::new()` (the real `Software\Classes`) and `production_explorer_order` are NEVER constructed by a pure test. `WindowsShellIntegration` tests use a private key and delete it.
- T5 (R0002): see Semantics 10; a test pins the registry prefix (`PhotoReviewRs`) through `production`'s construction only in an N test.
- T6 (language switch): `LocalizedTexts`, `LocalizedFormat` and the adapters read the ambient localizer on EVERY call; a value captured once is a bug (the settings dialog switches the language while the app runs).
- T7 (texts): UI text comes from the catalog only; the literals of this unit are log messages, the `RegistryError` / `PlatformError` Display texts and registry paths.
- T8 (panics): no `unwrap`/`expect` on paths that touch files or user data. The two documented panics are in the `Lazy*` adapters (an impossible composition error), caught by the worker's/UI step's `catch_unwind` (R0003).
- T9 (unsafe, S2): `shell_integration.rs`, `culture.rs`, `physical_memory.rs` each wrap the Win32 call in a small safe function with a `// SAFETY:` comment naming the live buffer and its length; a failing API gives the documented neutral answer, never a panic.
- T10 (registry writes): `WindowsShellIntegration::register` never leaves half of the pair; `unregister` deletes only its two verbs (`DeleteSubKeyTree` of exactly those paths).
- T11 (clippy): `#[allow(clippy::arc_with_non_send_sync)]` on the one `Arc::new(SharedDialogService(..))`, with the one-line reason.
