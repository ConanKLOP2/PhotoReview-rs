## Semantics
1. **Entry order.** `cancel.check()` first: an already-cancelled token returns `Err(Canceled)` without locking anything, even on a
   free gate (golden `pre-cancelled-token-on-free-gate`: `slots == 1`). Then under the lock: `!busy` => `busy = true`, return a lease
   (no queue, no stamp, no hook, the preload bound is NOT consulted: golden `max-zero-free-slot-grants-preload`). Otherwise a
   `Preload` with `preload_queue.len() >= max_queued_preloads` (compare as `i64`, `max` may be `0` or negative) => `Err(Busy {
   PRELOAD_QUEUE_BUSY_MESSAGE })` with nothing queued. Otherwise append `Waiter { id: next_waiter_id++, enqueued_at_completion:
   completions }` to the lane of `priority` (`Preload` => preload lane, `Viewer` => viewer lane).
2. **Queued wait (outside the lock).** Run the hook (if any) inside `catch_unwind(AssertUnwindSafe(..))`; then loop on the condvar:
   each iteration checks `cancel.is_canceled()` first, then `pending_grant == Some(id)` (take it: set `None`, return the lease with
   `busy` still true), else `wait_timeout(CANCEL_POLL_INTERVAL)`; spurious wake-ups just loop. On hook `Err`, hook panic or
   cancellation, under the lock: if `pending_grant == Some(id)` => `pending_grant = None` and `release_locked()` (pass the slot on,
   C# "racing grant"); else remove `id` from its lane immediately (so a cancelled preload frees its bound spot: golden
   `cancel-preload-frees-queue-spot`). Then return `WaiterHook { message }` / `Canceled`, or `resume_unwind` the hook panic. The
   completion clock is NOT advanced by any of these paths.
3. **Release** (`FullDecodeLease::release`, `Drop`). `gate.take()`; if it was `Some`, lock, `completions += 1` iff `worked` (read
   now), then `release_locked()`, unlock, `notify_all` if a grant was made. A second `release`/the final `Drop` does nothing
   (`Lease_DisposedTwice_*`, golden `holder-released-twice-*`). `mark_worked` after release is harmless and changes nothing.
4. **`release_locked` (the policy).** `overdue = preload_queue.front() is Some(w) && completions - max(w.enqueued_at_completion,
   last_promotion_completion) >= MAX_PRELOAD_AGE_COMPLETIONS`. If overdue: `last_promotion_completion = completions` and grant the
   preload front. Else grant the viewer front, else the preload front. Nobody => `busy = false`. A grant sets `pending_grant =
   Some(id)` and leaves `busy == true` (ownership moves straight to the waiter; `slots_available()` stays 0, `Lease_DisposedTwice`).
   Only the FRONT preload is ever considered; a non-overdue front is never skipped for a later one. The overdue check runs on EVERY
   release, worked or not (a lease that did no work can still hand the slot to an already-overdue preload).
5. **One promotion per three worked completions.** Moving `last_promotion_completion` makes a second preload stamped at the same
   completion wait three more (golden `two-overdue-preloads-one-promotion-per-three`: `v1 v2 p1 v3 v4 p2`). A preload that queued after
   the last promotion ages from its own stamp (the `max`). Only new test 9 reaches that branch (every C# test and golden waiter is stamped at 0).
6. **Counters.** `slots_available()` = `busy ? 0 : 1`; `queued_viewers()` / `queued_preloads()` = lane lengths (`i32::try_from`,
   saturating at `i32::MAX`). Each takes the lock briefly. A waiter that has been granted but not yet woken is in no lane.
7. **Locking.** One `Mutex<GateState>`; poisoning is recovered with `unwrap_or_else(PoisonError::into_inner)` (R0003). The hook, the
   condvar wait and any user code run WITHOUT the lock held: the mutation-gap test's hook drops the holder lease, which locks the gate
   (calling the hook under the lock would self-deadlock). `notify_all` (not `notify_one`): every waiter shares the condvar and only
   the grantee proceeds; `notify_one` could wake the wrong waiter and delay the grantee by a poll tick.
8. **Cancellation latency.** C# wakes a cancelled waiter at once; Rust notices within `CANCEL_POLL_INTERVAL` (10 ms), because
   `CancelToken` is a flag (contracts/README.md A7: when `CancelToken::wait_timeout` lands, switch to it; behaviour unchanged).
   Grants are never delayed by polling (condvar).
9. **Numbers.** `completions`, `last_promotion_completion`, `enqueued_at_completion`: `i64` like C# `long`; plain `+= 1` and `-` cannot
   overflow (one increment per decode). `max_queued_preloads: i32` unvalidated like C#.

## Traps
- §7 item 3 (numbers: `i64` clock, `i32` counters, compare the bound as `i64` so `-1` behaves like C#), item 9 (each C# exit path is its
  own `GateError` variant: never collapse Busy into Canceled; `Busy` must stay distinguishable because the preload scheduler defers on
  it, INV-12 "busy is not fallbackable"), item 10 (FIFO `VecDeque`, never a `HashMap`/`HashSet` for the lanes).
- Lost grant (deadlock): cancellation or hook failure after `release_locked` picked this waiter MUST pass the slot on. Golden cannot hit
  this race; the mutation-gap twin (hook drops the holder, then fails) pins it deterministically.
- Orphaned waiter: on hook failure the waiter must leave its lane, or `queued_preloads` stays inflated and later preloads are refused.
- Hook panic: without `catch_unwind` the waiter is orphaned AND `busy` may stick; clean up first, then `resume_unwind`.
- Double count: `release` twice must not increment `completions` twice (golden `holder-released-twice-counts-once`: `v1 v2 p`).
- Off-by-one: `>=` (not `>`) in both the bound and the aging check; `max(enqueued, last_promotion)` (not either alone).
- Viewer refusal: a viewer is never `Busy`, whatever the preload lane holds.
- No sleeps in tests (AGENTS.md): every wait is a condvar/channel signal with a 30 s bound; never assert on elapsed time.
- `unsafe`: none in this file (the crate's FFI lives in W5-15 files).

  with worked viewers, two overdue preloads, long viewer run, second preload ageing from the last promotion, mixed worked flags, three preloads, preload holder), lease
  (release twice worked/unworked, sequential enters on a free gate, holder only).

## Open questions
1. Cancellation latency: 10 ms polling now vs C# immediate wake. Recommended: keep polling until A7 (`CancelToken::wait_timeout`)
   lands, then switch inside `wait_for_grant` only. No API change either way.
2. Cancel-vs-grant precedence when both are visible in one wake-up: specified "cancel first, pass the grant on" (matches C#
   `SemaphoreSlim.Wait(token)` entry check); unobservable in tests except that the slot is never lost. Lead may choose "grant first"
   (saves one hand-off) without breaking any C# test.
3. Hook type `Fn(SourceReadPriority) -> Result<(), String>`: the C# seam can throw any exception; only the message survives in Rust
   (`GateError::WaiterHook`). Test-only seam, so recommended as is.
