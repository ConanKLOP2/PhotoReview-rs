- Semantics notes:
  1. **Type mapping.** C# `PixelBuffer` is `pr_imaging::pixels::PixelBuffer` (W4-16a), `DecodeBox` is `pr_imaging::decode_types::DecodeBox`
     (W4-01b), `PixelLayout?` is `Option<PixelLayout>`, `out WicCacheImageInfo` is the second tuple element. `COMException` is a value
     (`Com { hresult }`, signed like .NET `HResult`), `InsufficientMemoryException` is `InsufficientMemory`, `InvalidDataException` is
     `InvalidData(text)`, `ArgumentOutOfRangeException` / `ObjectDisposedException` / `ArgumentException` are typed variants. No panic reaches the
     caller on bad input. `ReadOnlySpan<byte> encoded` is `&[u8]`; `Stream output` is `&mut dyn Write`.
  2. **`resize`** (C# `WicPixelScaler.Resize`). Check order: disposed, `width < 1`, `height < 1`, `byte_count > u32::MAX`; then the plan.
     `width == source.width && height == source.height` is a COPY (new buffer, same layout, row by row; own `id` and address; WIC not
     called). Otherwise: WIC `CreateBitmapFromMemory` of the source (the one copy), Fant scaler, `CopyPixels` straight into the destination which
     is allocated AFTER the scaler is initialised. Enlargement is allowed (no "shrink only" check). The source is never modified or disposed.
     `E_OUTOFMEMORY` (0x8007000E) from any WIC call is `InsufficientMemory`, every other HRESULT is `Com`. Exactly one buffer is allocated.
     (REVIEW note, no behaviour change: in the C# the generated COM stubs throw via `Marshal.ThrowExceptionForHR`, which maps 0x8007000E to
     `OutOfMemoryException`, not `COMException`; so the `catch (COMException) when IsOutOfMemory` may never fire for a real WIC call and the
     caller sees a plain `OutOfMemoryException`. Either way it is not an entry failure and is not fallbackable, the same classification as
     `InsufficientMemory`; W4-11a's `exception_kind_for_hresult` already maps it to `OutOfMemory`. Keep the variant name.)
  3. **`decode`** (C# `WicCacheImageReader.Decode`), exact order:
     (a) empty payload is `InvalidData("Cache entry payload is empty.")` before WIC is touched;
     (b) WIC reads the frame size; `0` or `> i32::MAX` on either axis is `InvalidData("Cache entry payload has invalid dimensions.")`;
     (c) `expected_width > 0` and the frame differs from `(expected_width, expected_height)` in EITHER dimension is
         `InvalidData("Cache entry payload dimensions do not match its header.")`, BEFORE any allocation;
     (d) target layout = `layout` or, by the frame pixel format, `Bgr32` for the 14 opaque GUIDs and `Pbgra32` for every other format;
     (e) size = frame size when the box is unbounded, else `box.fit_stored(w, h, transposed = false)`; `downscaled = w' < w || h' < h`; a
         not-downscaled result has the frame size; the box never upscales;
     (f) `w' * h' * 4 > i32::MAX` is `InvalidData("Cache entry payload is implausibly large.")`, checked on the FINAL size and AFTER the scaler
         was created (so an implausible frame that is shrunk below the limit by the box is accepted). The product is `u64` (trap 3, above).
         `plan_decode` evaluates (b), (c), (e) and (f) up front, before any scaler exists; that differs from C# only when the scaler's own
         `Initialize` fails AND the final size is implausible (C# reports the COM error, the plan reports `InvalidData`). Accepted, document
         it with `// DIVERGENCE:`; if the porter prefers exactness, split `plan_decode` into `plan_frame` (b, c) and `plan_size` (e, f) and
         call `plan_size` after `CreateBitmapScaler`/`Initialize`;
     (g) pipeline: frame -> (Fant scaler if downscaled) -> format converter to `source_format(target_layout)`, `WICBitmapDitherTypeNone`,
         null palette, alpha threshold 0.0, `WICBitmapPaletteTypeCustom` -> `CopyPixels` into the new buffer. Scale first, then convert.
     (h) `E_OUTOFMEMORY` anywhere is `InsufficientMemory` (the entry is kept: `is_entry_failure() == false`); any other WIC failure (garbage
         payload, truncated PNG, unknown codec) is `Com` and an entry failure (`DiskCacheStore.IsCacheEntryFailure` deletes the entry).
         A garbage payload is `Com`, NOT `InvalidData` (golden `zero-bytes-64-garbage-throws-com`, `four-bytes-garbage-throws-com`).
     The info is `(frame width, frame height, downscaled)` (the SOURCE size, never the result size).
  4. **`encode_jpeg` / `encode_png`** (C# `WicImageEncoder`). `encode_jpeg` checks `quality` in `1..=100` first (`QualityOutOfRange`, nothing else
     touched); then disposed, then `byte_count > u32::MAX`. (C# `Encode` also checks a null `pixels` and a null `output`, before disposed:
     no Rust twin, references cannot be null.) Exact call order: factory; `CreateEncoder(container GUID, VENDOR_MICROSOFT)`;
     `encoder.Initialize(stream, WIC_BITMAP_ENCODER_NO_CACHE)`; `encoder.CreateNewFrame(out frame, out options)` (the option bag exists
     for PNG too and is passed to `frame.Initialize` unchanged); for JPEG `ImageQuality` = `quality as f32 / 100.0` written as a
     `VT_R4` variant through a `PROPBAG2` with `dwType = PROPBAG2_TYPE_DATA`, name `"ImageQuality"` (`IPropertyBag2::Write(1, &bag,
     &variant)`; a failing HRESULT is `Com`; the C# string is CoTaskMem, any NUL-terminated UTF-16 buffer that outlives the call is fine in
     Rust); PNG writes no property (`quality == 0` internally means "none"); `frame.Initialize(options)`, `SetSize`,
     `SetResolution(96, 96)`, `SetPixelFormat(source_format(layout))` (in/out: the encoder may change it). Then by
     `plan_encode_path(source_format, accepted_format)`:
     `Direct` (accepted == source) one `WritePixels(height, stride, byte_count, address)`;
     `Bgr24Bands` (accepted == 24bppBGR; JPEG and opaque PNG) bands of `rows_per_band(width, height)` rows through ONE reused band buffer
     (`BAND_BYTES / (width * 3)` rows, clamped to `1..=height`), each row converted by `bgrx32_to_bgr24`, one `WritePixels` per band (REVIEW: for a `Pbgra32` source the fourth byte is dropped as is: a
     JPEG of translucent premultiplied pixels shows the premultiplied colour, not a composite; `PreviewCacheFile` refuses alpha before it
     gets here; golden case `jpeg-pbgra32-source-alpha-byte-dropped` pins it);
     `WicConversion` (anything else, PNG with alpha wants 32bppBGRA) a temporary `IWICBitmap` of the source + `WriteSource`, so WIC un-premultiplies
     exactly like WPF. Then `frame.Commit()`, `encoder.Commit()`. The source buffer must outlive `Commit`. The payload bytes written to `output`
     are what the C# wrote (same WIC, same parameters): the on-disk cache format is unchanged and the W4-08b/W4-09 cache files stay readable by both apps.
  5. **`bgrx32_to_bgr24`** drops byte 3 of every pixel; `pixel_count = source.len() / 4` (a partial trailing pixel is ignored);
     `destination.len() < 3 * pixel_count` is `Err(DestinationTooShort)` and nothing is written. Bytes beyond `3 * pixel_count` are
     unspecified in C# (a vector store may zero up to 4 of them) and untouched in Rust; the golden compares only the first `3 * pixel_count` bytes.
     The C# `+ 16` slack requirement does not apply to the Rust version.
  6. **`is_out_of_memory(hresult)`** is exactly `hresult == 0x8007000E` (signed `-2147024882`); `WINCODEC_ERR_*` codes (e.g. `0x88982F60`)
     and `E_FAIL` are false. **`is_opaque_format`** is exact 16-byte membership; an unknown GUID with the same prefix is false.
  7. **Factory.** C# `CreateFactory`: `WICCreateImagingFactory_Proxy(WINCODEC_SDK_VERSION1)`; `hr < 0` throws its HRESULT, a null result with
     a non-negative `hr` is `E_FAIL`. W4-11a implements exactly this as `interop::create_factory()` (no `CoInitializeEx` needed, its test
     pins that): USE IT, do not re-declare the proxy import. One factory per call, never shared across threads (`Com<T>` is `!Send`).
     Open question 1 is closed by W4-11a.
  8. **Errors are values, not panics.** An `Err` from the `Write` adapter becomes `EncodeError::Io` (when recorded) or `Com`. No `unwrap()` on
     user data, no `todo!()` left.
  9. **Release discipline.** Every COM interface created is released exactly once on every path (success, early `Err`, `E_OUTOFMEMORY`), in the
     C# reverse order (converter, scaler, frame, decoder, stream, factory; options, frame, encoder, factory and the IStream adapter for encode;
     scaler, bitmap, factory for resize), by RAII guards. A partially built `PixelBuffer` is freed by `Drop` (the C# `finally { pixels?.Dispose(); }`). Use W4-11a's `Com<T>` (counted,
     `outstanding_on_this_thread()`) for every interface, so the `CacheEncodeDecodeAndScale_Balanced` twin asserts the counter returns to
     its starting value after each call, error paths included.
  10. **Output stream (REVIEW, resolves open question 2).** W4-11a's `ComStream` takes a `Box<dyn StreamBackend>` (`'static`, `Send`), so a
      borrowed `&mut dyn Write` cannot be handed to WIC directly, and C# `ManagedIStream` also forwards `Seek`, `SetSize`, `Stat`
      (`cbSize = Length`) and `Commit` (flush) to the `Stream`. Implement `encode` as: `ComStream::writable_memory()`; encode; on success
      `dispose()` it, `into_any()` back to `Cursor<Vec<u8>>`, `output.write_all(&bytes)` (so the bytes land at the CURRENT position of
      `output`, which C# only guarantees if WIC never seeks to an absolute origin). A write error of `output` is `EncodeError::Io`. The
      payload is a few MB at most. Keep `output: &mut dyn Write` (no `Seek` bound).

- Traps checklist (docs/MULTI-AGENT-PLAN.md §7; the first draft cited wrong numbers): **3** (arithmetic: `w * h * 4` of the decoded size is
  computed in `u64`, NOT `i64`: `(2^31-1)^2 * 4` overflows `i64` (a debug panic in Rust; in C# `(long)width * height * 4` WRAPS negative
  and the check passes, then `Allocate` fails) - Rust returns `InvalidData(TOO_LARGE)` for it, a deliberate divergence, `// DIVERGENCE:`
  in the code; `stride`, `byte_count` are `i32`/`i64` like C#, cast to `u32` only after the `> u32::MAX` check, `rows_per_band` uses
  `BAND_BYTES / (width * 3)` with `width * 3` in `i64`), **8** (`layout: Option<PixelLayout>` is `None` = "by frame format", never a
  default value; `expected_height` is read only when `expected_width > 0`), **9** (every C# `catch`/throw is its own variant: empty payload,
  invalid dimensions, header mismatch, too large are four `InvalidData` texts that callers log, keep them byte-identical; `COMException`
  with `E_OUTOFMEMORY` is `InsufficientMemory`, any other is `Com`; failures are values, never a panic). Traps 1, 2, 4-7 and 10 do not
  apply (GUIDs are 16-byte equality, not string compare; there is no mutable global: the band buffer is per call). INV ids: this unit owns
  none. `INV-2` (PARITY: "Clear/evict invalidates in-flight and persist work") is NOT what the first draft said: the entry-failure
  classification (`DiskCacheStore.IsCacheEntryFailure`, W4-09/W4-10b/W4-14) is the input of W4-09's cache-miss-and-delete branch and only
  indirectly of INV-2; INV-12 (cache never mixes backends) is not touched here (the payload carries no backend). Unsafe policy: `unsafe`
  only in the two `native` modules, one `// SAFETY:` per block, never in the pure functions.

## Golden package
- `oracle/W4-11e.cs`: four commands (dispatch lines in the file header). `wic-bgrx-to-bgr` and `wic-cache-classify` call the internal functions by
  reflection and `DynamicMethod` (span parameters) and are machine independent. `wic-scale-resize` and `wic-cache-codec` run the real WIC of the
  oracle machine (deterministic for one Windows version, D19) over a deterministic pattern. Not run by the author; the wiring step runs it.
- `golden-inputs/*.json`, outputs in `golden-reference/` after the wiring step. Pattern (identical in the Rust test): byte `i`
  (row-major, no padding) = `((i as u64 * 131) + (seed as u64 * 17) + (i / 251) as u64) & 0xFF`; with `alpha: true` on `Pbgra32` byte 3 of
  pixel `(x, y)` is `255 - (x * 255 / max(width - 1, 1))` and the three colour bytes are `min(colour, alpha)`. The hashed bytes are B,G,R of
  every pixel for `Bgr32` (the unused fourth byte is WIC-defined, not part of the contract) and all four for `Pbgra32`; the hash is FNV-1a 64,
  16 lowercase hex digits (offset `14695981039346656037`, prime `1099511628211`).
- Case design: BGRX conversion at 0, 1, 3, 4, 5, 8, 17, 64, 257 pixels, destination exactly `3N` (no room for the C# vector slack), a partial
  trailing pixel, two too-short destinations; every opaque GUID, the alpha formats, a near-miss GUID and the empty GUID, HRESULTs
  `E_OUTOFMEMORY`, `WINCODEC_ERR_COMPONENTNOTFOUND`, `E_FAIL`, `E_INVALIDARG`, 0; resize 4x, odd target, 1x1, exact 3x, non-uniform axes,
  enlargement, 1-pixel strip, same size for both layouts (copy), one axis changed (goes through WIC), zero and negative sizes, disposed source
  (also at same size: the disposed check comes before the copy); codec PNG opaque/alpha/forced layouts (the Pbgra32 case without `alpha: true` carries the raw pattern in byte 3, it is NOT opaque:
  renamed from `...-fully-opaque-...`), JPEG q 1/30/90/95/100, JPEG from a `Pbgra32` source (alpha byte dropped, decodes as Bgr32), width not a
  multiple of 4, width 1, quality 0/101/-5, boxes (width only, height only, both, larger than frame, equal to frame, 1-pixel strip, with alpha),
  expected size mismatch in each dimension and a match, empty / zero-filled / 4-byte / signature-only payloads.

## Open questions
1. **COM apartment and factory ownership. CLOSED by W4-11a**: `interop::create_factory()` calls `WICCreateImagingFactory_Proxy` and needs no
   `CoInitializeEx`; this unit uses it and `native` has no copy.
2. **Seekability of the output. RESOLVED by note 10**: encode into `ComStream::writable_memory()` (a seekable `Cursor<Vec<u8>>`) and copy the
   bytes to `output`; no `Seek` bound, signatures unchanged. If the lead prefers streaming, W4-11a would need a `StreamBackend` over a
   borrowed writer (not `'static`), which its trait cannot express.
3. **Native goldens across Windows versions.** `wic-scale-resize` and `wic-cache-codec` hash WIC output. WPF's cross-version cache test relies on
   the same determinism, but windows-latest may carry a different WIC build than the golden machine. If a first run differs, compare
   `width/height/layout/sourceWidth/sourceHeight/downscaled/throws` exactly and the hash columns only against the same run's C#-reference
   re-generated on that runner (the oracle can run there), and record it in the PR. Do not weaken the pure goldens.
4. **`Pixels(PixelBufferError)` classification.** `is_entry_failure` returns `false` for `OutOfMemory` and `true` for every other pixel error
   (C# `PixelBuffer.Allocate` throws `ArgumentOutOfRangeException`, an `ArgumentException`, for bad geometry; `IsCacheEntryFailure` is true for
   `ArgumentException`, `InvalidOperationException` (so `ObjectDisposed`) and false for `OutOfMemoryException`; unreachable here because the
   size is validated first). If W4-16a renames its variants this follows it.
5. **`DecodePlan` uses `u32` raw sizes.** WIC reports `UINT`; the C# compares against `int.MaxValue` on `uint`. The stub keeps `u32` in
   `plan_decode` so the `> i32::MAX` check is testable (`0x8000_0000`); the native code passes the WIC values unchanged.
6. **Home of the three trait seams** (REVIEW, new). W4-09 defines `PngEncoder`, W4-08b defines `PreviewPayloadCodec`, W4-10b proposes
   `CacheImageReader` in `pr_imaging::cache::image_reader` (owned by W4-08b), and W4-09's own open question 1 recommends ONE merged
   `CacheImageEncoder`. The lead must pick before W4-08b/W4-11e start; this unit then writes `WicCacheCodec` once.
7. **GUID constants duplicate W4-11a's `interop::guids`** (`windows::GUID` there, `pr_core::...::Guid` in this stub, same 16 bytes; W4-11a
   lacks the PNG container, the vendor and nothing else). Recommended: keep the pure decisions on `pr_core` `Guid` (no `windows` crate in
   pure tests) and add one `From<GUID>` conversion in the native module; the constants test pins both against each other.
8. **Who owns `crates/pr-platform-win/tests/preview_cache_wic.rs`** and the other cross-draft native tests (see Test list). W4-08b says
   "lands with W4-11e". Recommended: this unit's porter writes it, adding it to the Owned files; if the lead prefers W4-08b's porter, strike
   the three bullets under "Native tests that OTHER drafts assign to this unit".
