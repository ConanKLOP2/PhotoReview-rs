## Semantics notes (C# is the spec)
1. **comctl32 v5 vs v6 (the one real trap, D-W8B3-8).** A process without a Common-Controls v6 manifest (every `cargo test` executable of this crate; the .NET test host in C#) loads `System32\comctl32.dll` v5.82. That DLL has **no** `TaskDialogIndirect` (and no `GetWindowSubclass`); it does
   export `InitCommonControlsEx`, `SetWindowSubclass`, `RemoveWindowSubclass`, `DefSubclassProc` by name (checked on this machine by parsing the export table: 119 named exports). A static import of `TaskDialogIndirect` (what a plain `windows::Win32::UI::Controls::TaskDialogIndirect` call produces)
   would make Windows refuse to start any executable that links it ("entry point not found", before `main`). Therefore `task_dialog` binds the function itself: `LoadLibraryW("comctl32.dll")` + `GetProcAddress("TaskDialogIndirect")` on first use, under the **current thread's** activation
   context; **only a successful lookup is cached** (a `OnceLock<unsafe extern "system" fn(..)>` set on success), so a lookup that failed before an `ActivationScope` existed does not poison a later one. The other four functions are imported statically through the `windows` crate.
2. **Run-time bound `task_dialog_indirect`.** Signature of the export: `HRESULT TaskDialogIndirect(const TASKDIALOGCONFIG*, int* pnButton, int* pnRadioButton, BOOL* pfVerificationFlagChecked)`. The wrapper always passes all three out pointers (C# lets callers pass null) and returns them in `TaskDialogResult`.
   `Err(Hresult)` for a negative `HRESULT`; when the function cannot be resolved the error is `Hresult(0x80004002)` (`E_NOINTERFACE`). The call is modal: it runs a message loop until the dialog closes. `cbSize` must be 160 (use `structs::new_task_dialog_config`, 11a) and the struct is 1-byte packed (a 4/8-byte
   packed struct gave `E_INVALIDARG` in C#, WP-19a). `is_available()` resolves without calling.
3. **Icons.** `TD_WARNING_ICON`..`TD_SHIELD_ICON` are the C# values -1..-4 (`nint`). The SDK macro is `MAKEINTRESOURCEW(-1)` = `(LPWSTR)(ULONG_PTR)(WORD)(-1)` = `0xFFFF`; the windows-rs constants are `0xFFFF`..`0xFFFC`. C# passes the sign-extended `0xFFFF_FFFF_FFFF_FFFF`
   in `MainIcon` (a union with a pointer) and the OS accepts it; the Rust code stores `(TD_WARNING_ICON as u16) as usize as *const u16` instead (identical for the OS, which reads the low word of an integer resource id, and it never relies on the upper bits). The constants keep the C# value because the golden does.
4. **`init_common_controls_ex(classes)`** builds `INITCOMMONCONTROLSEX { dwSize: 8, dwICC: classes }` and returns the `BOOL` (`false` for an unknown flag). C# callers pass `ICC_STANDARD_CLASSES | ICC_LISTVIEW_CLASSES | ICC_PROGRESS_CLASS | ICC_BAR_CLASSES` (the `uint[2]` they build is the same struct).
   It must run on the UI thread before the first control of those classes is created; calling it repeatedly is harmless.
5. **Subclassing.** `set_window_subclass(hwnd, proc, id, ref_data)`: the pair `(proc, id)` identifies the subclass; calling it again with the same pair only updates `ref_data`. The procedure must call `def_subclass_proc` for messages it does not handle and must `remove_window_subclass` on `WM_NCDESTROY` (the OS does not).
   The calling thread must be the window's thread (else `FALSE`). `SubclassProc` is `unsafe extern "system" fn(hwnd, msg, wparam, lparam, id, ref_data) -> isize`; a Rust panic must not unwind out of it (wrap the body in `catch_unwind` and return `0`, the C# code wraps in try/catch the same way).
6. **`get_combo_box_info(combo)`** returns the windows-rs `COMBOBOXINFO` with `cbSize = 64` set by the wrapper; `None` when `GetComboBoxInfo` returns `FALSE`. `hwndList` (offset 56) is the drop-down list, used by `DialogEditCentering`/the dark list painter.
7. **`get_class_name(hwnd)`** uses a 256-unit buffer and returns the text up to the returned length; `None` when the length is `0`. The class name `"Static"`, `"Edit"`, `"ComboBox"`, `"SysListView32"`... compare ordinal ignore-case in the callers (not here).
8. **`fill_rect(hdc, rect, brush)`** returns the raw `int` (non-zero on success); **`create_pen(style, width, color_ref)`** returns `0` on failure (C# does not check). `color_ref` is a `COLORREF` (`0x00BBGGRR`), not ARGB; the caller selects the pen out before `DeleteObject` (W8-11d).
9. **ActivationContext.** `create_act_ctx` returns the handle or `Err(Win32Error::last())` when the OS returns `INVALID_HANDLE_VALUE` (-1); `activate_act_ctx` returns the cookie; `deactivate_act_ctx(0, cookie)` must run on the same thread and in reverse order of activation (an out-of-order deactivation is a fast-fail in the OS);
   `release_act_ctx` drops the handle's reference. `ActivationScope::from_manifest_text` writes the text to `%TEMP%\PhotoReviewRs-comctl-<pid>-<counter>.manifest` (UTF-8, no BOM), creates the context with `lpSource` = that path (no `ACTCTX_FLAG_*` set: the source is a manifest file), activates it, then **deletes the file before returning** (the context has parsed it).
   `from_module_resource` sets `ACTCTX_FLAG_RESOURCE_NAME_VALID` with `lpResourceName = MAKEINTRESOURCE(id)` (the C# kit: `Source = <dll path>`, `ResourceName = 1`). `Drop`: `DeactivateActCtx(0, cookie)` then `ReleaseActCtx(context)`; errors in `Drop` are ignored (cannot be reported). The scope is `!Send`.
10. **Manifest content** (checked by the two pure tests): root `assembly` in `urn:schemas-microsoft-com:asm.v1`; `dpiAwareness` (namespace `http://schemas.microsoft.com/SMI/2016/WindowsSettings`) text starts with `PerMonitorV2`; one `dependentAssembly/assemblyIdentity` with `name="Microsoft.Windows.Common-Controls"`, `version="6.0.0.0"`, `type="win32"`,
    `processorArchitecture="*"`, `publicKeyToken="6595b64144ccf1df"`, `language="*"`; `requestedExecutionLevel level="asInvoker"`; `supportedOS Id="{8e0f7a12-bfb3-4fe8-b9a5-48fd50a15a9a}"`. The application exe embeds the manifest at link time (W8-20a: `cargo:rustc-link-arg-bins=/MANIFEST:EMBED` + `/MANIFESTINPUT:<path>`; no extra dependency).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1: do NOT call `windows::Win32::UI::Controls::TaskDialogIndirect` anywhere (note 1): the test executables stop loading. A grep for `TaskDialogIndirect(` outside `comctl.rs` must find nothing.
- T2 (item 3, integers): `NMHDR.code` is `u32` in windows-rs and the `NM_*`/`LVN_*`/`TTN_*` constants are negative `i32`: compare `hdr.code as i32 == NM_CUSTOMDRAW`, never `hdr.code == NM_CUSTOMDRAW as u32` written wrong or with an unsuffixed literal that wraps.
- T3: `CDRF_*` are `isize` (the `LRESULT` a window procedure returns) and `CDDS_*` `u32` (a `DWORD` in the struct): do not mix; `CDRF_NOTIFYITEMDRAW` and `CDRF_NOTIFYSUBITEMDRAW` are both 0x20 (SDK: `CDRF_NOTIFYSUBITEMDRAW` is 0x20 as well).
- T4: `LPSTR_TEXTCALLBACKW` is `(LPWSTR)-1` = `isize` -1; `TTTOOLINFOW.lpszText` is a pointer: `-1isize as *mut u16`.
- T5: `TTTOOLINFOW_V2_SIZE` (64) is the size that works with comctl32 v5 AND v6 (the v6 struct is 72 with `lpReserved`); use it for `cbSize` in `TTM_ADDTOOL` so a test host without manifest works (the C# comment).
- T6: `LVNI_SELECTED`/`LVNIS_SELECTED` and `LVIS_SELECTED` are different families with the same value 2 here; use `LVIS_*` for item state, `LVNI_*` for `LVM_GETNEXTITEM`.
- T7: `NMLISTVIEW_SIZE` (88) and `NMLVCUSTOMDRAW_SIZE` (104) are wrong in C# (64 and 136) and unused: do not use them; use `size_of::<NMLISTVIEW>()` / `size_of::<NMLVCUSTOMDRAW>()`.
- T8: `SetWindowSubclass` leaks the subclass if `WM_NCDESTROY` is not handled; `RemoveWindowSubclass` inside the procedure while processing a message is allowed.
- T9: the activation context is per thread: an `ActivationScope` created on the test thread does not activate on other threads; create controls and call `task_dialog_indirect` on that thread.

## Safety rules (a `// SAFETY:` per `unsafe` block)
- `GetProcAddress` result transmuted to `unsafe extern "system" fn(*const TASKDIALOGCONFIG, *mut i32, *mut i32, *mut BOOL) -> HRESULT`: "the export has exactly this documented signature in comctl32 v6".
- The `task_dialog_indirect` call: "`config` is a live packed struct whose pointer members the caller guarantees (`# Safety`), the three out pointers are locals".
- `set_window_subclass`/`def_subclass_proc`: obligations in `# Safety`; the inner block repeats "upheld by the caller of this function".
- `get_combo_box_info`: "`info` is a local `COMBOBOXINFO` with `cbSize` set; the OS writes at most `cbSize` bytes".
- `get_class_name`: "the buffer is a local `[u16; 256]` and the length passed is 256".
- `ActivationScope`: the `ACTCTXW` pointer fields point into locals (`Vec<u16>` of the path, NUL-terminated) alive during `CreateActCtxW`.

## Decisions taken in this contract (D-W8B3-n; the lead may overrule in `contracts/README.md`)
- **D-W8B3-8 `TaskDialogIndirect` is bound at run time and only successful lookups are cached; the manifest is a file in the crate (`shell.manifest`) plus the `SHELL_MANIFEST` constant; native tests activate it with `ActivationScope::from_manifest_text`.** Reason: notes 1 and 9. Alternatives: embed a manifest into every test executable through a `build.rs` linker argument
  (works for the app, but `cargo test` executables of other crates would need it too and the rule "the only FFI dependency is windows-rs" leaves no `embed-manifest` crate); skip TaskDialog tests (loses the only C# twin that proves the packing).
- The two wrong unused size constants are ported with the C# value (golden equality) and flagged, not corrected: fixing them would make the golden test fail by design (D-W8B1-8 "golden wins").
