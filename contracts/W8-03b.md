## Semantics notes

### `Enter(hwnd, current)` (exact order of effects)
1. `state_before = if current == Minimized { Normal } else { current }`. Set `enter_needs_maximized_state = true` first.
2. `hwnd == 0`: set `normal_bounds = None` and return. Nothing else is touched or called (stale `window_rect_before`, `monitor_before` etc. stay as they were;
   `exit` never reads them without saved bounds). `ops` receives NO call.
3. `ops.is_iconic(hwnd)` true: `ops.show_normal(hwnd)` (before any measuring; a minimized window has a bogus rect). This is the only `is_iconic` use.
4. `ops.normal_position(hwnd)`: `Some(r)` => `normal_bounds = Some(r)`, `None` => `normal_bounds = None`.
5. `window_rect_before = ops.window_rect(hwnd)` or an all-zero rect `ScreenRect::new(0, 0, 0, 0)` when `None` (C# ignores the `GetWindowRect` result and
   keeps the zeroed `out` struct). Read after the minimized restore.
6. `ops.nearest_monitor(hwnd)`:
   - `Some(m)` (the snapshot is never handle 0): `monitor_before = m.handle`, `work_before = m.work`, `style_before = ops.window_style(hwnd)`,
     `ops.set_window_style(hwnd, style_before & !WS_CHROME)`, then ONE `ops.set_window_pos(hwnd, m.monitor, SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)`
     (flags `0x34`; the full `rcMonitor`, which covers the taskbar), then `enter_needs_maximized_state = false`. Exactly these 3 mutating calls in this
     order, no `show_maximized`.
   - `None`: `monitor_before = 0` (legacy path: the caller maximizes). No style change, no `set_window_pos`. `enter_needs_maximized_state` stays `true`.
7. `enter` does NOT reset `exit_needs_state_restore`. There is no "already fullscreen" guard: calling `enter` twice without `exit` stores the fullscreen
   rect/style as "before" (ShellFullscreen, W8-13k, guards this; do not add a guard here, the C# controller has none and the tests pin it).

### `Exit(hwnd)`
1. `hwnd == 0 || normal_bounds.is_none()`: `exit_needs_state_restore = true` and return IMMEDIATELY: `normal_bounds` is NOT cleared on this path (with
   `hwnd == 0` and saved bounds the bounds survive; a later `exit` with a real handle still restores). No `ops` or `layout` call.
2. `monitor_before == 0`: `exit_needs_state_restore = true`; no `ops` call, no style restore (the legacy path never changed the style).
3. Otherwise `exit_needs_state_restore = false` and:
   - `same_work = layout.monitor_of(hwnd) == monitor_before && layout.try_get_work(monitor_before) == Some(work_before)`. Short circuit: `try_get_work` is
     not called when the monitor differs. Equality is on all four edges (a 1 px difference is "not the same").
   - `ops.set_window_style(hwnd, style_before)` (exact original value, including bits outside `WS_CHROME`), BEFORE any `set_window_pos` / `show_maximized`.
   - if `same_work || state_before != Maximized`: `b = window_rect_before`; when `!same_work`, `b = resolve_normal_exit_rect(b, &layout.work_areas())`
     (`work_areas` is called only on this path); then ONE `ops.set_window_pos(hwnd, b, SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)`.
     A Maximized window with an unchanged work area therefore also goes back with the exact rect (its rect already includes the frame overhang) and is
     NOT sent `show_maximized`.
   - else (state was Maximized and the work area / monitor changed): `ops.set_window_pos(hwnd, ScreenRect::new(0, 0, 0, 0), SWP_NOMOVE | SWP_NOSIZE |
     SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)` (flags `0x37`, refreshes the frame), THEN `ops.show_maximized(hwnd)` so Windows computes the
     maximized rect.
   - `state_before == Minimized` cannot happen (`enter` maps it to `Normal`).
4. At the end of paths 2 and 3 (not path 1): `normal_bounds = None`.
5. A second `exit` after a completed one takes path 1 (`normal_bounds` is `None`): `exit_needs_state_restore = true`, no calls.

### `resolve_normal_exit_rect(saved, works)`
1. `works.is_empty()` => `saved`.
2. `band_bottom = min(saved.bottom, saved.top + 32)`. For each work area `w` in list order: `iw = min(saved.right, w.right) - max(saved.left, w.left)`,
   `ih = min(band_bottom, w.bottom) - max(saved.top, w.top)`; the first `w` with `iw >= 120 && ih >= 16` returns `saved` unchanged. Boundaries are inclusive:
   `iw == 120` keeps, `119` moves; `ih == 16` keeps, `15` moves. A rect shorter than 16 px can never pass (its band is its own height): it falls to step 3
   and, when it is inside an area, comes back unchanged anyway.
3. Else pick the work area nearest to the rect centre: `cx = (saved.left + saved.right) / 2`, `cy = (saved.top + saved.bottom) / 2` (`i32`, `wrapping_add`,
   integer division truncating toward zero, like C#); per area `dx = max(max(w.left - cx, cx - w.right), 0)` and `dy` likewise (computed in `i32`
   with wrapping subtraction, then widened to `i64`), `d = dx*dx + dy*dy` in `i64` (wrapping ops). Strictly smaller wins, so on a tie the FIRST area in the
   given order stays. Start with `best = works[0]`, `best_dist = i64::MAX`.
4. `width = min(saved.width(), best.width())`, `height = min(saved.height(), best.height())`; `left = clamp(saved.left, best.left, best.right - width)`,
   `top = clamp(saved.top, best.top, best.bottom - height)`; result `(left, top, left + width, top + height)`. Implement the clamp as
   `value.max(lo).min(hi)`, NOT `i32::clamp` (which panics when `lo > hi`; C# `Math.Clamp` throws `ArgumentException` there, reachable only through `i32`
   overflow or an inverted work area; a production path must not panic, and the result for `lo <= hi` is identical).
5. Pure: no `ops`, no layout. The input slice is not modified.

### Properties
`state_before` starts `Normal`; `normal_bounds()` returns `Some((left, top, right, bottom))` while the saved rect is held, `None` otherwise (initial,
after `enter(0, ..)`, after a failed `normal_position`, after a completed `exit`). `enter_needs_maximized_state` and `exit_needs_state_restore` start `false`.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- Item 3 (arithmetic): C# `int` is unchecked; use `wrapping_add` / `wrapping_sub` everywhere in `resolve_normal_exit_rect` (`saved.top + 32`, `iw`/`ih`, `best.right - width`, `left + width`, `top + height`, the `cx`/`cy` sums and the `dx`/`dy` subtractions) (also `ScreenRect::width`/`height` from W8-03a must wrap). A debug-build
  `-` would panic on extreme coordinates. The `long` distance uses `wrapping_mul` / `wrapping_add` in `i64`.
- Item 10 (ordering): iterate the `works` slice in the given order; first match / first minimum wins; no sort, no `HashMap`.
- Item 8 (null vs empty): `NormalBounds` is `Option`, "no saved rect" is `None`, never an all-zero rect. Conversely `window_rect_before` has no `Option`: a failed
  `GetWindowRect` is an all-zero rect (C# `out` default), and a later exit would move the window to `(0,0,0,0)`. Port as is; do not "fix" it.
- Order of Win32 effects is the behaviour (the C# comments record DWM animation / stale-frame measurements): style change BEFORE the single `set_window_pos`
  on enter; style restore BEFORE the move on exit; frame refresh BEFORE `show_maximized`. Tests assert whole call sequences, not single calls.
- `is not Maximized` is `!= Maximized` over a 3-state enum; `Minimized` never reaches `exit`'s branch (mapped to `Normal` on enter).
- Early return of `exit` path 1 leaves `normal_bounds` untouched (note above); path 2/3 clear it. A `bounds = None` in the wrong place changes the
  `hwnd == 0` then real `exit` behaviour.
- No sleeping, no timers, no logging, no clock: this unit is single-threaded UI-thread logic.
- UI text: none. No `unsafe`, no `windows` crate, no `unwrap`/`expect`.

## Open questions
1. **Shape of the W8-03a types.** The stub assumes `ScreenRect { left, top, right, bottom: i32 }` with `new`, wrapping `width()`/`height()`, and
   `MonitorLayout` with `monitor_of / try_get_work / work_areas` taking `isize` handles, in `windowing::{monitor_layout, contracts}`. 03a is written in the
   same batch, so confirm when the two contracts are merged; only paths and names move.
2. **`IFullscreenController`** (4 members: `StateBefore`, `NormalBounds`, `Enter(hwnd, state)`, `Exit(hwnd)`) is a C# interface used by DI/tests. In Rust the
   controller needs the `WindowOps` handle on each call, so it does not fit a handle-only trait. Recommended: do not port the interface (no second
   implementation exists in C#; `ShellFullscreen` uses the concrete class); 03a should not generate an empty trait for it. If 03a does, the Rust form
   would be a thin adapter in W8-13k that owns the ops and the controller.
3. **`WindowOps` placement.** It lives in `fullscreen.rs` because only this unit uses it today. W8-13k may add the other window operations (title bar,
   `Refit`'s `TryGetMonitorRect`/`MoveTo` from `IFullscreenNative`) as further methods or a second trait; the lead can move the trait to
   `windowing/window_ops.rs` then (a rename-only change). The plan's name `WindowOps` is kept.
4. **`GetWindowRect` failure** keeps the all-zero rect like C# (an unreachable case for a live HWND, but the quirk is cheap to keep and changes the
   exit target to the screen origin). A stricter port could skip the restore; kept as C# for parity.
