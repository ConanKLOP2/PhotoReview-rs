- Semantics (exact; the loop is the spec):
  1. **Wrapper.** `try_read_lossy_frame` = `walk_lossy_frame`; an `Err(e)` with `e.is_io_failure()` is returned as `Err(e)`; any other
     `RawHeaderError` (budget exhausted, read past end, truncated) becomes `Ok(None)` (C# sets width = height = 0 and returns false). The
     probe never converts an I/O failure into "not a preview" (I-13: it must surface as an I/O problem).
  2. **Range check, in this order, before any read:** `length < 4 || offset < 0 || offset > source.length() - length` => `Ok(None)`.
     All i64; `source.length() - length` cannot overflow for `length >= 4` and a non-negative source length, so `length = i64::MAX` and
     `offset = len/2` are plain `Ok(None)` (fuzz test). Never compute `offset + length` before this check; after it `end = offset + length <= len`.
  3. **SOI.** `source.read(offset, 2)` must be `FF D8`, else `Ok(None)` (a source error here follows rule 1).
  4. **Walk.** `pos = offset + 2`, `fill_bytes = 0`, `segment = 0`. `while segment < MAX_JPEG_MARKER_SEGMENTS (512) && pos + 4 <= end`:
     - read 4 bytes at `pos` (copy them into a `[u8; 4]` at once: the source slice is invalidated by the next read, and the borrow checker
       enforces it). `head[0] != 0xFF` => `Ok(None)`. `marker = head[1]`.
     - **Fill byte** (`marker == 0xFF`): `fill_bytes += 1; if fill_bytes > MAX_JPEG_FILL_BYTES (65 536) => Ok(None)`; `pos += 1`; `continue`
       WITHOUT incrementing `segment` (C# does `segment--` before the `for` increment). So 65 536 consecutive fill bytes are tolerated,
       the 65 537th rejects (golden `fill-65536-then-frame` true, `fill-65537-then-frame` false), and fill bytes never use the 512 budget
       (golden `fill-does-not-use-segments-...`). The loop condition still applies on every fill step: a fill run that reaches
       `pos + 4 > end` ends the walk with `Ok(None)`.
     - `fill_bytes = 0` for every other marker (the run is "in a row": reset on the first non-FF marker byte).
     - `marker == 0x00 || marker == 0xDA || marker == 0xD9` => `Ok(None)` (stuffed byte, SOS, EOI before a frame).
     - **Standalone** (`marker == 0x01 || 0xD0..=0xD8`): `pos += 2`, and it DOES count as a segment iteration (golden
       `standalone-markers-count-as-segments-511` true / `-512` false). `FF D8` inside the walk is skipped like RSTn.
     - `segment_length = (head[2] << 8) | head[3]`; `< 2` => `Ok(None)`.
     - **SOF candidates** are `0xC0..=0xCF` except `0xC4` (DHT), `0xC8` (JPG), `0xCC` (DAC); those three are ordinary segments (skipped by length).
       For a SOF candidate: `marker > 0xC2 || segment_length < 8 || pos + 9 > end` => `Ok(None)` (a lossless SOF3 or an arithmetic/hierarchical
       frame ends the walk, the next SOF is NOT searched). Then read 5 bytes at `pos + 4` = precision, height (2, BE), width (2, BE).
       `precision != 8` => `Ok(None)`. Result `Some(LossyFrame { width, height })` iff `width > 0 && height > 0`, else `Ok(None)`.
     - otherwise `pos += 2 + segment_length`, `segment += 1`. (`segment_length` is at most 65 535, so `pos` stays far below i64::MAX.)
  5. Loop exit without a frame (cap reached, range exhausted) => `Ok(None)`.
  6. Budget: the source charges 64 KB blocks once each (W5-01/W5-12 semantics, 8 MiB total); the probe adds no state, so the golden cases
     `budget-exhausting-app-segments-140` (false) and `budget-just-inside-app-segments-100` (true) are decided by the SOURCE. The test source
     must reproduce the charging rule exactly (see Depends on).
- Traps checklist (§7): numeric ones: 3 (C# `long`/`int` => i64 for offsets/lengths, `i32` for width/height, never `usize` arithmetic that can
  wrap on `pos + 4`), 10 (cap semantics, the fill/segment interaction). Also:
  - A source that returns fewer bytes than requested violates the trait; do not index blindly: `<[u8; 4]>::try_from(slice)` and treat a
    mismatch as `Ok(None)`. No `unwrap`, no direct `[]` on source data (parsers must never panic).
  - The C# `out` values on `false` are 0/0 except one corner (zero width with non-zero height leaves the height set, then returns false).
    No caller reads them on false; Rust returns `None`. Goldens deliberately omit width/height when `ok` is false.
  - INV ids: none apply (no cache, gate or generation). Hot path: called per IFD in the strip-preview path; allocation-free (small stack
    arrays), no `String` formatting on the `Ok(None)` paths (the text of a wrapped non-IO error is dropped).
  - Native libraries: none. No `unsafe`. No test is `#[ignore]`.

## Golden package
- `oracle/W5-02b.cs`: command `jpeg-marker-probe`; calls the internal `JpegMarkerProbe.TryReadLossyFrame` by reflection with a budget-charging
  memory source or a throwing source. Needs `<Reference Include="PhotoReview.Imaging.Raw">` in `tools/oracle-cs/OracleCs.csproj` and the Raw dll in
  the baseline build folder (wiring step; the dispatch line is in the file header). It compiled against the working-copy dll in a scratch
  project; it was NOT run.
- `golden-inputs/jpeg-marker-probe.json` (generated by `gen-inputs.js`, committed; the node script is only a convenience): 86 cases
  `{name, source: memory|throw-invalid|throw-io, parts:[{hex, pad_to?, repeat?}], offset, length? | length_delta?}`. Bytes = concatenation of
  the parts; each part is `hex`, zero-extended to `pad_to` bytes, repeated `repeat` times (large inputs such as 512 segments or 140 x 64 KiB
  stay a few lines). Effective length: `length` if present (a number, or a decimal string for `9223372036854775807`), else
  `total - offset + length_delta`. The oracle output row echoes `source` and `parts` and adds `total_length`, `offset`, the resolved `length`
  (decimal string), `ok`, `io_failure`, and `width`/`height` only when `ok`.
  The Rust golden test reads the OUTPUT file only (it holds the inputs too), rebuilds the bytes with the same part rule, runs the probe against
  the budget-charging source (or the failing source for `throw-*`) and compares `ok`, `width`, `height`, `io_failure` (`Err` with `is_io_failure`).
- Case design: every range-check boundary (negative/huge/short length, offset past the end, range ends inside the frame, exact 11-byte minimum);
  every SOF marker C0-CF; zero/maximum sizes; precisions 0/8/12/16; DHT/JPG/DAC skipping; segment lengths 0, 1, 2, 300, 65 533, 65 535;
  terminators 00/DA/D9; standalone markers; both caps at their exact boundary (511/512/513 segments, 65 536/65 537 fill bytes, fill between
  segments, fill runs reset by markers); no SOI; header budget exhausted vs just inside; throwing sources.
