- Semantics notes:
  1. **Result is `Result<Option<DecodedImage>, BlankPath>`.** `Ok(None)` is "no thumbnail" for ALL of: missing file, directory,
     sharing violation, access denied, not an image, damaged EXIF, zero frames, no APP1 thumbnail, thumbnail too big, copy failure.
     C# catches `IOException, NotSupportedException, InvalidOperationException, UnauthorizedAccessException, ArgumentException,
     OverflowException, InvalidCastException, FormatException, COMException` (the COMException branch is what a damaged
     metadata header turns into; `ThumbnailCache` does NOT catch around the reader, a throw would fail the whole thumbnail load).
     In Rust every `io::Error` and every `ThumbnailBackendError` collapses to `Ok(None)`; there is no per-type branch to port
     (trap §7.9: the merge is intentional here, the C# list is one "treat the same" block). `OutOfMemoryException` is NOT in the
     C# list; Rust allocation failure aborts, and `PixelBuffer::allocate` returning `Err` (aligned alloc refused) is also `Ok(None)`
     (open question 2).
  2. **Blank path is the only error.** `ArgumentException.ThrowIfNullOrWhiteSpace(path)` runs BEFORE the try block: `""`, `"   "`
     => `Err(BlankPath)`. A non-blank missing path is `Ok(None)`. (`ArgumentNullException.ThrowIfNull(codec)` has no twin: a reference
     cannot be null.)
  3. **The file is opened shared (INV-8).** `fs.open_read_shared(path, 64 * 1024)`: ReadWrite|Delete sharing, sequential scan. The
     stream is handed to the backend and dropped when the frame is dropped, which happens before `try_read` returns (the returned image
     never depends on the stream: eager copy). Do not read the whole file into memory (C# streams it: a 30 MB JPEG is not slurped).
  4. **Order and early exits (do not reorder; the size gate must precede any allocation).**
     a. `backend.open` -> `None` frame (count 0) => `Ok(None)`.
     b. `frame.main_size()`: a side above `i32::MAX` => `Ok(None)` (checked BEFORE the thumbnail is fetched).
     c. `frame.thumbnail()` is `None` => `Ok(None)`.
     d. `bitmap.size()`: a side above `i32::MAX` or `!is_acceptable_size(w, h)` => `Ok(None)`. WIC itself refuses thumbnails above
        about 400-500 px (measured in the C# test comments); this gate is the second line of defence and must hold for a fake backend.
     e. `PixelBuffer::allocate(w, h, Pbgra32)`, `copy_pbgra(buf, stride = w * 4)`; on `Err` drop the buffer, `Ok(None)`.
     f. `orientation = frame.orientation()` (read AFTER the copy, like C#; it is infallible, 1 on failure).
     g. `apply_orientation(pixels, orientation)` takes ownership; `oriented.width/height/byte_count` are read from the RESULT.
     h. `transposed = is_transposed(orientation)` (5..=8 of the RAW value, not normalised: a 9 is not transposed, and `orientation` in
        the result is the value the frame returned, which is already 1..=8 by contract).
     i. `original_width/height = transposed ? (main_h, main_w) : (main_w, main_h)`.
  5. **Result fields.** `pixel_width/height` = oriented size; `estimated_bytes` = oriented byte count (`w * h * 4`); `downscaled = true`
     ALWAYS (even for a thumbnail the same size as the main frame); `actual_backend = DecoderBackend::Wpf` (cache identity: the
     label is part of the thumbnail cache stamp's decoder identity, do not change to WicDirect, do not "improve"); platform image =
     `codec.wrap_pixels(oriented)`; `exif`/`is_degraded_fallback` default (None / false). Layout is `Pbgra32` (A = 255 for a JPEG
     thumbnail).
  6. **`is_acceptable_size`**: `width > 0 && height > 0 && (w as i64) * (h as i64) <= 4 * 1024 * 1024`. The `i64` product matters:
     `100000 x 100000` and `i32::MAX x i32::MAX` overflow `i32`. Boundaries: `2048x2048` true, `2048x2049` false, `4194304x1` true,
     `4194305x1` false, any non-positive side false, `-5 x -5` false.
  7. **No `unsafe` here.** `copy_pbgra` takes `&mut [u8]`; the COM `CopyPixels(NULL rect, stride, size, ptr)` lives in the backend.
  8. **Thread safety.** The function is re-entrant; backend and codec are `Send + Sync`; no static state (C# creates a WIC factory per
     call and releases it in `finally`: the backend does that, `try_read` holds none).
- Traps checklist: §7 items 3 (the `i64` product; `u32 -> i32` range checks; `stride = w * 4` cannot overflow once the 4 MP gate

## Open questions
1. **`Result<Option<_>, BlankPath>` vs plain `Option`.** C# throws `ArgumentException` for a blank path. Recommended (and used by the
   stub): keep it as an `Err(BlankPath)` so a caller bug is visible. Alternative: `debug_assert!(!blank)` and return `None`.
   `ThumbnailCache` (W4-10b) is the only caller and never passes a blank path (it validates earlier), so either is safe.
2. **Allocation failure.** C# lets `OutOfMemoryException` escape (the 4 MP gate bounds the request to 16 MB, so it is theoretical).
   The stub maps an `Err` from `PixelBuffer::allocate` to `Ok(None)`. Alternative: propagate as a new error variant. Lead decides with W4-16a.
3. **Native pixel exactness.** If the Rust WIC backend is real WIC the SHA-256 should match; if `windows-rs` initialises the format
   converter with different dither/palette arguments the hash differs. The contract for W4-11c says `WICBitmapDitherType.None`,
   `WICBitmapPaletteType.Custom`, alpha threshold 0.0 (the three C# arguments), which should be bit-identical.
4. **Test factory name.** `pr_platform_win::wic::embedded_thumbnail_backend()` is this contract's assumption; W4-11c may name it
   differently. Native twins adapt; the pure tests do not depend on it.
5. **`PlatformImageCodec` method name** (`wrap_pixels` vs W4-01c's choice): cosmetic, resolved at wiring.
