## Semantics (C# is the spec)
### Sharing and re-entrancy (D-W8B3H-2)
1. A clock is shared: `MessageLoop` polls it, windows and presenters subscribe to it. So `FrameClockBase<P>` is used as `Rc<dyn HostFrameClock>` with `&self` methods; its state is one `RefCell<State<P>>` (policy, handler slots, `next_id`, `requested`, `armed`, `disposed`, `tick_count`).
   It is `!Send` (`PhantomData<*const ()>`, boxed `FnMut` handlers): the C# `VerifyAccess` runtime check becomes a compile-time property.
2. **No borrow is held while a handler runs.** `try_tick` clones the list of slot ids, then for each id takes the handler out of its slot (`handler.take()`), calls it, and puts it back. A handler may therefore call `unsubscribe` (also for itself), `subscribe` and `request_frame` on the same clock.
   Snapshot semantics, like a C# multicast delegate: handlers present when the tick STARTED are called in subscription order even if an earlier handler unsubscribed them (the `removed` flag only drops them when they come back and stops them from the NEXT tick on); handlers added during the tick are NOT called in it.
   `update_armed` counts a slot as live when it is not `removed` (a slot whose handler is out running counts, a removed one does not).
3. `subscribe`/`request_frame`/`unsubscribe` in `HostFrameClock` cannot return an error (they mirror `pr_app`'s `FrameClock`). When arming the source fails (`SetWaitableTimer`), the trait methods PANIC with the `HostError` text, which is what the C# `Win32Exception` thrown out of `Frame +=` does to its caller (D-W8B3H-2);
   `try_subscribe`/`try_request_frame`/`try_unsubscribe` return the `Result` and are what the tests of the failure path use. `on_signaled`/`on_deadline` return `Result` (the C# exception reached the loop; the loop returns it).
4. `unsubscribe` of an unknown id is a no-op (`unsubscribe` after `dispose` too). Ids are `u64` from a counter starting at 1, never reused.

### Tick algorithm (`TryTick`, C# 128-159) -- port line by line
`on_signaled()` = `try_tick(true)`, `on_deadline()` = `try_tick(false)`. In `try_tick(signaled)`:
- not armed: return `Ok(false)` (no `now()` call, no policy call).
- `now = clock()`. `policy.should_tick(env, now, signaled)?`: `None` -> `Ok(false)`; `Some(frame_timestamp)` -> go on. (Policy errors propagate.)
- `requested = false`; `tick_count += 1`; `tick = FrameTick { timestamp: frame_timestamp, rendering_time_ms: rendering_time_ms(frame_timestamp, epoch, frequency), timing: env.current_timing() }`.
- raise to the snapshot of handlers (see 2) inside `catch_unwind`; then, whether or not a handler panicked (the C# `finally`): `update_armed()?`; if still armed, `policy.on_ticked(env, frame_timestamp, clock())?`. Then, if a handler panicked, `resume_unwind` the first payload (a later handler of the same tick is not called after a panic, like the C# exception that aborts `Invoke`).
- return `Ok(true)`.
`update_armed()`: `armed = !disposed && (any live slot || requested)`; if unchanged return; else store it and call `policy.on_armed_changed(env, armed, clock())` (the policy sees the NEW state through the `armed` argument).
`request_frame` = `requested = true; update_armed()`. `dispose` = once: `disposed = true`, drop all slots, `requested = false`, `update_armed()` (which disarms), `policy.dispose_core()`; a second call does nothing. After `dispose`, `wait_handle()` returns 0 (the C# value was a closed handle; the loop never polls a disarmed clock, a 0 makes the intent explicit).
`ticks_until_deadline()`: `deadline = policy.deadline_timestamp(armed)`; `i64::MAX` stays `i64::MAX`, else `deadline.wrapping_sub(now)` -> use `saturating_sub` (T7).
`FrameClockBase::new` takes `epoch = clock()` once; `timestamp = None` is `qpc_now`.

### `TimerFrameClock` (C# 17-148)
5. Constructor (`TimerPolicy::new`): `fixed_period <= 0` -> `ArgumentOutOfRange { param: "fixed_period" }` (checked BEFORE creating the timer); `period = fixed_period` or `qpc_frequency() / 60`; `WaitableTimer::new()` (11f already does high-resolution first, then the normal one); both failing -> `HostError::Gfx` (C# `Win32Exception "CreateWaitableTimerEx failed"`; the `GfxError.operation` carries the name).
6. `on_armed_changed(true)` -> `schedule(now)`; `(false)` -> `scheduled = false` and `timer.cancel()` (a failure is ignored, as in C#). A signal already raised by the timer stays raised; `should_tick` ignores it because `scheduled == false` (test 5).
7. `should_tick`: `frame = due`; `!signaled || !scheduled` -> `None` (the timer has no deadline of its own; a stale signal after cancel is dropped); `now < due - early_tolerance()` -> `arm_timer(due, now)?` and `None` (an early signal re-arms the SAME frame, never ticks twice in a frame);
   `now - due >= period` -> `frame = now` (the UI was busy for a whole period: anchor to the present and never burst the missed frames); `scheduled = false`; `Some(frame)`.
8. `on_ticked`: `last_frame = frame_timestamp; has_last_frame = true; schedule(now)`.
9. `schedule` = `compute_next_due` (pure, rules in the stub doc; the idle-display rule "draw at once" is the perf gate 3 comment of C# 119-122) then store `due`, `scheduled = true`, `arm_timer(due, now)`.
10. `arm_timer`: `relative_due_100ns(due, now, frequency)` is `-max(1, (due - now) * 10_000_000 / frequency)` (negative = relative; at least 1 so "now" still fires); `timer.set_due_100ns(value)`; failure -> `HostError::Gfx` ("SetWaitableTimer failed").
11. `early_tolerance()` = `qpc_frequency() / 500` (2 ms at 10 MHz).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (item 3, integers): every QPC arithmetic here is `i64`; `(due - now) * 10_000_000` overflows `i64` for gaps above about 9.2e11 ticks (a 25 hour wait at 10 MHz; the C# test `TimerClock_SignalWithinEarlyTolerance...` uses `Period * 1_000_000` which is fine).
  Compute the product in `i128` and clamp; do not `wrapping_mul` (a wrapped negative would turn a far deadline into "fire now").
- T2: `next_grid_point` with `at <= last_vblank` or `refresh_period <= 0` is `max(at, last_vblank)`; the ceiling division `(at - last + period - 1) / period` can overflow for `at` near `i64::MAX`: `i128`.
- T3 (the `finally`): the `update_armed` + `on_ticked` pair runs even when a handler panics (test 12 pins `is_armed` and `scheduled_frame` afterwards).
- T4 (snapshot): a handler that unsubscribes ANOTHER handler of the same tick does not stop it in this tick; one that subscribes a new handler does not get it called in this tick. A mutant that iterates the live list fails the snapshot tests below.
- T5: `should_tick` returns `None` for an early signal AND re-arms; a version that ticks (or does not re-arm) double-ticks a frame. The boundary is inclusive: `now == due - early_tolerance` ticks, one tick less does not (test 3).
- T6: `rendering_time_ms` is `(frame_timestamp - epoch)` as an integer subtraction, then `* 1000.0 / frequency`; test 8 checks to 9 decimals.
- T7: `FrameTick` equality is `double.Equals` for `rendering_time_ms` (NaN equal, `0.0 == -0.0`), not derived `PartialEq`.
- T8: the two `Option`s: `fixed_period: None` means "follow the display / 60 Hz" and changes `period` when a timing is known; `Some(p)` never does (test 9 vs 3/4).
- T9: `request_frame` while a handler runs (test 7): `requested` is set AFTER `requested = false` of the tick, so the clock stays armed for exactly one more frame.
- T10: `Debug`/`!Send`: `FrameClockBase` must not become `Send` by accident (a field change); the compile-time check below fails then.

## Open questions (recommended default in bold)

4. A fake `WaitableTimer` so the timer clock is testable with no OS handle at all: **not needed** (creating the handle is cheap and nobody waits on it); the one test that waits is `#[ignore]`.
