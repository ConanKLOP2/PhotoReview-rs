  Mapping notes: `string destination` => `&Path` (D1: the boundary takes `&Path`; callers hold `String` records and pass `Path::new(&s)`);
  `long sourceSize` stays `i64` (a journal `Size` is C# `long`; do not widen to u64); `FileStat` is the existing
  `abstractions::FileStat { length: u64, last_write_utc: DateTimeUtc }` (only these two fields are compared);
  `ArgumentNullException.ThrowIfNull(created)` has no Rust twin: `&FileStat` cannot be null (record it as a PARITY note). `IsSameFile` is C#
  `internal` but called by `FileActionService` (W3-04), so it is `pub` here.
- Semantics notes:
  1. **Guard order, one stat.** Call `file_system.get_file_stat(destination)` EXACTLY once. If `None`, return. Else delete only when
     `length < source_size` AND `is_same_file(&stat, created)`, both evaluated on the same stat value; never re-stat. The C# order is the length
     check first, then `IsSameFile`; with pure comparisons the order is unobservable, keep it anyway.
  2. **Strictly shorter.** `stat.Length < sourceSize`. Equal means a complete copy: kept "for Recovery to judge" (M23). A longer file is kept.
     `source_size <= 0` never deletes (empty dest with `source_size == 0` is kept: `0 < 0` is false; negative: `0 < -1` is false).
     Implement without a wrapping cast: `source_size > 0 && stat.length < source_size as u64` (safe once `source_size > 0`), or `i128`.
     TRAP: `stat.length as i64 < source_size` would wrap for `length > i64::MAX`; never cast the stat length to a signed type.
  3. **Same file = exact.** `now.length == created.length && now.last_write_utc == created.last_write_utc`. No tolerance. The Undo/Move
     fingerprint compare uses a +-2 s window (`FileFingerprint`, W3-05); do NOT reuse it or share a helper with it ("a tolerance would only
     widen what a replacement can pass as"). `DateTimeUtc` equality is tick equality (100 ns), like .NET `DateTime ==`.
  4. **Never throws except OOM.** C# wraps everything in `catch (Exception ex) when (ex is not OutOfMemoryException)` (this also swallowed
     `ArgumentException` from `PhysicalFileSystem`'s null/whitespace path guard; `&Path` has no such failure, but an empty path must still not panic:
     the Rust `PhysicalFileSystem` returns `None`/`Err`, so nothing special is needed). In Rust the failures
     are values: `get_file_stat` is `Option` (`None` when missing OR when the stat failed: the C# `GetFileStat` returning null and throwing both end
     as "kept"); `delete` returns `io::Result` => ignore the `Err` (`let _ = ...` with a comment; no `unwrap`). Deleting a file that vanished
     meanwhile succeeds per the trait (C# `File.Delete`). No panic is caught (no `catch_unwind`, see open question 4). Nothing is logged or
     returned: the original error is what the caller reports and the Failed journal line still describes the operation. Do NOT add a `Log`
     parameter (the C# method has none).
  5. **Only `get_file_stat` + `delete`.** No `file_exists`, `directory_exists`, `enumerate_*`, `move_file`. A destination that is a directory is
     out of scope (no golden case: the fake and the real stat of a directory are different facts, tested in W2-14).
  6. **The caller's proof is a precondition, not checked here.** The function takes no `CopyCreationProof`; `FileActionService` (W3-04) must call
     it only when `proof.destination_created()` is true AND `created` is the stat observed right after the copy. It is in the stub doc and
     must be an acceptance line of W3-04.
  7. **Inherent race.** Stat and delete are not atomic: a foreign file can replace the destination between them. C# accepts this (the
     size+mtime guard narrows it); Rust must not "improve" it (no deleting through a handle: that would be new behaviour).
- Traps checklist (docs/MULTI-AGENT-PLAN.md section 7): 3 (`i64` vs `u64` length, sign of `source_size`), INV-3/INV-4 (a user file is deleted

  (`Assembly.GetType("PhotoReview.Core.FileActions.PartialDestinationCleanup")`, `BindingFlags.Static | Public | NonPublic`), as W2-07

  Recycle Bin). Dispatch line is in the file header. It does not use `W2Util`.
- `golden-inputs/partial-cleanup.json`: 26 cases (17 `cleanup`, 9 `same-file`). Ticks are .NET UTC ticks (all inside the NTFS range);
  `delete_fails` holds the file open with `FileShare.None` so `File.Delete` throws `IOException`.
  Case design: strict `<` boundary (shorter by one byte, equal, longer, 0 vs 0, 0 vs 4, negative source size, source size over `int.MaxValue`);
  each guard of `IsSameFile` broken alone (other length, +1 tick, -1 tick, +1 s) so a tolerance mutant dies; "shorter than the source but not
  the created stat" in both directions; destination missing; delete fails for a partial AND for a complete file (no exception either way);
  pure `IsSameFile` table with `long.MaxValue` lengths and `DateTime.MaxValue` ticks.
- Output per `cleanup` case: `existed_before`, `exists_after`, `deleted`, `threw` (null expected; non-null means the C# `catch` leaked).
  Per `same-file` case: `same_file`.

## Open questions
1. **`destination` type.** `&Path` (D1; every `FileSystem` caller). `&str` would save a conversion but diverge. Recommended: `&Path`.
2. **`is_same_file` home.** C# keeps it on the cleanup class and `FileActionService` calls it at lines 344 and 364 (group copy rollback
   verification). Recommended: stay in `partial_cleanup` as `pub fn`. Alternative: hoist into a shared module when W3-04 is written.
3. **Module name.** `partial_cleanup.rs`; no better split for 38 lines. `mod.rs` doc already says "services in Wave 3".
4. **Panicking `FileSystem`.** C# swallows every exception except OOM; Rust swallows `Err`/`None` only, a panic propagates. Recommended
   (as written): accept; `catch_unwind` would need `UnwindSafe` plumbing on `&dyn FileSystem` for no real-world gain. If the lead disagrees
   the signature does not change (wrap the body).
5. **Line count.** Plan table says 29 lines, baseline d92d6aae has 38 (XML docs). Not semantic.
