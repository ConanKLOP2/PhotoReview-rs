## Semantics (C# is the spec)
### OverlayHost
1. **Roots are `Box<dyn ElementNode>`** (contract W8-15a: "15f holds `Box<dyn ElementNode>`"). The host owns the elements ONCE; the C# habit of also keeping typed properties (`Toolbar`, `Status`) is replaced by `root::<T>`/`root_mut::<T>` by id (downcast through `ElementNode::as_any`) and, for children inside `LayerElement`, `LayerElement::child_mut` (pr_app amendment A1 of W8-15h).
2. **`add`**: `Err(Disposed)` after `dispose`; `Err(DuplicateId(id))` when `find(root.base().id())` is `Some` over the existing trees (the message text of C# is "An overlay element with id '<id>' already exists."); otherwise `roots.push`. Test: adding a root whose id equals a DESCENDANT of an earlier root fails, adding a root that has a descendant with an existing id does not (C# checks only the root id).
3. **`find`**: roots in order, `ElementNode::find` (depth first). **`opacity_store`** (C# `Resolve` + `Animator`'s resolver): an `OpacityStore` whose `opacity(id)` is the root's opacity when a ROOT has that id, `None` otherwise (the animator then treats the element as gone and drops its tween), and whose `set_opacity(id, v)` writes `base_mut().set_opacity(v)` of that root. Descendants cannot be written because `ElementNode` has no `find_mut` (amendment A2, optional; today only roots are animated: `ToolbarPanel`, `InfoOverlayHost`, and the C# host test animates a root).
4. **`arrange`**: each root `OverlayElement::arrange(context)` in order (the blanket impl measures in the whole client, then places). **`render`**: each root `OverlayElement::render(dc)` in order; the last root is drawn last (on top). **`hit_test`**: iterate roots in REVERSE; first `Some(find_at(point))` wins; hidden, hit-test-disabled and zero-opacity elements never answer (that logic lives in `find_at`, 15a); `None` = the image gets the click.
5. **`dispose`**: `release_resources()` on every root, `roots.clear()`, `disposed = true`; the second call does nothing. `remove` after dispose is allowed (C# did not check).

### OverlayMessageHandler (`try_handle`; the handler runs FIRST in the chain)
6. The arms are listed on the stub; the rules that are easy to get wrong:
   - **Observe vs swallow.** `WM_MOUSEMOVE`, `WM_MOUSELEAVE`, `WM_CAPTURECHANGED` and every key that is not an overlay key return `None` (the image still receives them). `WM_LBUTTONDOWN`/`DBLCLK` return `Some(0)` only when `pointer_down` is true. `WM_LBUTTONUP` returns `None` unless the overlay holds a press, else `pointer_up`'s answer. The wheel returns `Some(0)` only over an overlay panel.
   - **Tooltip relay order.** Move: overlay first, relay second. Down: relay FIRST, then `pointer_down`. Up: the early `None` (no press held) comes BEFORE the relay; relay, then release the capture, then `pointer_up`.
   - **Capture.** After a swallowed press that left `is_pointer_down()` true, `window.capture_pointer()`. On release: `if window.has_pointer_capture()` set `releasing`, `release_pointer()`, clear `releasing` on every path (`ReleaseCapture` sends `WM_CAPTURECHANGED` synchronously to this same window while the arm is still running: the nested call must find `releasing == true` and NOT cancel the press). `WM_CAPTURECHANGED` cancels only when `!releasing && overlay.is_pointer_down() && lparam != hwnd` (`lParam` is the window that gains the capture; `hwnd` itself gaining it is not a theft).
   - **DPI.** Mouse `lParam` is client PIXELS: `low_word(lparam) / dpi`, `high_word(lparam) / dpi`, `dpi = window.dpi_scale()` or `1` when `<= 0`. The wheel `lParam` is SCREEN pixels (signed, multi-monitor negatives): `window.screen_to_client_dip(PointD { x: low_word, y: high_word })`; the result is already DIP.
   - **Keys.** `repeat = (lparam >> 30) & 1 != 0` (previous key state bit), `shift = os.is_key_down(VK_SHIFT)`, key = `(wparam & 0xFFFF) as i32` (the virtual key). Only overlay-owned keys (Tab, Space/Enter on a focused button) are swallowed, decided by the overlay.
   - **`WM_MOUSELEAVE` tracking.** The first `WM_MOUSEMOVE` after a leave (or ever) calls `os.request_mouse_leave(hwnd)` and sets `tracking_leave`; `WM_MOUSELEAVE` clears it. The request is one-shot per the OS contract.
7. `low_word(v) = (v & 0xFFFF) as u16 as i16 as i32`, `high_word(v) = ((v >> 16) & 0xFFFF) as u16 as i16 as i32` (arithmetic shift on a negative `isize` is fine because of the mask).
8. State is in `Cell`s; the handler never holds a borrow across a call into the overlay, the window or the tooltips (they re-enter).

### OverlayNative (`native.rs`)
9. `Win32OverlayOs::request_mouse_leave`: `win32::dialog_chrome::track_mouse_event(TME_LEAVE, hwnd, 0)` (11d; the wrapper sets `cbSize`), result ignored. `is_key_down`: `key_state_is_down(win32::settings_native::get_key_state(vk))` (the module path is as exported by 11e; the porter uses whatever 11e names it). `client_origin_on_screen`: `ClientToScreen` has **no wrapper in 11b/11c/11d**: one local `unsafe` call in `native.rs` (`windows::Win32::Graphics::Gdi::ClientToScreen`, `POINT { 0, 0 }` on the stack, safe because the pointer is a live local). `(0, 0)` when it fails (C# `ClientToScreen ? origin : (0,0)`). Lead may instead add `client_to_screen` to 11d (Q3); the stub does not change.
10. `key_state_is_down(state: i16) = (state as u16 & 0x8000) != 0`.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (re-entrancy): `ReleaseCapture`/`SetCapture` deliver `WM_CAPTURECHANGED` synchronously; `releasing` is a `Cell` set around the call. A test calls the handler from inside a fake `release_pointer` and checks no cancel.
- T2 (z-order of messages, D-W8B4X-15): the overlay handler is inserted FIRST by `MainWindowOverlay::attach` (15j), which runs AFTER the main-window constructor. The constructor already inserted the keep-warm handler first (16d, C# `RegisterKeepWarm`), so the chain from the head is overlay, keep-warm, scroll bars, input, windowing, context menu. Keep-warm returns `None` for every message, so the order between the two is not observable; what matters is that nothing but the overlay is inserted first after it.
- T3 (hit testing with DPI): everything past the handler is DIP; `dpi_scale() <= 0` means `1`, NaN is not `<= 0` (kept as in C#, so a NaN scale yields NaN points: no hit).
- T4 (signed words): `low_word`/`high_word` are signed; `(short)` of `0xFFFF` is `-1`. A client point left of or above the window is negative and must not hit.
- T5 (z order of the host): later roots are on top; `hit_test` iterates in reverse, `render` forward.
- T6 (element identity): C# compared button references; Rust compares ids. Ids are unique across the host's trees only for roots (the `add` check); duplicate descendant ids are possible and `find` returns the first.
- T7 (panics): none of these functions may panic on user input; `expect` only on host invariants documented here. A panic in a message handler is captured by the window's guard (13e) and resumed at the owner.
- T8 (error mapping): C# `ArgumentNullException` of `Add`/`Remove`/`Find`/`Render` has no twin (references and `&str` are never null).

## Safety rules (`// SAFETY:` per block)
Only `native.rs` has `unsafe`: the `ClientToScreen` call (a live local `POINT`; the OS writes it and does not keep the pointer). `track_mouse_event` and `get_key_state` are safe wrappers. `host.rs` and `messages.rs` contain none.

## Error mapping
| C# | Rust |
|---|---|
| `Add` duplicate id -> `ArgumentException` | `OverlayHostError::DuplicateId(id)` |
| `Add` after dispose -> `ObjectDisposedException` | `OverlayHostError::Disposed` |
| `ClientToScreen` false | `(0, 0)` |
| `TrackMouseEvent` false | ignored |
| null arguments -> `ArgumentNullException` | not representable |
