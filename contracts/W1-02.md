## Design: how the C# converters map to Rust

* C# attaches `LenientEnumConverter<T>` to each enum type; Rust implements `serde::Serialize`/`Deserialize` for each enum in `enums.rs`
  (macro-generated) by calling `serialize_lenient` / `deserialize_lenient`. So `serde_json::from_str::<LoadingMode>("\"fast\"")` and
  `HashMap<DecoderBackend, u64>` just work.
* Implement the readers as a `serde::de::Visitor` driven by `deserializer.deserialize_any(...)` (JSON is self-describing). One private visitor that
  yields `Option<T>` (`None` = "unreadable, use the fallback") backs `deserialize_lenient` (`unwrap_or_else(T::zero)`), `deserialize_lenient_or`
  (`unwrap_or(default)`) and `deserialize_settings_enum` (returns the `Option`). Implement the visit methods `visit_str`, `visit_i64`, `visit_u64`,
  `visit_f64`, `visit_bool`, `visit_unit`, `visit_none`, `visit_seq`, `visit_map`. Do NOT buffer into `serde_json::Value`: the journal reads one of
  these per line.
* Flag sets work the same way with a second visitor returning `T`.
* `SettingsEnumConverter<T>` returns a C# undefined sentinel (`(T)int.MinValue`); Rust returns `None`. Everything about WHEN it is the sentinel
  is the same as "the plain converter would have returned its default because the input was unreadable". Careful: the zero member is a
  legitimate readable result (`0`, `"0"`, `"Name"`) and gives `Some(zero)`, while for the plain converter you cannot tell.

## Rules for the lenient (plain and settings) enum read, all pinned by the golden

JSON token kinds, by serde_json callback:

| Token | Callback | Result |
|---|---|---|
| string (also a dictionary key) | `visit_str` | `parse_lenient_text(Some(s))` |
| integer that fits `i64` (`visit_i64`) or `u64` (`visit_u64`) | | `lenient_from_number(n)`: needs `i32::try_from(n)` and a member with that value; otherwise unreadable. `-1`, `99`, `2147483648`, `-2147483649`, `9223372036854775807` are unreadable |
| `null` | `visit_unit` (and `visit_none`) | unreadable |
| `true`, `false` | `visit_bool` | unreadable |
| any number written with a fraction or exponent (`1.5`, `1.0`, `1e0`, `0e0`, `1E2`), or an integer beyond `u64`/`i64` range | `visit_f64` | unreadable (even `1.0`; C# `TryGetInt32` rejects it). The generated golden pins `1.0` as unreadable |
| array, object (any nesting) | `visit_seq`, `visit_map` | consume every element/entry (use `IgnoredAny`) and give unreadable. Never an error |

`parse_lenient_text(text)`:
1. `None` or blank (every char is `char::is_whitespace`, includes `""`) gives `None`.
2. `t = text.trim()` (Unicode whitespace both sides: U+00A0, U+3000, U+2003, tab, newline are trimmed; U+200B zero width space and U+FEFF are NOT).
3. Name/alias match: compare `t` with every member name and every alias using `pr_core::text::eq_ignore_case` (C# `OrdinalIgnoreCase`). An alias is trimmed
   before comparing, and blank aliases are skipped. Names and aliases share one table; if two entries ever collided the later one wins (no collision exists).
   Non-ASCII characters that merely look like ASCII do not match: dotless i (U+0131), capital I with dot (U+0130) and long s (U+017F) are not equal to `i`, `I`, `s`.
   Whole-string comparison only: `"Fastx"` does not match `Fast`.
4. Number fallback: parse `t` as a .NET `int` (`int.TryParse(NumberStyles.Integer, InvariantCulture)`), implemented by hand as: optional single `+` or `-`,
   then at least one ASCII digit `0-9` (Arabic-Indic and fullwidth digits are NOT digits here), then optionally any run of ASCII whitespace
   (space and 0x09 to 0x0D), then ONLY U+0000 characters up to the end. Value must fit `i32`. Examples: `"1"`, `"+1"`, `"01"`, `"001"`, `"-0"`, `"+0"`,
   `"1\0"` (digit then NUL), `"1 \0"`, `"1\0\0"` all parse; `"1.0"`, `"1e0"`, `"0x1"`, `"1,0"`, `"1 2"`, `"1\0x"`, `"\01"`, `"+\0"`, `"2147483648"` do not.
   The golden has all of these (the NUL rows look odd but are real .NET behaviour). Then require a member with that value, else `None`.
   Note `"-1"` parses as -1 which is not a member, so unreadable.

Writing: `serialize_lenient` writes the JSON string `value.json_text()`; the same text is the dictionary key (serde_json accepts `serialize_str` for map keys).
`serialize_settings_enum(None)` writes the string `-2147483648`. `SettingsEnumConverter` for a `Some` writes exactly what the plain converter writes.

`deserialize_lenient_or(d, default)`: identical to `deserialize_lenient` except for the fallback value (C# `new LenientEnumConverter<T>(defaultValue)`). The zero
member is still readable as itself.

## Rules for flag sets (`FlagEnumJson`), all pinned by the golden

`deserialize_flags::<T>`:

| Token | Result |
|---|---|
| string | `parse_flags_text(Some(s))` |
| integer `n` that fits `i64` and `n >= 0` | `T::from_bits((n & ALL_BITS as i64) as u32)`: unknown bits stripped. If nothing is left the result is `None` (bits 0), NOT the default: `1024` for ExifInfoFields gives 0, `2147483648` gives 0, `4095` gives 1023 |
| integer `n < 0` (`-1`, `-512`, `i64::MIN`) | default (`DEFAULT_BITS`). `-1` must never become "everything on" |
| integer above `i64::MAX` (visit_u64 beyond i64) | default |
| float (`1.5`, `1.0`, `1e2`, `0e0`), `null`, `true`, `false` | default |
| array, object | consume, then default |

`parse_flags_text(text)`:
1. `None` or blank gives the default.
2. Split on the character `,` only (not `|`, `;`, space). For each piece: `trim()`; empty pieces are skipped.
3. A piece is valid when it equals (OrdinalIgnoreCase) a name in `T::NAMES`, which includes `None`, `All` and `Default`; or when it parses as an `int` with the
   same hand-written grammar as the enum number fallback above (sign, ASCII digits, optional ASCII whitespace, trailing NULs; must fit `i32`) and is NOT
   negative. `"-0"`, `"+0"`, `"0"` are valid zero. `"-1"` and `"-512"` are skipped, as are `"2147483648"` (overflow) and `"1.5"`, `"1e2"`, `"0x10"`.
   An unknown or invalid piece is skipped, it does not poison the others (`"FileName, Foo"` gives FileName).
4. OR the values of all valid pieces; remember whether any piece was valid.
5. Any valid piece: `from_bits(bits & ALL_BITS)` (so `"1024"` for ExifInfoFields gives 0 = None; `"Camera, None"` gives Camera; `"All, None"` gives All;
   `"Default, ModifiedDate"` gives Default | ModifiedDate). No valid piece: default.
   Examples (Exif): `"Foo, Bar"` default; `""`, `" , ,"` default; `"FolderName, FileName"` gives FileName only (FolderName is TitleBar's flag).

`format_flags(value)` (`FlagEnumJson.Format`):
1. `bits = value.bits() & ALL_BITS`. If 0 return `"None"`.
2. Otherwise walk `T::NAMES` in order, skip the names `None`, `All`, `Default` (compare by name), and for each remaining entry with a single bit set
   (`flag != 0 && flag & (flag - 1) == 0`) that is also set in `bits`, push its name. Join with `", "` (comma + one space).
   So the order is ascending bit value as listed in `NAMES`, never the order of the input. Unknown bits are ignored.
   `ExifInfoFields::DEFAULT` writes `"DateTaken, Camera, Lens, Iso, FocalLength, Aperture, ShutterSpeed"`, never `"Default"`.
3. `serialize_flags` writes that text as a JSON string.

## Known divergence (accepted, no golden row; confirm in review)

serde_json parses the bare token `-0` as a float (`-0.0`), so it takes the "float" row (unreadable / default) whereas C# reads it as the integer 0
(plain: `Fast`; settings converter: `Fast` instead of undefined; flags: None instead of default). The same text inside a JSON string (`"-0"`) goes
through the string path and matches C#. The token `-0.0` is unreadable in both. The golden inputs deliberately contain no bare `-0`. Do not add a hack
for it; list it in `behaviour_doubts`.
