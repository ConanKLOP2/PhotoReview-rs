- Semantics notes (read the C# next to them):
  1. **Estimate formula** (the C# class comment is the spec): `total = width*height*(8+3) + rawPixels*rawBpp + max(0,tw)*max(0,th)*4`, with `rawBpp` = 2 (Bayer) / 8 (Linear) / 24 (Float).
     The 11 is `WORKING_IMAGE + RGB_OUTPUT`; do not fold constants into a literal that hides the three parts (the mutation run targets each one).
  2. **Invalid source** returns `0` when `width <= 0 || height <= 0`, BEFORE any other term (so a negative or zero source never reports the target or raw buffer).
     A zero target is NOT invalid: the sum then has no third term.
  3. **Raw pixel count.** The sensor size is used only when BOTH `raw_width > 0` and `raw_height > 0`; otherwise (either one `<= 0`, including a lone positive one) the OUTPUT
     size `width*height` stands in. A sensor smaller than the output is used as given (no `max`): golden `sensor-smaller-than-output`.
  4. **Target** is clamped per axis: `max(0, tw) * max(0, th)`. One negative axis therefore zeroes the term (`target-one-negative`), it is not `abs`.
  5. **Exact arithmetic, then saturate.** C# uses `decimal` (28 digits, no overflow for these ranges: the largest sum is about 2^31 x 2^31 x 35 + 2^62 x 4 ~ 1.8e20 (2^62 x (11 + 24 + 4)), well inside `decimal`).
     Rust: widen every operand to `u128` (or `i128`) before multiplying; never use `i64` multiplications with `checked_*` fallbacks that could change the order of saturation.
     `if total >= i64::MAX as u128 { i64::MAX } else { total as i64 }`: note `>=`, so a total of exactly `i64::MAX` also returns `i64::MAX` (identical value, but keep the `>=`).
     Negative `i32::MIN` width: rejected by note 2 before any widening, so `as u128` on a negative never happens. Use `i128::from(..)` for the target clamp then convert.
  6. **Classify order matters.** `None` => Bayer, FIRST. Then `contains("_fp_dng")` => Float (before the DNG test, so `deflate_dng_fp_dng`-like names are Float). Then the four-name DNG family test,
     ORDINAL and CASE-SENSITIVE (`"LOSSLESS_DNG_LOAD_RAW()"` and `" deflate_dng_load_raw()"` with a leading space: the second still contains `deflate_dng`, so it is DNG; the first is not => Bayer).
     Use `str::contains` on the `&str` as is (no `to_lowercase`, no `trim`). `""` => Bayer (no substring matches). `structure` is consulted ONLY in the DNG branch, and `is_bayer()` is required, so a
     non-DNG name with `NoMosaic` is still Bayer ("no refusal without evidence").
  7. **Known numbers** (pin them in the Rust tests; all `i64`): 100 MP = 11 600 x 8 700 = 100 920 000 px; Bayer bounded = `100_920_000*13 + 1920*1280*4` = 1 321 790 400 (so a 1.2e9 budget refuses
     and 1.5e9 admits); Linear = `*19`; Float = `*35`. `10 000 x 10 000`, target `100 x 100`, raw = sensor 10 000 x 10 000 (what W5-16a's fake probe gives): Bayer = 1 300 040 000 (admitted at total
     1_600_000_000, load 0, headroom 1_600_000_000); Linear/Float 8 B/px or 24 B/px = 1 900 040 000 / 3 500 040 000 (refused at 1.6e9).
  8. **No state, no OS access.** The memory the caller compares with comes from `MemoryInfoSource` (W4-07b); this unit never reads it. Keep every item `pub` (W5-16a is another module of the same crate; `pub(crate)` would
     also work, but the golden test lives in `tests/`, an external crate, so `pub` is required).

## Golden package
- `oracle/W5-16b.cs`: command `libraw-memory-guard`, one result object per input case with `name`, `op` and the op's fields. Dispatch line and the `OracleCs.csproj` change (reference to
  `PhotoReview.Imaging.LibRaw.dll`, built by `tools/oracle.ps1`) are in the file header. The class is `internal` and the oracle assembly is not in `InternalsVisibleTo` (the C# repo is never edited), so the
  oracle uses REFLECTION (nested internal enum and record struct included). It needs no `libraw.dll`: `DecodeMemoryGuard` calls no P/Invoke and loading the assembly does not bind natives.
- `golden-inputs/libraw-memory-guard.json` (generated by `golden-inputs/gen-libraw-memory-guard.js`: `node gen-libraw-memory-guard.js <out.json>`, deterministic, 359 cases): `constants` 1,
  `is-bayer` 40 (colors -1..7 and `i32::MAX` x filters 0, 1, 0x94949494, 0xFFFFFFFF), `classify` 200 (25 decoder names incl. `null`, `""`, case variants, leading space, `_fp_dng`, `fp_dng`, `deflate dng`
  x 8 structures incl. null, 4-colour, 5-colour, colours 0 and -1), `estimate` 111 (37 shapes x Bayer / Linear / Float), `estimate-defaults` 7.
- Result shapes the Rust test must reproduce (JSON equality): `constants` -> `{values:{WorkingImageBytesPerPixel, RgbOutputBytesPerPixel, BitmapBytesPerPixel, BayerRawBytesPerPixel,
  LinearRawBytesPerPixel, FloatRawBytesPerPixel}}` (ints); `is-bayer` -> `{value}`; `classify` -> `{family}` (`"Bayer"|"Linear"|"Float"`, compare with `format!("{:?}", family)`); `estimate` /
  `estimate-defaults` -> `{bytes}` (integers up to 9223372036854775807: parse as `i64`, read the golden number with `serde_json::Value::as_i64`, never through `f64`).
  `filters` in the input is a JSON number up to 4294967295: read as `u64` then `u32::try_from`.
- Case design: every colour boundary of `IsBayer` (0 / 1 / 4 / 5 / negative / `i32::MAX`) with the filter edge values; every substring of the DNG family and of `_fp_dng` alone, sub-string and case near-misses, the
  empty and null names; raw width / height both unknown, one unknown, one-pixel sensor, negative sensor, sensor larger and smaller than the output; target zero, one axis zero, negative axes; width / height zero and
  negative and `i32::MIN`; `i32::MAX` everywhere (saturation), a value just below `i64::MAX` and Float shapes straddling `i64::MAX` (`float-just-below-i64` vs `float-crossing-i64`).
- NOT in the golden: nothing in `DecodeMemoryGuard` is excluded. `TryReadRawStructure` (native pointer reader) and `AdmitDecode` are other units.

## Open questions
1. **Constant types.** The stub uses `i64` for the six `*_BYTES_PER_PIXEL` constants (C# `int`). If W5-16a prefers `u32`/`usize`, change the six lines only; the golden compares numerically.
2. **`estimate_peak_bytes_output_sized` name.** Only a convenience for the C# default arguments (used by 3 tests and none of the production callers, which always pass the raw size and the family).
   The porter may drop it if the tests are written with the full call; keep it if W5-16a's tests want it. It is not part of the golden.
3. **Where the headroom comparison lives.** C# calls `MemoryHeadroom.HasHeadroom` from `LibRawDecoder.AdmitDecode`; the Rust call is `pr_imaging::memory_headroom::has_headroom` (W4-07b). Nothing in this unit
   changes if W5-16a wraps it with a `MemoryInfoSource` closure.
