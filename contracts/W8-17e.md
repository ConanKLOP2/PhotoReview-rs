## Semantics (C# is the spec)
1. **`ShellStartup::run`**: the numbered list in the stub doc is the spec. Notes: (a) `ShellLaunch::parse` happens BEFORE anything else and with the shell's own log; (b) the posted first step is `ui_hop(ui, |_| state.begin())` + `send(())`: the work starts only once the loop pumps (the C# `dispatcher.Post`); (c) the exit code is `forced_exit.unwrap_or(loop_code)`; (d) `run` returns after `run_shutdown`; the dispatcher is shut down last (`Win32UiDispatcher::shutdown()` after the shutdown steps, the C# `using var dispatcher`); (e) the loop result `Err(HostError)` (a failed wait) ends the run with `EXIT_STARTUP_FAILED` after a forced log.
2. **Crash handling (P-15, D-W8B6-25)**: the dispatcher already catches a panic of a posted job and logs it (D-W8B3H-10), the window procedures capture theirs for `rethrow_pending` inside `MessageLoop::run`. The run loop catches what `run` resumes: `catch_unwind(AssertUnwindSafe(|| message_loop.run()))`; `Err(payload)` -> `log_unhandled_forced("UI loop exception", &*payload)`, `LoopFaultCounter::record(MAX_LOOP_FAULTS)`: `Continue` -> run again (the C# "handled = true"), `GiveUp` -> exit code 1. `MessageLoop::run` is re-entrant-safe after an unwind (its `RunningGuard` clears the flag). This is the ONE `catch_unwind` of the UI thread besides `catch_step` and `run_fail_startup` (the last-resort handlers R0003 allows; all three are named in D-W8B6-25).
3. **`install_process_hooks`** (C# `AppDomain.UnhandledException`): installed by `run` right after the state exists (D-W8B6-25: earlier than C# line 321, strictly more coverage; the report is forced, so it does not depend on the settings); chains the previous hook (`take_hook`, then `set_hook(Box::new(move |info| { forced log; previous(info) }))`); `OnceLock` guard so a second `run` in the same test process does not stack hooks; tests pass `install_process_hooks: false`.
4. **`begin` / `after_phase_one` / `phase_two` / `fail_startup`**: per the stub docs. `phase_two` steps in order; the `?` of `create_main_window` is the only failure besides panics (caught by `catch_step`). `fail_startup` is idempotent: a second call (a failure while failing) only repeats the quit.
5. **`create_main_window` and `attach_overlay`**: per the stub docs, in the stated order. Extra rules: (a) the closures given to the window (`Closed`, `Closing`, the owner provider of the dialogs, the `fit` closure, the forwarded-open target) capture `Weak` of the state or of the SLOT, never a strong `Rc` (a cycle would keep the window alive past the shutdown); (b) the slot is filled BEFORE `attach_renderer` and `attach_overlay` run (the overlay's `fit` and the owner closures read it); (c) `window.hwnd()` is non-zero from creation, so `cloak.hide` needs no later retry; (d) the Fit closure calls `with_feature::<MainWindowInputFeature, _>(|feature| feature.input().input().apply_fit())`; (e) the second `NativePopupMenuHost` (Tools menu) has its OWN owner closure over the slot, and is not shared with the context menu (14f).
6. **`MainWindowOverlayViewModel`** (D-W8B6-27): the borrow discipline is the contract: commands that need `&mut MainViewModel` go through `MainWindow::update_view_model` (the borrow ends before the change set is applied); the four read-only dialogs (`show_skipped_files`, `show_recovery`, `show_diagnostics`, `show_benchmark`) use a SHARED `borrow()` so the nested loop of the dialog can still paint; `window` is cloned out of the slot first. With no window (the slot is empty) a command does nothing; `settings()` and `overlay_model()` still read the view model.
7. **`MainWindowForwardTarget`**: per the stub docs; `WindowGone.message` for a missing window is `"The main window is already destroyed."` (the text of `MainWindowError::WindowDestroyed`).
8. **Journal recovery** (`recovery.rs` both crates): the pure rule `prompt_for_failed_entries` and the hop in `start_journal_recovery`. Order rule (C# test `Startup_JournalReconcile_RunsAfterTheLockAndShowAndBeforeAnyQueuedInput`): it is started AFTER `windowShown` and the open of the first path, and its UI continuation is queued behind everything already posted, so it cannot run before input that was queued earlier. The reconcile worker is started at once (before any later queued input is processed); the prompt is shown ONCE; Yes opens Recovery through a SHARED borrow of the view model (`view_model.borrow().show_recovery()`, modal), NEVER through `update_view_model` (a `borrow_mut` held for the whole nested loop would make the paint of the dialog panic). The hop continuation captures `Weak`s (state, window slot), not a strong `Rc<MainWindow>`.
9. **Smoke** (`smoke.rs` both crates): per the stub docs. `Closed` of the window cancels the timeout thread (no thread outlives the window). `close_once` on a destroyed window skips the dispose but still quits with the code. Exit codes: 0 after the frame, `EXIT_SMOKE_TIMEOUT` on timeout. `close_once` may run on the timeout worker, and the state is `!Send`: the worker only sends the code through a `ui_hop`; `forced_exit` is set by the UI-thread continuation (before the dispose and the quit).
10. **Shutdown and failure order** (`shutdown.rs` both crates): `run_shutdown` calls `stop_listening`, `dispose_coalescer`, `close_secondary_windows`, `dispose_main_window`, `dispose_cloak`, `dispose_frame_clock`, `dispose_services`, `shutdown_log`, `dispose_instance_scope`, `dispose_perf_listener` and nothing else. The main window is disposed BEFORE the services (the window releases the surface and the features while the view model and dialogs are alive). Every real step takes its object out first (`take()`), so a second run does nothing and no `RefCell` is borrowed across a `Drop` that may call back. `run_fail_startup`: `log_failure`, `show_failure_box` (each under `catch_unwind`, panics ignored), `force_exit_code(1)`, `close_secondary_windows`, `dispose_main_window`, `quit(1)`, in that order.
11. **`read_saved_placement`** and the placement part of `create_main_window`: `apply_before_show` is skipped for smoke; the saver is given to the window regardless (it is `None`-file in smoke, `placement_file: None`).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (re-entrancy and borrows): `StartupState` fields are `RefCell`s; NO borrow is held across a call into the window, a dialog, `quit` or `Drop`. Rule of thumb in every method: `let x = self.field.borrow().clone();` or `take()`, then use `x`. The slot of the main window is read by dialog owner closures at use time and may be emptied by a nested loop: clone the `Rc<MainWindow>` out first.
- T2 (cycles): see semantics 5(a). Test `state_is_freed_after_run` (a `Drop` counter on a fake in the options, or `Rc::strong_count` of the slot after the shutdown is 1).
- T3 (order is behaviour): cloak -> placement -> show -> view model -> surface -> first frame; early decode after the lock; journal after the show; shutdown order. Each has a recording-fake test (marks in order, step order).
- T4 (exit codes): normal close 0; second instance 0; start-up failure 1; loop fault limit 1; smoke 0 / 7. `forced_exit` wins. Test each.
- T5 (panics): only the three named catches; everything else (including the Fit closure and the owner closures) is panic-free by construction (no `unwrap`/`expect`/indexing on user data); `run` itself never panics: its own `Err` paths return a code.
- T6 (threads): workers get only `Send` data; the sender/`Arc` is cloned before the spawn; the smoke timeout thread and the journal waiter thread are named and bounded (a timeout, a join by the hop); no polling, no `sleep`.
- T7 (modal dialogs inside the view-model borrow, D-W8B6-39): `show_settings` and the other `&mut` commands run a nested loop inside `update_view_model`. The window already tolerates re-entry (`pump_view_model` returns at once on re-entry, `render_frame` uses short borrows); the porter checks with the native test `settings_dialog_command_does_not_panic_the_paint` and reports a `BorrowMutError` as a bug of the window (13h/13j) to the lead, not by working around it here.
- T8 (user data and bin): the native tests use a temp data root, WARP, a fake graph or the real one over temp folders, a unique instance prefix, fake journal recovery; no test touches the real Recycle Bin, config or placement.
- T9 (exit of the dispatcher): the dispatcher is shut down after the last step so late `post`s from workers are dropped, not run (the hop jobs of a dead run find no registry entry).
- T10 (smoke): no lock, no placement read or write, no journal, no focus, `placement_file: None`.
- T11 (strings): all texts through the localizer; the failure box uses the built-in English catalog if `Localizer::current()` was never set (a failure before the language loaded).
- T12 (hooks): `install_process_hooks` never calls into UI code and never takes a lock that the panicking thread may hold except the log's own.

## Safety rules (`// SAFETY:` per `unsafe` block)
None expected: `pr-app` and `pr-shell` have no `unsafe`; the only native calls are through safe wrappers of `pr-platform-win` (`user32`, `dwmapi`). If a porter needs an `unsafe` block, it goes into `pr-platform-win` with a `// SAFETY:` comment and the lead is told.

## Error mapping
| C# | Rust |
|---|---|
| exception in `RunStartupGuardedAsync` / `StartupCoreAsync` | `Err(StartupError)` or a panic caught by `catch_step` -> `fail_startup` |
| exception escaping `_loop.Run()` | panic resumed by `MessageLoop::run`, caught by the run loop, `LoopFaultCounter` |
| `AppDomain.UnhandledException` | `install_process_hooks` (panic hook), forced log |
| `TaskScheduler.UnobservedTaskException` | none (worker panics are reported where they are caught); `Different` row |
| `ShowError` throwing in `FailStartup` | `catch_unwind` around `show_failure_box`, ignored |
