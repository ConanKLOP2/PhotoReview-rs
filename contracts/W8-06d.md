## Scope and decisions (D-06d-1 to D-06d-6 settle what the plan left open; the lead may reverse any of them before the contract PR)

- **D-06d-1 Sinks are imperative, not change-set producers.** The plan row says "take a `&mut dyn` or return a `ChangeSet`". The
  sinks here are the shell side of the coordinators: they repaint the window, show status text and present images. They are not
  view-model state, so they return `()`. The `ChangeSet` of D-W8-1 is returned by the view-model methods (W8-08a), not by these traits.
  Recommended default: `&mut self`, `()`. Alternative (rejected): a `ChangeSet` return from every sink call, which would make each
  coordinator merge UI-side repaint sets it does not own.
- **D-06d-2 `Task` becomes a synchronous call (D-W8-2, R0003).** `OpenFolderAsync`, `PresentAsync`, `MoveAsync`, `ExecuteAsync`
  and `ExecuteGroupAsync` become sync methods. The UI-facing ones (`open_folder`, `present`) return after the request is posted
  to the UI dispatcher; the completion comes back through `UiDispatcher::post` with the INV-9 generation token. The file-action
  executor and move override are blocking, as pr-core already is (`FileActionService::execute`, `MoveOverride`). `PreloadAroundAsync`
  returns the scheduler's own `RunHandle` (the Rust `Task`): `wait()` / `is_complete()` replace `await`.
- **D-06d-3 C# defaults are kept as real Rust bodies; required C# members stay required.** Default members in this file (C#
  `= default` interface bodies): `IDuplicateCleanupSink::show_late_action_status`, `IDuplicateCleanupSink::reload_folder`,
  `IFolderLoadSink::on_empty_with_subfolders`, `IFolderLoadSink::on_files_skipped`, `IFileActionSink::evict_cached_paths`,
  `IPreloadController::{is_idle, notify_navigation, get_viewer_decode_delay}`. Members WITHOUT a C# default are required:
  `IFileActionSink::show_late_action_status` (C# abstract), `IFolderLoadSink::on_unreadable_removed` (AR16 comment: "no default"),
  `IFolderLoadSink::on_empty`, `IFolderLoadSink::on_failed`, and every `IPreloadController` member except the three defaults.
  Rust has no default arguments: `IPresentationSink::set_current_image(.., is_file_change)` and `open_folder(.., initial_path)` take
  every argument, callers pass `false` / `None` explicitly.
- **D-06d-4 `reload_folder` returns a `bool` decided at call time.** C# `ReloadFolderAsync` returns `Task<bool>` that becomes `false`
  when another folder load started while the reload ran (D-03). With a sync request that cannot be known at return. Recommended
  default: the Rust method returns `true` when the shell accepted the reload for the folder that is still shown at call time; the
  "another load started meanwhile" check is done by the coordinator after completion, with its generation token (INV-9), in
  W8-07f. The default body keeps the C# default (`true`). **Lead: confirm before W8-07f starts** (open question 1).
- **D-06d-5 The two forwarding classes live in `coordinators::traits`.** The plan row says "traits only", but the C# files
  `IFileActionExecutor.cs` (32 lines, production `FileActionServiceExecutor` inside) and `PreloadControllerAdapter.cs` (32 lines) are in
  this unit's line count, and the plan lists `PreloadControllerAdapter` under W8-06d. Both stay in `traits.rs`, plus the helper
  `into_move_override` (the C# registration of `IMoveOverride`). Alternative: `coordinators::adapters`; that is a new file and a
  new `mod` line, so it is not chosen by default (open question 3).
- **D-06d-6 The image type of `IPresentationSink::set_current_image` is `Option<Arc<pr_imaging::decode_types::DecodedImage>>`.**
  C# passes `object?` (a WPF `BitmapSource` in the old app). `DecodedImage` is the framework-independent decoded image (C-02) and
  contains no windows types; the shared `Arc` keeps the bitmap alive while the presenter shows it. The presenter (W8-07h) and
  the Win32 sink (W8-16i) use this type; a Win32 surface wrapper is their own concern. Open question 2.

## Semantics (from the C# code; the stub doc comments repeat them)

### Adapter (`PreloadControllerAdapter`)
1. **Lazy and per call.** `new` does not call the factory. Every `IPreloadController` member calls `(self.get_scheduler)()` once and
   forwards to the returned `Arc<PreloadScheduler>`. Nothing is cached: a scheduler that the factory returns later is the one used.
2. **Forward everything.** `is_idle` forwards to the scheduler (the trait default `true` must NOT be used by the adapter).
   `notify_navigation` and `get_viewer_decode_delay` forward too. `preload_around` returns the scheduler's `RunHandle`
   unchanged (not `RunHandle::completed()`), so a caller that waits on it waits for the real run.
3. **`dispose`** calls `(self.get_scheduler)().dispose()`. Afterwards the scheduler starts nothing for `preload_around` (pr-imaging
   `PreloadScheduler::dispose` semantics). The adapter itself adds no state.
4. `cancel` forwards to the scheduler's `cancel`; `clear_preloaded_keys`, `remove_preloaded_keys_for_path` and
   `try_consume_preloaded_key` forward unchanged (`normalized_path` and the key are not re-normalised).

### Move override and executor forwarders
5. `into_move_override(over)` returns a closure that calls `over.move_file(source, destination)` and returns its `io::Result`
   unchanged; the closure keeps the same `Arc`, so one override serves both services (the composition root).
6. `FileActionServiceExecutor` forwards `is_busy` and `lacks_recycle_bin` to the service and passes the request AND the `&CancelToken`
   to `execute` / `execute_group` unchanged (no `CancelToken::none()` substitution).

### Sink and seam defaults
7. The defaults are the C# defaults: see D-06d-3. `reload_folder` returns `true` and opens the folder with `None` as the initial path.

## Traps (docs/MULTI-AGENT-PLAN.md section 7, items 1, 9, 10 do not apply, plus this unit)
1. **Factory read per call (adapter).** A cached `Arc` breaks test `EveryMember_ReadsTheSchedulerFromTheLazyFactoryOnEachCall`
   (reads must be 7, not 1) and the "factory returns a new scheduler" case.
2. **`is_idle` must be forwarded**, not left to the trait default: a forgotten override returns `true` while a preload is in flight,
   and `CancelAndIsIdle_ReflectTheSchedulersInFlightPreload` fails.
3. **`preload_around` returns the real `RunHandle`.** Returning `RunHandle::completed()` makes the caller stop waiting early.
4. **`reload_folder` default is `true`** (C# default). Do not flip it to `false` to "be safe": that would make every reload look stale.
5. **`on_unreadable_removed` and `show_late_action_status` (of `IFileActionSink`) have no default.** Adding one silently drops the AR16
   preload cleanup, or the APP-03 status, in a sink that forgets to override it.
6. **`on_empty_with_subfolders` forwards to `on_empty`.** An implementer that overrides only `on_empty` must keep its behaviour.
7. **`is_file_change` is always explicit.** No Rust default: the caller decides crossfade vs upgrade (see the C# doc comment).
8. **`dispose` and `Drop` differ.** Only the explicit `dispose` forwards; do not implement `Drop` for the adapter (the factory's scheduler may
   be shared with the shell, which disposes it itself).
9. **Blocking calls in a sink are not an error.** `open_folder`, `present` return after posting; an implementation that waits for the
   UI completion inside them deadlocks the message loop (D-W8-2). No test here; it is a review item for W8-07/W8-16.
10. **No path comparisons, no `unsafe`, no `windows` crate** (pure module). Paths are passed through unchanged (`OrdinalIgnoreCase`
    lives in pr-core, `pr_core::text`).
