## Semantics (C# is the spec)
1. **`attach(edit)`**: see the C# line above; the property is `PROP`; `set_window_subclass(edit, subclass_proc, SUBCLASS_ID, 0)` is the one `unsafe` call (its contract: the procedure stays valid until `remove_window_subclass`/`WM_NCDESTROY`, true for a function item). Returns `true` on a second call without installing a second subclass (the property guards it).
2. **`top_padding`** = OS metrics + `padding_for_metrics`; OS failures give `0`. `ReleaseDC` and the restore of the old object run on every path after `GetDC` succeeded (guard type, T1).
3. **`padding_for_metrics`**: integer arithmetic exactly as the C# (truncating division). All operations saturating: `client_height - cap` etc. never panic in debug (T3).
4. **`subclass_proc`**: the message switch runs under `pending_panic::guarded(None, ..)` (D-W8B5-207) and returns `Some(result)` only for the two cases that return early in the C# (`WM_NCCALCSIZE`, `WM_NCPAINT`); every other outcome (other messages, `WM_NCDESTROY` after its two removals, AND a captured panic) continues with the final `def_subclass_proc(hwnd, message, wparam, lparam)` OUTSIDE the guard, exactly where the C# `catch (Exception) {}` falls through to its last line. Returning `0` for a panicking `WM_NCDESTROY` would skip the edit's own destruction handling (a leak); the panic itself is not lost, `guarded` captured it for the owner of the native call. the `WM_NCCALCSIZE` pointer is used only when non-null and `align_of::<Rect>()`-aligned (D-W8B3H-19, `// SAFETY:` on the two reads/writes); `Top += padding` uses `saturating_add`. `WM_NCDESTROY` removes the subclass with the SAME `(proc, id)` it installed and the property; the final `def_subclass_proc` always runs for it.
5. **`paint_band`**: as the C#; `SendMessage` to the parent uses `dialog_native::user32::send_message` (`unsafe`: `WM_CTLCOLOREDIT` carries `hdc`/`hwnd` values, no pointer). The brush is the dialog's: never deleted. `ReleaseDC` on every path after `GetWindowDC` succeeded. The parent answers from inside a `WM_NCPAINT`: the dialog's handler must not hold a `RefCell` borrow across a native call (D-W8B3H-6; test: a parent that answers `WM_CTLCOLOREDIT` while borrowed would panic).
6. **`ListDialogContent`** builders: texts from the presenters of `pr_app::presenters::secondary` with the given `Localizer` (`SkippedFilesPresenter::{title, intro, close_text}(localizer)`, `SkippedFilesPresenter::build_lines(entries, localizer)`, `BatchReviewPresenter::summary(items.len() as i64, localizer)`, `BatchReviewPresenter::build_lines(items, localizer, numbers)`) and `localizer.get(pr_l10n::keys::{BATCH_REVIEW_TITLE, BATCH_REVIEW_CONFIRM, COMMON_CANCEL})`; the sizes are the constants above; no literal user text (D-W8-4).
7. **`ListDialog`**: `build_items`, ids, sizes and layout exactly as the stub docs; `on_initialized` sends `LB_INITSTORAGE` (wParam = count, lParam = count * 256, saturating) ONCE before the loop, `LB_ADDSTRING` for every line (`unsafe` `send_message` with a pointer to a NUL-terminated UTF-16 buffer that lives across the call), tracks `widest` through `base.measure_text_width(line)`, then `LB_SETHORIZONTALEXTENT(widest + base.dx(8))`. A list with 50 001 lines must not be quadratic (one buffer reused is fine). No selection logic (post-baseline).
8. **Behavioural facts the tests pin**: the default button is Cancel when there is no confirm button (Enter closes with Cancel); the intro text colour comes from the content key; the list is the initial focus; Heading is the only header-font control; the minimum width is `max(dx(300), button_row_width + 2 * margin_x)`.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (handle and DC leaks): every `GetDC`/`GetWindowDC` has its `ReleaseDC` on all paths; the font selected into the DC is restored first. Test: `GetGuiResources(GR_GDIOBJECTS)` flat over 100 attach/destroy cycles.
- T2 (re-entrancy): the subclass procedure runs inside `SetWindowPos`, `WM_NCPAINT` and `SendMessage` of the dialog; it holds no borrow and keeps no state (the C# passes `refData = 0`).
- T3 (arithmetic): `padding_for_metrics`, `band_rect`, `layout_controls` and `LB_INITSTORAGE` use saturating/checked operations where C# wraps.
- T5 (integer ids): `CONFIRM_ID`/`CANCEL_ID` are `IDOK`/`IDCANCEL` (`win32::messages`), the three list ids 300..302 do not collide with them.
- T9 (exception to Result): the C# `catch (Exception)` of `Proc` swallows; Rust captures through `pending_panic` instead (D-W8B5-207); `ArgumentNullException(content)` is unrepresentable.
- Panic safety (R0003): no `unwrap`/`expect`/indexing on the UI thread; the window procedure never unwinds. A panic inside `top_padding`/`paint_band` must not leak the DC: `ReleaseDC` and the font restore sit in a guard type (`Drop`), not after the call. Test (native, `ncpaint_*` group): 100 attach/paint/destroy cycles leave `GR_GDIOBJECTS` flat.
- Handles are `isize`, a destroyed edit is detected with `is_window`.

## Safety rules (`// SAFETY:` per `unsafe` block)
`set_window_subclass`: the procedure is a `fn` item valid for the process lifetime and removes itself on `WM_NCDESTROY`; `def_subclass_proc`: called only from the subclass procedure with the parameters it received; `WM_NCCALCSIZE` pointer: "non-null, aligned, points to the `RECT` the system passed for this synchronous message"; `send_message` with `LB_ADDSTRING`: "pointer to a NUL-terminated UTF-16 buffer alive for the synchronous call"; the other `send_message` calls carry values only.

## Error mapping
| C# | Rust |
|---|---|
| `Attach` returns false | `false` |
| `catch (Exception)` in `Proc` | `pending_panic::guarded` (captured, resumed by the owner of the native call); the procedure then falls through to `def_subclass_proc` like the C# |
| `GetTextMetrics`/`GetDC` failure | `top_padding` = `0` |
| `ArgumentNullException(content)` | unrepresentable |
