## Semantics notes
1. **Pass 1 (one full read, `compute_latest_entries`).** For each parsed line in file order: if its `group_members` is `Some` and
   non-empty, `history[id] = (group_id, members)` (last such line wins, position of the first); then, unless
   `is_stale_reconcile_after_committed(line, latest[id])`, `latest[id] = line`. Both maps enumerate in FIRST-INSERTION order (C#
   `Dictionary` without removals): use the stub's `OrderedById`, never iterate a `HashMap`. A read error here is the ONLY `Err` of
   `reconcile_pending_operations`.
2. **Pass 2, downgrade guard (ADR 0003 "older builds"), per Id of `history` in order, each inside `catch_unwind`.** Skip when the latest
   line has non-empty members or is `Dismissed`. `restored` = latest + history's `group_id`/`group_members` (all other fields, incl.
   `timestamp_utc`, `error`, `error_code`, unchanged: the d-fixture keeps `PendingUnconfirmed` and 00:00:30). Latest `Prepared` ->
   `latest[id] = restored`, nothing appended here (pass 3 judges it with the members; it may still be after the cutoff and then nothing
   at all is written). Live -> skip. `Committed` and some member incomplete -> outcome = restored with `Failed`, clock timestamp,
   `error = SETTLED_BY_OLDER_BUILD_TEXT`, `error_code = None` (NOT `with_outcome`: no code, no catalog text). Otherwise outcome =
   restored (a pure member restore). Append only if the Id's effective latest line still EQUALS the latest seen in pass 1
   (`append_if_latest_is`, FA-01 fold); then update `latest[id]`; return the line only when its state changed (Committed -> Failed).
   Idempotent: the appended line has members, so the next run skips the Id (goldens run twice).
3. **Pass 3, per latest `Prepared` in Id order, each inside `catch_unwind`.** Skip when `prepared_before_utc` is `Some(c)` and
   `timestamp_utc.value >= c` (ticks, the Kind is ignored like C# `DateTime` compare). Live -> skip BEFORE any file check.
   Verdicts (`with_outcome`, journal clock, `Error`+`ErrorCode` only for Failed, English text):
   - group (non-empty members): Committed iff EVERY member completed (`all`, short-circuits like LINQ `All`); failure code
     `SourceStillExistsAfterRecovery` for Recycle, `PendingUnconfirmed` otherwise;
   - Recycle: `file_exists(source)` -> Failed `SourceStillExistsAfterRecovery`, else Committed;
   - Move/Copy: `source_exists = file_exists(source)` first, then `get_file_stat(destination)` only when `destination.is_some()`;
     recorded = `types::matches_moved_destination(stat, size, last_write_utc.value)`; Move = `!source_exists && recorded`, Copy = `recorded`.
   The outcome is appended through `append_if_still_pending`: the Id's RAW last line (no FA-01 here) must be `Prepared` and, checked
   AFTER the re-read, the Id must not be live. `Ok(true)` -> the line goes to the result; `Ok(false)` -> silently dropped (superseded).
4. **Member completion** (`is_group_member_completed`): Recycle not undo -> source gone; Recycle undo (`undo == Some(true)`) -> source stat
   with EXACT `length == size` (u64 vs i64: `i64::try_from`) and `last_write_utc == member.last_write_utc.value` (no 2 s tolerance, R15);
   Move/Copy -> destination stat only when `member.destination` is not null/empty/whitespace (`char::is_whitespace` over the text, like
   `string.IsNullOrWhiteSpace`), then `file_exists(source)`; the undo direction is already in the manifest (no swap).
5. **Failures never stop the others.** An `io::Error` from `append_if` (its re-read OR its append) -> diagnostics warn
   `"Journal reconcile: could not append outcome for {id}: {err}"`, entry left as is. A PANIC while judging -> `"Journal reconcile:
   skipped {id}: {panic_message}"`; while repairing -> `"Journal reconcile: skipped group repair of {id}: {panic_message}"`. Rust's
   `FileSystem::file_exists`/`get_file_stat` cannot fail, so the C# ArgumentException path is reachable only through a panicking
   file system (tests) or a bug: `catch_unwind(AssertUnwindSafe(..))` is the faithful port; never `unwrap()` on file-system results.
6. **Result order:** pass-2 lines (state changed only) first, then pass-3 lines. Startup filters `state == Failed` keeping that order.
7. **Startup (`run_with_cutoff`).** Reconcile inside `catch_unwind`; on success compaction runs on the same thread (C# "quiet moment")
   BEFORE the summary warn; then `"Startup journal reconcile: {n} pending operation(s), {f} failed."` only when `n > 0` (n counts
   Committed results too). Reconcile `Err`/panic -> `log.error("Startup journal reconcile failed", Some(err))`, no compaction, `vec![]`.
   Compaction messages (exact): `"Journal compacted: {before} -> {after} bytes."` (info), `"Journal compaction failed (journal
   unchanged): {error}"` (warn, `None` -> empty), `"Journal compaction skipped (Busy); journal unchanged."` / `(Changed)` (info);
   NotSupported/BelowThreshold/NotWorthIt log nothing; a panic in `try_compact` -> `log.error("Journal compaction failed", ..)` and
   the reconcile result is still returned. All startup messages go to the caller's `log` (`None` = silent); the per-entry reconcile
   warnings go to the journal's diagnostics log, never to `log`.
8. **`spawn`.** `clock.utc_now()` is read on the CALLING thread before the thread starts (the cutoff must be the moment startup
   began, not when the worker got scheduled). One `std::thread::Builder::new().name(RECOVERY_THREAD_NAME)`; spawn error -> log error,
   empty handle. No async runtime, no thread pool (R0003). The handle never blocks in `is_finished`.
9. **P03.** Nothing here touches Undo; there is deliberately no Undo parameter (the C# tests that assert "Undo stays empty" are about
   that absence).

## Traps checklist
- §7.1 Ids compare ORDINALLY (case-sensitive: `"ABC"` and `"abc"` are two operations); paths go through the file system (case-insensitive
  there). §7.3 `FileStat::length` is u64, sizes are i64: never `as`-cast. §7.5 timestamps: compare `JournalDateTime.value` ticks; an
  Unspecified-kind stamp (no `Z`) is compared by its raw ticks (golden `unspecified-kind-stamp-compares-raw-ticks`); new outcome
  timestamps are `JournalDateTime::utc(clock.utc_now())` (written with `Z`), while `restored` keeps the old stamp and kind.
  §7.6 the outcome line is W1-14 `to_line()` (property order, `Error` always written, optional members only when set): never build JSON
  by hand. §7.8 `destination: None` vs `Some("")`: `None` skips the stat; a member destination of `""`/`"  "` also skips it (whitespace
  rule), an entry-level blank destination is already `None` after parsing. §7.9 C# catches IO in `TryReconcileAppend` but EVERYTHING
  (except OOM) per entry: two distinct branches (io::Error -> "could not append outcome", panic -> "skipped"). §7.10 result order.
- INV applicability: INV-6 (below) and INV-10 are this unit's. INV-3/4/5 (action ordering, one action at a time, no stale
  catalog/undo writes) belong to W3-04/W3-05: reconcile runs before any action and touches neither catalog nor Undo (P03).
  INV-8 (shared read handles) is honoured by W3-01's reader (`open_read_shared`); this unit opens no file itself. INV-11
  (config) is unrelated.
- INV-6: never mark Failed what another writer committed meanwhile (re-read under the gate, raw last line), never judge a live Id or an
  Id stamped at/after the cutoff. INV-10: the diagnostics default (`FileLog`) is off and creates nothing.
- FA-01 has TWO readers with different rules: the snapshot and `append_if_latest_is` use the FA-01 fold (`effective_latest`);
  `append_if_still_pending` uses the RAW last line. Swapping them is a real bug (goldens `fa01-*` and
  `older-build-stale-reconcile-after-committed-still-repaired` pin both).
- The repair outcome for a Committed group with a missing member has `error_code = None` and the fixed English text: do not route it
  through `with_outcome`.
- A panic inside `append_if` while W3-01's gate is held must release the gate (W3-01's guard does it on unwind); do not hold any other
  lock across `catch_unwind`.
- Never use the real Recycle Bin (nothing here deletes; keep it that way in tests). No sleeps in tests: block with channels/Barrier.

## Open questions
1. **Split of OperationJournal.** Recommended (this contract): reconcile in W3-03 behind `ReconcileJournal` (W3-01 implements 3
   accessors + 3 primitives, keeps the public delegate). Pros: both units stay inside the size budget; the reconcile rules (where every
   INV-6 bug in C# history was) get their own Opus porter and mutation run; W3-01's porter only has to get `append_if` right. Cons: one
   trait with a single implementor; the two contracts must agree on `append_if` semantics (written down in the trait doc). Alternative A:
   leave the reconcile in W3-01 and W3-03 = only `startup_recovery.rs` (75 lines; then the downgrade tests and goldens move to W3-01, and
   W3-01 exceeds the budget). Alternative B: make `reconcile` a child module of `journal` (`journal/reconcile.rs`, `impl OperationJournal`
   with access to private fields): no trait, but W3-03 then depends on W3-01's private, not-yet-written helpers. The lead decides when
   merging the W3-01 and W3-03 contracts.
2. `run`/`spawn` take the concrete `OperationJournal` (C# does too; `ShellStartup`'s `JournalRecovery` hook is App wave). If the App
   wave wants a fake, it wraps `spawn` at its own seam; no trait is added here.
3. **pr-test-support (lead-owned) needs hooks** that several Wave 3 tests share: (a) `FsOp::Exists` (file_exists is not counted or
   faultable today); (b) `FakeFileSystem::set_hook(op, Arc<dyn Fn(&Path) + Send + Sync>)`, called at the START of the operation and
   BEFORE the internal lock (so a hook can block on a channel, append to the journal through another `OperationJournal`, delete the
   journal, or panic to emulate C#'s ArgumentException); (c) a way to fail only the Nth `open_append` (a hook returning
   `Option<io::Error>` covers it: `set_fault_hook(op, Fn(&Path) -> Option<io::Error>)`). Without them the test porter must write a full
   `FileSystem` wrapper (15 methods) in each test file. Recommended: add (a)-(c) in the contract PR.
4. PARITY F-14's text is outdated (see PARITY rows); the lead updates it with this unit.
5. **W3-01 refers to a W3-03 `StartupJournal` trait** (its module doc: "implements W3-03's `ReconcileJournal` / `StartupJournal`
   traits ... with `try_compact`"), and says W3-03 re-exports `JournalCompactionOutcome`. Neither exists here: `startup_recovery`
   takes the concrete `OperationJournal` (Open question 2) and imports the compaction types from `journal`. The lead either drops
   both remarks from W3-01's doc, or (if the App wave needs a fake journal for startup) adds a two-method trait
   (`reconcile_pending_operations`, `try_compact`) here and changes `run`/`spawn` to take it.
6. Test-file ownership vs W3-01: `JournalStartupRecoveryTests.Dismiss_ClearsErrorCode` and the non-reconcile tests of the shared files
   listed above are W3-01's; W3-01's contract should list them so nothing is ported twice or not at all.
