## Semantics and wrapper rules (C# is the spec; the conventions of D-W8B3-4 apply)
1. **IME.** `imm_associate_context(hwnd, 0)` returns the previous `HIMC` (`0` when the window had none or on failure); the shortcut box calls it once at setup and never restores. `imm_get_virtual_key(hwnd)` returns the virtual key of the key the IME is processing when `WM_KEYDOWN` carried `VK_PROCESSKEY`; `0` means "no key": the caller keeps `VK_PROCESSKEY` (C# `if (real != 0)`).
   Both are safe `pub fn`: the OS validates the handle; they must be called on the window's thread.
2. **Scroll bar.** `set_scroll_info(hwnd, bar, info, redraw)` copies `info`, sets `cbSize = 28`, calls `SetScrollInfo` and returns the current position; `bar` is `SB_VERT` for the window's own bar or `SB_CTL` for a scroll-bar control; `info.fMask` selects what is used (`SIF_RANGE | SIF_PAGE | SIF_POS`; `SIF_DISABLENOSCROLL` keeps a disabled bar visible; `SIF_TRACKPOS` is read-only). `get_scroll_info` sets `cbSize` and fills the
   fields chosen by `fMask`; `true` on success. `nTrackPos` is the live thumb position during a drag (the scroll pages read it on `SB_THUMBTRACK`). `get_key_state(vk)` returns `i16`: the high bit (a negative value) = key down, the low bit = toggle (C# comment: "high bit negative = pressed; used for Ctrl+Tab page switch").
3. **`set_parent(child, new_parent)`** returns the previous parent (`0` on failure). The Settings pages are template controls created inside a dialog and re-parented into a scrolling viewport window; the caller adjusts styles; the wrapper does not.
4. **DPI awareness.** `set_process_dpi_awareness_context(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)` is `Err(Win32Error(5))` (`ERROR_ACCESS_DENIED`) when the awareness was already set by the manifest or an earlier call; C# `TrySetPerMonitorV2()` returns that as `false` and the bootstrap re-checks with `are_dpi_awareness_contexts_equal(get_thread_dpi_awareness_context(), -4)`
   (11b). It must run before the first window of the process exists; later it has no effect. `are_dpi_awareness_contexts_equal` compares two contexts by meaning (a context returned by the OS may be a handle value that is not the `-4` constant yet equals it): never compare the integers with `==`.
5. **`is_iconic`** = `IsIconic`; **`set_foreground_window(hwnd)`** = `SetForegroundWindow`: returns `false` when Windows refuses (foreground lock, caller not the foreground process); that is not an error to report (the single-instance forwarder already tolerates it).
6. **`create_item_from_path(path)`**: `SHCreateItemFromParsingName(path, None)`; the path need not exist for the call to succeed when it is a valid parsing name, but a nonexistent file path gives `HRESULT_FROM_WIN32(ERROR_FILE_NOT_FOUND)` (0x80070002) or `ERROR_PATH_NOT_FOUND`; the result is `Err(Hresult)`. Needs COM initialised (STA).
7. **`create_file_open_dialog` / `create_file_save_dialog`**: `CoCreateInstance(CLSID_FileOpenDialog / CLSID_FileSaveDialog, None, CLSCTX_INPROC_SERVER)`; `Err(Hresult)` (`CO_E_NOTINITIALIZED` 0x800401F0 when COM is not initialised on the thread). The returned interface is a COM smart pointer: dropping it is `Release` (the C# `ComInterop.Release`). Use it on the thread that created it (STA).
   The C# call-order rules remain: **file types BEFORE `FOS_PICKFOLDERS`** (afterwards `SetFileTypes` gives `E_UNEXPECTED`; test comment), options are or-ed with the dialog's defaults (`GetOptions` may carry extra flags: compare `actual & wanted == wanted`).
8. **`IModalWindow::Show(owner)`** blocks until the dialog closes (own message loop); `HRESULT_ERROR_CANCELLED` (0x800704C7) = the user cancelled (not an error to show); any other failure is a real error. Not called by this unit's tests (W8-18).
9. **`create_empty_data_object()`**: `SHCreateDataObject(None, None, None)`; `SetData(&format, &medium, true)` transfers ownership of the `HGLOBAL` to the object; `GetData` returns a medium the caller releases with `release_stg_medium`. `QueryGetData` returns `S_OK` (0) when present, `S_FALSE`/`DV_E_FORMATETC` (-2147221404) otherwise (test: `!= 0`).
10. **`take_co_task_string(p)`**: `None` for a null pointer; otherwise reads UTF-16 up to the NUL (`PWSTR::to_string`, lossy), then `CoTaskMemFree(p)` **even when the text is invalid UTF-16** (the free is unconditional, like the C# `finally`). Calling it twice on one pointer is a double free (`# Safety`).
11. **`release_stg_medium(&mut medium)`**: `ReleaseStgMedium`; afterwards the handle inside `medium` is invalid and `pUnkForRelease` is released. Call once per `GetData` result.
12. **Drop-effect semantics for the later drop-target port (documented here because the type is here):** `DragEnter`/`DragOver`/`Drop` receive the effect by pointer and must write the answer there (`DROPEFFECT_COPY` when files are carried, `DROPEFFECT_NONE` otherwise); the point is `POINTL` **by value** in screen coordinates; the key state carries `MK_*` bits. C# test `TheVtableMarshalling_CarriesPointByValue_AndTheEffectByRef` is the guard; its Rust twin is the recorder test below.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (item 3, integers): `DV_E_FORMATETC` is `0x80040064` which does not fit `i32` as a literal; the C# `unchecked((int)0x80040064)` is `-2147221404`; `HRESULT_ERROR_CANCELLED` is `0x800704C7` = `-2147023673`. Compare `Hresult(hr)` values with `i32`, never with `0x8007_04C7` as `u32` after a signed cast.
- T2 (null vs empty): `take_co_task_string(null)` is `None`, an empty string is `Some("")`; the C# `TakeCoTaskString` has the same two outcomes (`null` and `""`).
- T3: `PWSTR`/`COMDLG_FILTERSPEC` strings must outlive the dialog's `Show` (C# comment: "kept alive until the dialog closes"): in Rust keep the `Vec<u16>` buffers in the struct that owns the dialog, not in a temporary.
- T4: STA. `IFileOpenDialog`, `IShellItem`, `IDataObject` created by `SHCreate*` are apartment-bound: use them on the creating thread; `CoInitializeEx(COINIT_APARTMENTTHREADED)` first (the test helper `run_sta` mirrors the C# one, including the 60 s join bound).
- T5: `SIGDN` and `DROPEFFECT` values with the high bit set are negative in `SIGDN(i32)` and `0x80000000` in `DROPEFFECT(u32)`: compare through the typed windows-rs constants, never through hand-copied integers of the wrong sign.
- T6: the process-wide DPI call is not undoable: the only test that calls it is alone in its own test executable (`win32_startup_dpi.rs`).
- T7: `get_key_state` for keys the user may be holding: tests use a key that nobody presses (`VK_OEM_CLEAR` 0xFE).
- T8: `release_stg_medium` on a medium whose `tymed` is `TYMED_NULL` is a no-op; on `TYMED_HGLOBAL` it frees the global; releasing a medium that was built by the caller with a static handle is undefined behaviour (`# Safety`).

## Safety rules (a `// SAFETY:` per `unsafe` block; COM calls through windows-rs interfaces are `unsafe` in 0.62 for most methods)
- Every COM method call: "the interface pointer is a live COM object owned by the smart pointer, used on its creating (STA) thread; the arguments are locals that outlive the call". Cite the method contract (`SetFileTypes`: the `COMDLG_FILTERSPEC` strings must outlive `Show`).
- `take_co_task_string`: "`p` was allocated by the shell with `CoTaskMemAlloc`, is NUL-terminated UTF-16, and nobody frees it before this call".
- `release_stg_medium`: "`medium` was filled by `IDataObject::GetData` and is released exactly once".
- `imm_*`, `set_scroll_info`, `get_scroll_info`: "pointer to a local `SCROLLINFO` with `cbSize` set".

## Open questions
1. **Where the Rust `IDropTarget` implementation lives.** Recommended: W8-14 (drop target) with `#[implement(IDropTarget)]`; this unit only tests the shape. Alternative: a shared `shell_native::DropTargetBase`. Not needed now.
2. **`create_item_from_path` for non-filesystem names.** Recommended: accept any parsing name like the C# helper (the folder picker passes real folders). Alternative: reject relative paths up front (`PathIsRelative`): the C# does not and the OS parses relative names against the current directory, which is a surprise; the callers (W8-18) pass absolute paths.
3. **Should `set_foreground_window` retry with the `AttachThreadInput` trick?** Recommended no (C# does not). Behaviour parity.
