- Semantics notes (C# is the spec; line references are to `RgbBgraResampler.cs`):
  1. **Path choice (`Resize`).** `target == source` on both axes -> `Convert`; else `(sw as f64 / tw as f64) > 2.0 || (sh as f64 / th as f64) > 2.0` -> `BoxAverage` for the WHOLE image (one axis above the threshold is enough, even when the other axis grows); else `Bilinear`. The comparison is strict: a ratio of exactly 2.0 is bilinear (tests `..ExactlyTwo..`). `select_path` is the same chain as a value.
  2. **Convert.** `pixel_count = rgb.len() / channels` (NOT `sw * sh`), per pixel `bgra = [b, g, r, 255]` with `g = rgb[s + (channels == 3) as usize]`, `b = rgb[s + 2 * (channels == 3) as usize]` (gray: all three read the single byte). The token is checked when `(pixel_index & 0x3FFFF) == 0`, which includes index 0: a cancelled token fails before writing anything, for any size >= 1 pixel (`Resize_SameSizeWithACancelledToken_ThrowsEvenForASinglePixel`); an empty `rgb` never checks.
  3. **BoxAverage.** For target `(x, y)`: `y0 = (y * sh) / th`, `y1 = max(y0 + 1, ((y + 1) * sh) / th)`, same for x (all `i64`, truncating division, the `* sh` must not be done in `i32`). Sums of the footprint per channel in `i64`; `count = (y1 - y0) * (x1 - x0)`; `byte = ((sum + count / 2) / count) as u8` (round HALF UP, integer). Alpha 255. The token is checked ONCE PER TARGET ROW, after the row is written (so a cancelled token on a target with >= 1 row writes row 0 and then fails; with 0 rows nothing fails).
  4. **Bilinear (the trap-rich one).** Per row `source_y = clamp((y as f64 + 0.5) * sh as f64 / th as f64 - 0.5, 0.0, sh as f64 - 1.0)` (evaluation order `((y + 0.5) * sh) / th - 0.5`, no FMA, no reassociation), `y0 = source_y as usize` (truncation of a non-negative value), `y1 = min(y0 + 1, sh - 1)`, `fy = source_y - y0 as f64`; same for x. Per channel: `top = tl + (tr - tl) as f64 * fx`, `bottom = bl + (br - bl) as f64 * fx` where the differences are INTEGER subtractions of the bytes (`i32`) converted afterwards; `value = top + (bottom - top) * fy`; result `clamp(value.round_ties_even() as i32, 0, 255) as u8`. **`Math.Round(double)` is round-half-to-EVEN** (default `MidpointRounding.ToEven`): Rust `f64::round()` rounds half away from zero and gives different bytes (test `Resize_ReductionOfExactlyTwoOnOneAxis_StaysBilinear`: `(2 + 3) / 2 = 2.5 -> 2` in bilinear but `3` in the area average). Output channel order B, G, R from channels `blue_channel`, `green_channel`, `0`. Token checked once per target row after the row (as BoxAverage).
  5. **Gray (channels = 1).** The green and blue offsets/channels collapse to 0, so gray and RGB-with-equal-channels give identical output on all three paths (test `..ProduceIdenticalOutput`). `channels` other than 1 and 3 -> `InvalidData("LibRaw returned an unsupported processed image format.")` raised FIRST in `resize` and in `validate_source_length` (before any size check: `source-unsupported-channels-before-bad-size`), but in `resize_to_buffer` only after the size guard and the allocation (the buffer is then freed).
  6. **`validate_source_length`.** See the stub doc. The C# multiplications are `(long)width * height * channels` in an unchecked context. Two consequences the golden pins: (a) product of two `int` fits `i64`, so only the `* channels` can wrap, and only for dimensions near `i32::MAX` squared; (b) when it wraps NEGATIVE the checks `data_size < rgb_length` and `rgb_length > i32::MAX` are both false and the function RETURNS `rgb_length as i32` (garbage, e.g. `source-intmax-squared-c3-wraps-unchecked`). Port with `wrapping_mul` and `as i32` truncation, do not "fix" it (see open question 1). Error text for every failure after the channel check: `LibRaw returned an invalid processed image buffer length.`
  7. **`validate_target_length`.** Same wrap on `* 4` (`target-intmax-squared-wraps-unchecked` returns 4 in C#). Limit is `.NET Array.MaxLength = 0x7FFFFFC7`, not `i32::MAX`: `536870897 x 1` (2147483588 bytes) is accepted, `536870898 x 1` rejected. Message `The decoded RAW image is too large to hold in memory at {width}x{height}.` (the dimensions as signed decimals).
  8. **`resize_to_buffer`.** Order: (1) any of the four sizes `<= 0` -> `InvalidData("Invalid RAW resize dimensions {sw}x{sh} -> {tw}x{th}.")`, no allocation, channels not looked at (`rtb-guard-before-channels-zero-target`); (2) `BgraBuffer::new(tw, th)`; (3) `resize` into its slice; (4) on ANY error drop the buffer (`live_count` back to the starting value). It does NOT call `validate_target_length` or `validate_source_length` (the decoder does).
  9. **`BgraBuffer::new`.** `stride = tw.checked_mul(4)?` then `length = stride.checked_mul(th)?` (both `OverflowException` in C#; `Overflow` here), THEN `PixelBuffer::allocate(tw, th, Bgr32)` whose own range errors (`width < 1`, `height < 1`, `width > i32::MAX / 4`) surface as `ResampleError::PixelBuffer(..)`. Consequence: the overflow check comes first, so `-536870912 x -1` is `Overflow` (stride `-2^31`, length `+2^31` overflows) while `-1 x -1` is `ArgumentOutOfRange` (golden `buffer-new-*`). A `BgraBuffer` never holds more than `i32::MAX` bytes, so `as_mut_slice`'s "too large" branch (`try_get_span_mut` -> `None`) is unreachable but kept for parity.
  10. **Ownership.** `take_pixels` moves the `PixelBuffer` out (no copy, same `id`); afterwards `pointer()` is null, `as_mut_slice`/`take_pixels` are `Err(Disposed)`, `dispose` and `Drop` free nothing. `dispose` is idempotent. `pointer()` is also null after `dispose`. Alignment is `PixelBuffer`'s 64 bytes. Writing through `as_mut_slice` goes through the safe slice view of `PixelBuffer::try_get_span_mut`: this file has NO `unsafe`.
- "Different" (documented divergences, all in argument validation that C# leaves to the .NET runtime):
  - `resize` returns `InvalidData` instead of panicking when any of the four sizes is `<= 0`, when `rgb.len() < sw * sh * channels` (box and bilinear paths), or when `bgra.len() < tw * th * 4` (all paths; for Convert, `pixel_count * 4` with `pixel_count = rgb.len() / channels`). C# throws `IndexOutOfRangeException` / `ArgumentOutOfRangeException` / `DivideByZeroException` there. Production callers always validate first, so this is only reachable from tests; the check is done up front in `i64` arithmetic, before the first write, so a failing call leaves `bgra` untouched (C# may have written some rows). The oracle does not exercise these cases.
  - The Rust function takes `&CancelToken` and returns `ResampleError::Canceled`; there is no `OperationCanceledException` subtype distinction (`TaskCanceledException` etc.).
  - `BgraBuffer::pointer()` is a `*const u8` (null) instead of `IntPtr.Zero`; reading through it is the caller's `unsafe`.
- Traps checklist (docs/MULTI-AGENT-PLAN.md §7): 1 (no strings here), 3 (all sizes are `i32`, products in `i64`; `u8` casts after explicit clamp), 10 (stable output: pure function of the inputs; no threads, no hashing). Pixel-specific: (a) round-half-even vs half-up (semantics 3/4); (b) strict `> 2.0`; (c) box sums in `i64`, indices in `usize` computed from `i64` products (a 100 MP source is `300_000_000` bytes: `y * sw * channels` overflows `i32`); (d) the unchecked wrap in both validators; (e) cancellation points differ per path (Convert before pixel 0, others after each row); (f) `Convert` uses `rgb.len() / channels`, not `sw * sh`; (g) no `INV-*` id applies (the `PixelBuffer::id` of INV-1 is minted by `PixelBuffer::allocate`, one per `BgraBuffer`). No panics on any input: all index math is bounds-checked up front per the "Different" notes and `expect`/`unwrap` do not appear in non-test code.
- Performance: a 100 MP target (400 MB) is written once, straight into the native buffer, never into a `Vec`; do not add an intermediate `Vec<u8>` copy (C# note in the summary of `ResizeToBuffer`). Process whole rows with slices (`chunks_exact_mut(4 * tw)`) and hoist the per-row `y0/y1/fy`; the golden hashes make any such refactor safe. No threads (C# has none; the caller is already on a worker).

## Open questions
1. **Unchecked wrap in `ValidateSourceLength` / `ValidateTargetLength`** (semantics 6/7). C# returns garbage for `int.MaxValue x int.MaxValue` instead of throwing. Unreachable in production (LibRaw's header carries `ushort` dimensions, max 65535) but the golden pins it, so the stub documents `wrapping_mul`. If the lead prefers the "fixed" behaviour (always `InvalidData`), the four affected golden cases (`source-intmax-squared-c3-wraps-unchecked`, `source-intmax-squared-c1-wraps-unchecked`, `target-intmax-squared-wraps-unchecked`, `target-2147483646x2147483646-wraps`) would be listed as DIVERGENCE with a `rust_skip` flag; recommendation: keep parity (cost zero).
2. **Argument-validation divergence** ("Different" above): an alternative is to make `resize` `-> ()` and `debug_assert!`/panic like a slice index on bad input. Rejected for the stub because the project rule is "never panic on malformed input" and the cost is one up-front check.
3. **Visibility**: C# is `internal`; Rust items are `pub` so the integration test can reach them. The lead decides at wiring whether the module is `#[doc(hidden)]`.
4. **`select_path` is a Rust-only addition** (a pure function the unit tests use to pin the dispatch table); the C# has the chain inline. It does not change behaviour; delete it from the stub only if the lead objects to extra API.
5. **Native parity tests** (`LibRawPixelBufferNativeParityTests.Decode_CodecPath_EqualsWpfPath_ByteForByte`) need `libraw.dll` and the WPF path (gone, P-06); they belong to W5-16b, which compares against the golden `libraw-decode` instead.
