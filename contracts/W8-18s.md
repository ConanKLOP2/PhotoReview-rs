## Semantics (C# is the spec)
1. **Driver order of effects.** `run_click` / `quick_check_click`: read the controls (selected indices, folder text, limit text) BEFORE the presenter borrow; `with_field_context(|ctx| presenter.borrow_mut().run_selected(..))` with a `DialogView`; release; `flush_view_effects` (grid rebuild); then `dispatch_step`. The presenter's own order inside `start` (`set_running(true)`, rows cleared + `refresh_rows`, `set_progress(0)`) is W8-10i's.
2. **`dispatch_step`**: the three jobs run on the injected runner under the thread names `benchmark-scan`, `benchmark-profile`, `benchmark-save`. A profile job sends one `Progress` event per engine progress message BEFORE its `Profile` event (same inbox, FIFO), so the presenter sees progress first, as in the C#. Jobs cannot unwind (W8-10i catches), and `inbox.send` never panics. A runner that cannot start a thread logs and drops the job (`ThreadRunner`): the run then hangs in the "running" state until Cancel; the window stays usable (documented, not handled).
3. **`drain_inbox`** (`WM_BENCHMARK_WAKE`): `inbox.drain()`, then for each event in order: `with_field_context` + `presenter.try_borrow_mut()` + `apply_event` with a fresh `DialogView`; release; `dispatch_step(next)`. After the last event: `flush_view_effects`. A stale `Progress` (wrong run id, not running) is dropped by the presenter itself (`on_progress`, INV-9 style guard, W8-10i). The wake message carries no data; two wakes for one event are harmless (the second finds an empty inbox).
4. **`DialogView`** applies `set_status` / `set_progress` / `set_running` at once, records `refresh_rows`, and never reads the presenter (D-W8B5-504). `set_status` re-runs the layout only when the needed status height changes (`status_line_height` vs `layout.status_height`). `set_running` follows `enabled_flags` order and the focus rescue of `focus_target`.
5. **Commands** as the doc comment of `command`; `OPEN_REPORT_ID` / `OPEN_FOLDER_ID` call `presenter.open_report(view)` / `open_result_folder(view)` with a `DialogView` (the view's `open_in_explorer` runs `options.open_in_explorer`). Esc while idle returns `false` so the base closes the window (`end_modal(ID_CANCEL)`; for a modeless window that destroys it).
6. **Browse**: `Path::new(&current).is_dir()` replaces `Directory.Exists` (an empty or invalid text is not a directory, so the initial folder is `None`). The answer replaces the box text only when it is non-empty.
7. **Row colours** (`row_colors`): the `lParam` of the row is its index in `presenter.rows()`; `presenter.try_borrow()`; in range -> `from_key(row_color_key(row.is_best, row.status() == BenchmarkResultStatus::Fail, displayed_row))`; out of range or borrowed -> the alternating colour. `from_key` returning `None` falls back to `DialogColors::window()`. The text colour is always `DialogColors::text()`. The custom draw itself is `ListViewControl::custom_draw` (18g).
8. **Profile list text**: `profile_list_text` uses the ambient localizer at paint time, so a language switch needs only the `invalidate_rect` of 18r. The base answer for any other list or an index out of range is `ListItemText { text: ListBoxControl::text_at(dialog.item(id), index), badge: None }`.
9. **Header click**: `column_click_sub_item(header)` reads `NMLISTVIEW.iSubItem` through a typed struct pointer under a SAFETY comment and a compile-time `offset_of == 28` assertion (D-W8B5-311); a null `lParam` gives `None` and the notification is not handled.
10. **Exceptions.** The C# `Observe` logged a faulted presenter task. In Rust nothing can fault: the presenter returns steps, the jobs catch panics (W8-10i), a hook panic is captured by the dialog procedure (`pending_panic`, the dialog closes as Cancel).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- 3 (arithmetic): `status_line_height` and the client-width maths use wrapping `i32`; `fraction` is `f64` 0..1 (the presenter guarantees it).
- 8 (None vs empty): a pick-folder answer `Some("")` does NOT replace the box (C# `string.IsNullOrEmpty`); `profile_list_text` `None` is "not mine", not "empty".
- 9 (exception to Result): the C# `Observe` / `ContinueWith` has no twin; scan / save errors are presenter statuses.
- 10 (order): events are applied strictly in arrival order; the progress of profile N precedes its outcome; the next profile job is dispatched only after the previous outcome was applied.
- T-threads (D-W8-2, R0003): jobs and the wake function are the only things on other threads; everything the presenter or a control touches stays on the UI thread; the `CompletionInbox` and the `AtomicIsize` are the only shared state; no `Rc` crosses into a job.
- T-re-entrancy (D-W8B4I-1 / D-W8B5-504): the `DialogView` calls `SetWindowText` / `EnableWindow` / `SetFocus` while the presenter is mutably borrowed: those re-enter `on_command` / `on_notify` / `layout_controls`, which must not borrow the presenter for writing (they use `try_borrow`/nothing). A `set_focus` can fire `EN_SETFOCUS`: `command` ignores non-click notifications.
- T-leaks: a closed window leaves jobs running on workers; they hold only the inbox, the session and clones of `Arc`s (no window, no `Rc`); the session is disposed on the worker on every path.
- T-panic (R0003): no `unwrap`/`expect` outside tests; `post_wake` is the one new `unsafe` call (SAFETY: no pointer in the message); `custom_draw` pointer cast and `NMLISTVIEW` read have SAFETY comments and null checks; `post_wake` ignores an error (the window is gone).
