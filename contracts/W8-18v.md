## Semantics (C# is the spec)
1. **`retry`** in the order of its doc. Steps 1-3 touch no worker and no state (a declined question changes NOTHING: no `begin_retry`, no delegate call, no `retry_runs`). Step 4 under one `borrow_mut`: `begin_retry(&entry, &mut |b| pending.push(b))`; the closure only pushes (D-W8B5-603); after the borrow `for b in pending { apply_busy(content, dialog, b) }`. `begin_retry` sets `is_retrying = true` BEFORE calling the callback, so `apply_busy(true)` -> `update_buttons` reads `states` with Retry, Clear selected and Clear all all `false`. Step 5: `retry_runs += 1`; the job closure is `Send + 'static`: it owns the `RecoveryRetryJob`, a clone of the `CompletionInbox`, `entry_id` and the `closed` flag.
2. **`on_retry_finished`** in the order of its doc; the `finish_retry` borrow is ONE `borrow_mut` whose callbacks only record. `apply_busy(false)` runs before any message box (the wait cursor ends before the notice, C# parity: `finally` of `ExecuteRetryAsync`). The notice text is `RecoveryWindowPresenter::describe_retry(&result, texts.localizer())`.
3. **Late results** (D-W8B5-613): a result that finishes after `on_closed` never reaches `on_retry_finished` (the worker checks `closed` and logs; `on_closed` logs leftovers). Both log lines are the C# texts. A result that arrives while the window is merely `!is_alive` (closed between the pump and the handler) takes the `Ok` / `Err` branches above.
4. **`apply_busy`**: `restore.busy.set(busy)`; `dialog.hwnd() == 0` -> return; `actions::update_buttons`; `set_cursor(load_system_cursor(cursor_id(busy)))` (`CURSOR_ARROW` / `CURSOR_WAIT` are `i32`, the type `load_system_cursor` takes; an `Err` of the load is ignored; a shared system cursor, nothing to free). `wait_cursor()` of the content (`is_busy`) makes the base class answer `WM_SETCURSOR` with the wait cursor over the whole dialog while busy (18k).
5. **`dismiss`** in the order of its doc. `rows` are presenter indices captured by the caller (`selected_rows` or `0..rows.len()`); `presenter.dismiss(&rows)` ignores an index that is no longer valid (10g). `Hwnd == 0` (not `is_alive`) decides between `Stop` and `Refresh`: C# parity (line 690). `Refresh`: `list::refresh_entries`; then, when `skipped > 0`, `notify(RECOVERY_DISMISS_STALE_TITLE, localizer.format(RECOVERY_DISMISS_STALE_MESSAGE, count), warning = false)`.
6. **Closing.** While busy: `on_cancel` returns `true` (Esc and the Close button are refused), `can_close_by_user` is `false` (X, Alt+F4 and `WM_CLOSE` are refused, 18k); `RecoveryDialog::close()` and a quitting shell always close (`NativeDialog::close`), then `on_closed` runs (18t).
7. **INV-5 (the reason this slice exists).** The question text of Retry is `retry_confirm_text` (it already warns about permanent deletion according to the setting read NOW); a declined or unanswered question (`IDNO`, `IDCANCEL`, the box closed with X) is not a yes; the delegate is called exactly once per confirmed click; Clear only ever calls the dismiss delegate (a journal write), never a file operation. The data-safety tests assert the file tree and the journal text before and after.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (borrows): as 18u T1; the two presenter calls of this slice (`begin_retry`, `finish_retry`) take callbacks that run inside `&mut self`: they must not touch the dialog, the list or the presenter again (a `RefCell` double borrow panics on the UI thread, R0003). `dismiss` runs the journal write inside `presenter.dismiss` on the UI thread (C# parity): it must not call back into the dialog either (the production closure only calls `OperationJournal::dismiss`).
- T2 (order): question -> delegate -> notice -> close/recheck is the C# order and the tests pin it with a recorder; never fold the question after `begin_retry`.
- T3 (two message boxes): `confirm` and `notify` are modal nested loops; between them the dialog may receive paint, timers and the wake message: re-validate with `is_alive` after every box (steps marked in the doc).
- T4 (worker closure): it must not capture `Rc`, `RefCell`, the `NativeDialog` or the content; `Send` is checked by the compiler on `BackgroundRunner::run`.
- T5 (busy flag vs presenter flag): `restore.busy` mirrors `is_retrying` through `apply_busy`; if a test needs "locked" it reads the buttons (`is_enabled`), not the flag.
- T6 (`Err` of `begin_retry`): impossible after `can_start_retry`; shown as a rejected-retry warning, never `unwrap`.
- T7 (cursor): `set_cursor` only changes the cursor now; the wait cursor over the dialog is the base class's `WM_SETCURSOR` (`wait_cursor`).
- T8 (read-only of files): nothing in `restore.rs` or `dismiss.rs` calls `std::fs`.
- T9 (the late-result race): the worker checks `closed` BEFORE `inbox.send`, but `on_closed` (UI thread) may drain the inbox between that check and the send, losing the log line. So after the `send` the worker checks `closed` AGAIN and, when set, drains the inbox itself (`CompletionInbox::drain` is `Mutex`-guarded, callable from any thread) and logs every `Retry` it finds with the same texts; `Check` leftovers are dropped. The file work itself is never affected.
- T10 (C# parity, not a bug): between the Retry question and `begin_retry` there is no `is_alive` check (C# has none), and `dismiss` runs the presenter call after a question the window may not have survived (`Hwnd == 0` then ends the flow quietly). A product change would be a lead decision; the contract keeps parity.

## Open questions (recommended default in bold)
1. **Where does the production `RetryFn` get `confirmed_finish_cancelled`?** **`true`** (the dialog's own question is the confirmation, as `RealRetry`/`ShowRecovery` in C#); the closure lives in the production `SecondaryWindowDialogs` (proposed W8-18w, folded into W8-17c; D-W8B5-421), not in W8-18o (18o only holds the `SecondaryWindowDialogs` seam trait).
2. **Should `retry` guard against a second click while a retry runs?** **No extra guard**: `can_start_retry` is `false` while `is_retrying` and the button is disabled (C# parity).
3. **Cancel token of the retry job** (C# `RetryMoveOrCopyAsync` has none from the dialog): **`CancelToken::new()` never cancelled** (closing mid-retry never cancels the file work: INV-5, a half-finished move is worse than a late one).
