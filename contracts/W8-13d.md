## Semantics (C# is the spec)
1. **Queues** (`UiQueues`, C# 292-308 and 267-290). Four FIFO levels indexed by `UiPriority as usize` (Send 0, Normal 1, Render 2, Background 3). `dequeue_high` scans levels 0, 1, 2 in that order and takes the front of the first non-empty one. `high_count` = items in levels 0-2; a Background enqueue does not change it. `dequeue_background` returns `None` while `high_count > 0` (C# 196).
2. **Wake protocol** (C# 314-330, 177). `request_wake`: `if !wake_flag.try_set() { return }` (a wake is already on its way); `post_message(hwnd, WAKE_MESSAGE, 0, 0)`: `Ok` -> `wake_messages_posted += 1`; `Err(e)` -> `wake_flag.clear()` (the next enqueue retries; the loop still sees the work through `has_high_priority_work`) and `log.warn("Win32UiDispatcher: PostMessage(WM_APP+1) failed (error {code})")`
   with the code in invariant decimal. `run_high_priority_batch` clears the flag BEFORE it reads the queues (so an item enqueued during the drain either is seen by this drain or posts a fresh wake). Result: at most one `WM_APP + 1` waits in the thread's queue (10 000-entry limit) however many items are posted.
3. **Enqueue** (C# 267-290): under the mutex, shut down -> return `false` (the item is dropped: for `post` silently, for `invoke` its sender is dropped so the `UiCompletion` resolves as `UiActionPanicked { message: "UI scheduler dropped the action" }`, the existing `UiCompletion::wait` rule); else push, then `request_wake()` OUTSIDE the mutex.
4. **Drain** (`run_high_priority_batch`, C# 174-187, UI thread only: `verify_access`): `started = Instant::now()`; loop `dequeue_high()` -> `execute(item)`; stop when the queue is empty or `started.elapsed() >= 50 ms` after an item ran (the item that crosses the slice still ran). Items posted during the drain are drained in the same pass (drain to empty).
5. **Background** (`try_run_background`, C# 190-204): one item, only if no high work waits; the CALLER guarantees the thread's message queue is empty (`MessageLoop` checks `is_message_pending`). `on_wake_message` (C# 210-223, also reached from a foreign modal loop through the window procedure): drain high; then `if !has_high && has_background && !MessageLoop::is_message_pending()` run ONE background item;
   then `if has_high || (ran_background && has_background)` -> `request_wake()` (so the queue keeps running inside a modal loop one item per wake message).
6. **Execute** (C# 332-358): run the action under `catch_unwind(AssertUnwindSafe)`. Item with a completion (`invoke`): send `Ok(())` or `Err(UiActionPanicked { message: panic_message(payload) })`; NO log (test). Item without (`post`): `log.error("Win32UiDispatcher: a posted UI action threw; the message loop keeps running", Some(&UiActionPanicked { message }))`, the loop continues (D-W8B3H-10: the dispatcher is the one place that catches a panic on the UI thread, by explicit C# contract
   and test; R0003's "the UI thread does not catch panics" is about uncontrolled code, and the same rule is already in `ImmediateUiScheduler::invoke`). A `send` error (nobody waits any more) is ignored.
7. **Shutdown** (`Dispose`, C# 226-257; UI thread; idempotent): under the mutex set `shut_down`, `drain_all()` the queues (dropping the items resolves every pending `invoke` as dropped, and drops pending `post`s unrun), zero the high count; `destroy_window(hwnd)` (a failure is ignored); clear the thread's `current` if it is this dispatcher. After it `post`/`invoke` are dropped (never hang), `has_*_work` are false, `is_shut_down` is true.
   No `Drop` implementation (D-W8B3H-8): the composition root shuts down explicitly; a dispatcher dropped without it leaks its window until the thread ends (documented, acceptable: it lives for the whole run).
8. **Construction** (C# 55-73): `current` already set on this thread -> `InvalidOperation { message: "This thread already has a Win32UiDispatcher." }` BEFORE anything else; `ensure_class_registered()` (process-wide once, only a success is remembered; `register_class_ex` with `lpfnWndProc = Some(dispatcher_wnd_proc)`, `hInstance = get_module_handle()`, class name `CLASS_NAME`;
   `Win32 "RegisterClassEx (dispatcher window) failed"`); `create_window_ex(0, CLASS_NAME, "", 0, 0, 0, 0, 0, HWND_MESSAGE, 0, instance, 0)` (`Win32 "CreateWindowEx (message-only dispatcher window) failed"`); set `current`. The thread id is `std::thread::current().id()`.
9. **`UiScheduler`/`UiDispatcher` mapping**: `post` = `post_with_priority(.., Normal)`; `invoke` = `invoke_with_priority(.., Normal)`; `check_access` = `current thread id == ui thread id`; `invoke_with_priority`: `UiCompletion::channel()`, enqueue with the sender, return the completion. `from_current_thread()` returns `None` after shutdown.
10. **Window procedure** (`dispatcher_wnd_proc`): body under `pending_panic::guarded(LRESULT(0), ..)`; `message == WAKE_MESSAGE` -> `from_current_thread()` then `on_wake_message()`, result 0; else `DefWindowProcW`. A panic is captured and resumed by `MessageLoop` after `DispatchMessage` (or by the foreign loop's owner, which has no rethrow: documented limitation, the panic then surfaces at the next `MessageLoop` pump).

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (UI-thread affinity): `run_high_priority_batch`, `try_run_background`, `on_wake_message`, `shutdown`, `verify_access`-guarded members must be called on the UI thread; `post`, `invoke`, `has_*`, `check_access`, `wake_messages_posted` from any thread. The struct is `Send + Sync` so the compiler does not enforce this: the run-time check is `verify_access` (a wrong-thread call is `Err`/panic in the UI-only members).
- T2 (posted-message wake): never `SendMessage` to the dispatcher window from a worker (it would block on the UI thread and can deadlock with `invoke().wait()`); always `PostMessage`. The message-only window ignores everything else.
- T3 (re-entrancy): `execute` runs user code with NO lock held (the mutex guard is dropped before the call); an action may `post` (re-lock) or call `shutdown`. `UiQueues` is touched only under the mutex.
- T4 (flag order): clear the wake flag BEFORE reading the queues. A mutant that clears it after loses a wake (an item enqueued between the read and the clear never wakes anyone): the F test uses a hook between the two steps.
- T5 (WM_QUIT): the dispatcher never touches the quit state; `Quit_EndsTheLoopWithItsExitCode` goes through `MessageLoop::quit`.
- T6 (FFI panic guard): `dispatcher_wnd_proc` must not unwind; and `execute` already catches action panics, so only `on_wake_message`'s own bugs reach the guard.
- T7: `shutdown` drops items outside the mutex (their destructors may post). Collect with `drain_all` under the lock, drop after releasing it.
- T8: `BATCH_SLICE_MS` is checked after each item, with `Instant` (monotonic); a clock-seam is not needed, the test uses a 60 ms action to cross the slice and asserts the next item runs in the next wake, not the same drain.
- T9: `UiPriority` values are `Send=0 .. Background=3` (pr_core); never reorder, `as usize` indexing depends on it.
- T10: `invoke` on the UI thread itself followed by `wait()` deadlocks (documented in `UiCompletion::wait`): no code in this unit calls `wait` on the UI thread.

## Safety rules (`// SAFETY:` per block)
`register_class_ex` (the class name `Vec<u16>` outlives the call; `lpfnWndProc` is our `dispatcher_wnd_proc`), `create_window_ex` (parent `HWND_MESSAGE`, `param` 0: the procedure expects nothing), `post_message` (`WAKE_MESSAGE` with `wparam = lparam = 0`: no pointer is delivered), `def_window_proc` (message parameters forwarded unchanged from the OS call), and `dispatcher_wnd_proc` itself is `unsafe extern "system" fn` whose contract is "called by the OS only".

## Error mapping
| C# | Rust |
|---|---|
| `InvalidOperationException("This thread already has a Win32UiDispatcher.")` | `HostError::InvalidOperation` |
| `Win32Exception(.., "RegisterClassEx (dispatcher window) failed")`, `"CreateWindowEx (message-only dispatcher window) failed"` | `HostError::Win32 { operation, error }` |
| `InvalidOperationException("This Win32UiDispatcher member must be called on its UI thread.")` | `HostError::InvalidOperation` |
| `ArgumentOutOfRangeException` (priority), `ArgumentNullException` | unrepresentable |
| action exception: `Post` -> logged; `InvokeAsync` -> faulted `Task` | panic caught: `Log::error` / `Err(UiActionPanicked)` |
| canceled `Task` after `Dispose` | `UiCompletion` resolves as `UiActionPanicked { message: "UI scheduler dropped the action" }` |

## Open questions (recommended default in bold)
1. `Win32UiDispatcher` is `Clone` and shut down explicitly (no `Drop`): **yes**; alternative: an owner type with `Drop` plus a cheap handle type (more API, same behaviour).
2. Catching action panics in `post`: **yes, log and continue (C# test and contract)**; alternative: let it unwind to the top (R0003 purity) and change the C# test's Rust twin to expect a crash. Needs a `Different` row only if the lead picks the alternative.
3. Window class prefix `PhotoReviewRs.`: **yes** (R0002 consistency; a window class is process-local so there is no clash, the prefix only keeps tooling that looks windows up by class name apart).
4. A `UiDispatcher::post_with_priority(.., Background)` replaces `YieldAsync`: **yes** (W8-07h O5).
5. `verify_access` failing in `UiThread`-only members: **return `Err`** where the signature has a `Result`, else `debug_assert` + no-op; never panic in release.
