- Semantics notes:
  1. **Clock.** C# `Func<long>` over `Stopwatch.GetTimestamp`, converted with `Stopwatch.Frequency`. Rust: the injected function returns ticks of
     `TICKS_PER_SECOND = 10_000_000` (100 ns, the Windows `Stopwatch.Frequency`; at merge replace the local const by `pr_core::time::TICKS_PER_SECOND`).
     `new()` builds the source from `std::time::Instant` (elapsed nanos / 100). Elapsed ms = `(now - last_ticks) as f64 * 1000.0 / TICKS_PER_SECOND as f64`
     (multiply BEFORE divide, same as C#). The pr-core `Clock` trait is wall-clock UTC and must NOT be used (it can jump); this is monotonic.
  2. **`record(index)`.** `index < 0` returns immediately (no state change, no clock read). `index == last_index` returns (idempotent, so the
     post-present kick never counts as a key; the initial `last_index = -1` never equals a non-negative index).
     Else read `now` once, and when `last_index >= 0`: `delta = index - last_index`; if `delta.abs() == 1` then `direction = delta` (RV-I09: only a
     single step sets it; a jump keeps the previous value, initial `+1`); `elapsed_ms` as above; if `delta.abs() == 1 && elapsed_ms <= 500.0`
     (INCLUSIVE) then `interval_ms = if samples == 0 { elapsed_ms } else { interval_ms + 0.3 * (elapsed_ms - interval_ms) }`, `samples += 1`; else
     `interval_ms = 0.0, samples = 0`. Finally `last_index = index; last_ticks = now`. The first interval is taken as is (not blended with 0).
  3. **`get_lead(decode_ms)`.** `interval = active_interval_ms()`; `if interval <= 0.0 || decode_ms <= 0.0 { 0 }`; `ratio = decode_ms / interval`;
     `if ratio <= 1.0 { 0 } else { min(24, ceil(ratio) as i32) }`. Exactly `decode == interval` gives 0; `101/100` gives 2.
  4. **`get_viewer_start_delay(decode_ms)`.** `interval = active_interval_ms()`; `if interval <= 0.0 || decode_ms <= interval { zero }`; else
     `min(100.0, interval * 1.5)` milliseconds as a `Duration` (see open question 1 for the rounding of the conversion). Zero outside a burst.
  5. **`active_interval_ms`** (caller holds the lock): `0` when `samples < 2 || interval_ms <= 0.0`; else `since_last_ms = (now - last_ticks)*1000.0/freq`
     with a NEW clock read; `0` when `since_last_ms > max(2.0 * interval_ms, 150.0)` (the window edge is INCLUSIVE: exactly equal is still active),
     else `interval_ms`. `get_lead` / `get_viewer_start_delay` read the clock once each; `direction` never reads it.
  6. **Thread safety.** One `Mutex<State>`; no lock is held across a call out. Recover from a poisoned lock with `PoisonError::into_inner` (the
     state is plain numbers, so it is always consistent): the preload path must never panic. The timestamp function is called while the lock is held,
     as in C#, so it must not call back into the `NavigationPace`.
- Traps checklist (docs/MULTI-AGENT-PLAN.md §7): item 3 (`(int)Math.Ceiling` of a double: NaN and huge values), item 4 (float order, `ceil`),
  item 11 (default arguments: `timestamp = null`). Specific traps:
  1. **Inclusive vs exclusive.** `<= 500` (step), `<= 1` (ratio), `<= interval` (delay), `> max(...)` (window). Each has a golden pair around it
     (`step-exactly-500ms-is-still-burst` / `step-501ms-restarts`, `decode-equals-interval-...`, `active-window-*`).
  2. **EWMA is `i + a*(e - i)`**, not `a*e + (1-a)*i`: the two differ in the last bit. Keep the C# form.
  3. **NaN `decode_ms`.** `NaN <= 0` is false, `ratio = NaN`, `NaN <= 1` false, `(int)ceil(NaN)` is 0 in .NET (9, saturating) and `NaN as i32` is 0 in
     Rust, so `get_lead(NaN) == 0` (golden `decode-nan-and-infinity`). `get_lead(+inf)` is `24` (`inf as i32` saturates to `i32::MAX`, then min 24).
     For the delay, `NaN <= interval` is false so a NaN decode DOES get the delay; do not "validate" the input.
  4. **A negative step size on a fake clock** (`clock-goes-backwards`): elapsed is negative, `<= 500` holds, the EWMA gets a negative sample and
     `interval_ms <= 0` makes the burst inactive. Do not clamp elapsed to zero.
  5. **`i32` arithmetic.** `index - last_index` cannot overflow because both are non-negative; `delta.abs()` is safe. Do not use `i64` to "be safe"
     only to then compare `== 1` differently; behaviour is identical but keep `i32`.
  6. **Same-tick steps.** Two steps in the same tick give elapsed 0: the first sample is `0.0`, `interval_ms <= 0` keeps the burst inactive even
     with `samples == 2` (golden `zero-interval-same-tick-steps`).
  7. **`TimeSpan.FromMilliseconds` rounding** (open question 1) is the only place the Rust value could differ in the last tick.

## Open questions
1. **`TimeSpan.FromMilliseconds(double)` rounding.** .NET historically rounded the argument to whole milliseconds; newer runtimes keep sub-ms ticks.
   The C# tests compare against `TimeSpan.FromMilliseconds(33 * 1.5)` computed by the same function, so they never expose it. The oracle therefore
   reports both `ms` and `ticks` for `delay`; the porter must make `get_viewer_start_delay` reproduce the golden `ticks` exactly (either
   `Duration::from_secs_f64(ms / 1000.0)` or a round-to-ms first, whichever the golden shows) and note it in the code. Consumers (the scheduler) only
   use it as a `sleep` delay, so a 0.5 ms difference is harmless, but the golden is whole-value.
2. **Return type of the delay** `std::time::Duration` (recommended: non-negative by construction, never negative in C# either). No `pr_core` duration
   type exists.
3. **`new()` default clock** uses `Instant` since construction (starts near 0). C# `Stopwatch.GetTimestamp` is large; nothing depends on the absolute
   value because only differences are used, and `last_ticks` starts at 0 only matters when `last_index == -1` (never read then).
