- Semantics notes (every line is a C# behaviour. No INV id is owned here; the I-13 rule "container errors never fall back to WPF" (enforced by W5-12c and W4-12b) relies on this reader so that a
  hostile file is `Err(invalid data)` or a smaller result, never a panic):
  1. **CanRead.** `extension` equals `.rw2` with `OrdinalIgnoreCase` (use `pr_core::text::eq_ignore_case`: `.RW2`, `.Rw2` accepted; `.rw2 `, ` .rw2`, `rw2`, `.rw22`,
     `..rw2`, `""` rejected), `first_64_bytes.len() >= 4`, bytes `49 49 55 00`. Only the first 4 bytes matter (`49495500ffffffff` is accepted). `MM`+`00 55` and
     `II`+`2A 00` are rejected. Golden: 41 `can-read` cases (every byte xor 0x40/0x01/0xFF, 15 extension spellings, heads of length 0..64).
  2. **Header.** `source.length() < 16` => invalid data "File too short for RW2 container." (15 bytes with a perfect header is still too short; 16 is enough). Then
     `source.read(0, 16)` (an error of the source propagates), `pr_imaging::tiff::try_read_header` on those bytes; failure, `!little_endian` or `magic != 0x55`
     => invalid data "Invalid RW2 header." (`II` + `0x0055` only: `MM` + `00 55` is big-endian and rejected, `II` + `55 01` has magic 0x0155 and is rejected; one
     matching letter (`IM`, `MI`) fails inside `try_read_header`). The text of both errors is pinned by the golden (`too-short`, `invalid-header`).
     A source that hands back fewer bytes than asked (the fuzz test's tracking source returns `[]` out of range) must not panic: a slice shorter than 8 bytes is an invalid header.
  3. **IFD0.** `read_ifd_entries(source, ifd0_offset (u32 -> i64), true)` (W5-02a: offset `< 8` or `> length - 2` gives no entries, count clamped to 4096 and to the entries that fit,
     next-IFD pointer ignored here). Only IFD0 is ever read: tags in a second IFD are ignored (golden `*-in-second-ifd-ignored`); the next pointer is discarded (`hostile-next-ifd-points-to-itself`).
     The FIRST entry with a tag wins (`TryGetEntry`); a duplicate with a different value is never consulted, even when the first is unusable (`orientation-duplicate-first-invalid-second-not-consulted`).
  4. **Tag reads happen first and always, in this order:** `0x0002`, `0x0003`, `0x0004`, `0x0005`, `0x0006`, `0x0007` (each `read_tag_value`), then `0x0112`. A source error while reading an
     out-of-line value propagates even if the value would not have been used (golden `budget-*`). `read_tag_value` (W5-02a) returns `Option<i64>`: types BYTE(1), SHORT(3), LONG(4), IFD(13), SSHORT(8) and
     SLONG(9) are readable (8 and 9 can be NEGATIVE), UNDEFINED(7), ASCII(2), RATIONAL(5), type 0 and unknown types give `None`.
  5. **Orientation** (`ifd0_orientation`): `Some(v)` only for `1 <= v <= 8`; 0, 9, 255, 256, 0xFFFF, negative SSHORT, a LONG `0x80000006` all give `None` (then the JPEG fallback applies, step 8).
  6. **Extent** (`image_extent(start, end, tag)`, used for width with `(0x0005 left, 0x0007 right, 0x0002)` and for height with `(0x0004 top, 0x0006 bottom, 0x0003)`):
     if `start` is present with `start >= 0` AND `end` is present with `end > start` AND `end <= i32::MAX` then `end - start` (always fits an `i32`; C# `checked`); else if the size tag is present with
     `0 < tag <= i32::MAX` then the tag; else `0`. Consequences the golden pins: equal borders or reversed borders fall back to the tag; a border pair with `end > i32::MAX` falls back
     (and gives 0 when there is no tag); a NEGATIVE left/top (SSHORT/SLONG) falls back; `end == i32::MAX` with `start == 0` is accepted (`i32::MAX`); a tag of `0xFFFFFFFF` or `0x80000000` gives 0; width and
     height are decided independently (width from borders and height from the tag is a valid mix). The generic `ImageWidth/ImageLength` tags 0x0100/0x0101 are NOT used by this reader.
  7. **JpgFromRaw** (`0x002E`, first entry only): requires `entry.count > 4` (u32 compare: count 0..=4 is no preview, count 5 is one if it fits), `offset = entry.value_or_offset as i64`,
     `length = entry.count as i64`, `is_range_in_file(offset, length, source.length())` (offset `> 0`, length `> 0`, `offset <= file_length - length`: offset 0 is never valid, `offset + length == file_length` is valid,
     one more is not, `count = 0xFFFFFFFF` is not) AND `source.read(offset, 2)` equals `FF D8`. The entry TYPE is ignored (types 0, 1, 2, 3, 4, 5, 7, 99 all work). Failing any
     check silently lists no preview and no exif block (no error); a source error of the `read(offset, 2)` propagates. A preview is then
     `EmbeddedPreview { index: 0, offset, length, kind: Jpeg, width: 0, height: 0, color_space: Unknown, header_resolved: false }` (sizes and colour space are resolved later by W5-11b).
     The exif block is `ExifBlock { offset, length: exif_block_length(length) = min(length, DEFAULT_EXIF_BLOCK_BYTES = 131 072), is_tiff_header: false, ifd_is_exif: false }` (the block starts at
     the JPEG, `RawExif` parses its APP1). Exactly one preview / one exif block or none.
  8. **Orientation fallback.** Only when step 5 gave `None` AND a preview was listed: `n = exif_read_length(length, offset, file_length) = min(min(length, 131 072), file_length - offset)`; if `n > 0`
     `try_read_orientation_from_jpeg(source.read(offset, n)?)` (this read is NOT made when IFD0 has a usable orientation: golden `budget-ifd0-orientation-skips-exif-read-one-block` vs
     `budget-exif-window-needs-two-blocks-one-allowed-throws`). The result `orientation = ifd0 ?? jpeg ?? 1`. An EXIF segment cut by the 128 KiB window is whatever `try_read_orientation_from_jpeg` makes of the
     truncated bytes (golden `fallback-exif-segment-ends-at-131072/131073/131079/131080/131081`).
  9. **Result.** `RawContainerInfo { format: Rw2, sensor_width, sensor_height, orientation, previews, exif_blocks }`. A 16-byte file with an empty IFD gives `(0, 0, 1, [], [])`. The reader never
     uses `token` (C# never observes `ct`).
- Traps checklist (docs/MULTI-AGENT-PLAN.md §7): 3 (arithmetic: `end - start` and every offset/length in `i64`; `file_length - length` cannot underflow because `length > 0` is checked first and both are

6. The golden pins `bytes_read` (which 64 KiB blocks the reader touches). This is the "minimize disk reads" priority made testable; if the lead considers it too brittle for a reader refactor it can be dropped from the Rust
