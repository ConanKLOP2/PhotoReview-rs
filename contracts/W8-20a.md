## Semantics (C# is the spec)
1. **`main_entry`** (C# `Main`, lines 14-15): see the doc of the stub; the four steps are the whole function. The apartment is entered BEFORE `args_os` is read and before any other code: nothing in the process may initialise COM first. `StaApartment::enter()` returning `Err` is logged (`AppLog::global().error_forced("COM apartment", &error)`) and the run goes on; a missing apartment only costs drag and drop. The guard is dropped explicitly after `run_main` returns and before `std::process::exit` (`exit` does not run destructors of locals).
2. **`args_from_os` / `run_main`**: the CLR's `args` is the command line WITHOUT the program name, split by the standard Windows rules; Rust's `std::env::args_os()` uses the same splitting (`CommandLineToArgvW` compatible) and includes the program name first, so `skip(1)`. Conversion is lossy (`to_string_lossy().into_owned()`): a path with an unpaired surrogate cannot be named by a .NET `string` either (it arrives as U+FFFD). Nothing else is done to the arguments: `ShellLaunch::parse` (17a) owns the `--smoke` flag, the file-or-folder choice and the working-directory rule.
3. **`production_run`**: `ShellStartup::run(args, ShellStartupOptions::default())`. The default options read the three `PHOTOREVIEW_RS_*` variables (17d) once. Nothing else is configured here (no hooks: `install_process_hooks` defaults to true, `start_perf_listener` to true, `activate` to true, `warm_graphics` from the environment).
4. **Exit code**: `run` returns `0` (normal close, second instance), `1` (`EXIT_STARTUP_FAILED`: the start-up failed, the loop faulted 50 times), `7` (`EXIT_SMOKE_TIMEOUT`), or the forced code; `main_entry` passes it to `std::process::exit` unchanged (`i32`; Windows treats it as `u32`, so `-1` is 0xFFFFFFFF as it is for a .NET `int` return).
5. **The subsystem**: `windows_subsystem = "windows"` removes the console: nothing printed after `main` starts is visible. Every failure path of this unit therefore writes through `AppLog::error_forced` (a file under the data root, flushed), never `println!`/`eprintln!` (except the non-Windows stub).
6. **Manifest and icon** (`build.rs` + `res_writer`): per the docs of the two stubs. Format facts the porter needs (all little endian, MSDN "Resource File Formats"): a `.res` is a concatenation of resources; each is `{ DataSize u32, HeaderSize u32, TYPE, NAME, pad to 4, DataVersion u32, MemoryFlags u16, LanguageId u16, Version u32, Characteristics u32 }` followed by `DataSize` bytes and zero padding to the next 4-byte boundary; `TYPE`/`NAME` are `0xFFFF` followed by a `u16` id (all ids used here are numeric); `HeaderSize` counts the header only (so 32 for numeric type and name); the first resource of a file is the empty one (`DataSize 0`, `HeaderSize 32`, type `0xFFFF 0x0000`, name `0xFFFF 0x0000`, zeros). An `.ico` file is `ICONDIR { reserved u16 = 0, type u16 = 1, count u16 }` then `count` x `ICONDIRENTRY { width u8, height u8, colorCount u8, reserved u8, planes u16, bitCount u16, bytesInRes u32, imageOffset u32 }`; the `RT_ICON` data of image `i` is the `bytesInRes` bytes at `imageOffset` (a BMP DIB or a PNG, copied as is); the `RT_GROUP_ICON` data is `GRPICONDIR { reserved 0, type 1, count }` + `count` x `GRPICONDIRENTRY` (same fields as `ICONDIRENTRY` but the last `u32` offset is replaced by a `u16` id, 14 bytes per entry). `build.rs` passes the file with `cargo:rustc-link-arg-bin=PhotoReviewRs=<path>`: `link.exe` runs `cvtres`. If the linker reports `CVT1100` (duplicate `MANIFEST` resource) because it also generated a manifest, add `cargo:rustc-link-arg-bin=PhotoReviewRs=/MANIFEST:NO` and record it in the PR; the `exe_resources` tests decide. `cargo:rerun-if-changed` names the DIRECTORY `../../assets` (a missing file path would re-run the script on every build).
7. **Process tests** (`exe_process.rs`): the child is the REAL exe built by cargo for this test run. Because `CARGO_BIN_EXE_PhotoReviewRs` is set only for integration tests of the package that owns the binary, the tests live in `pr-shell` (they do). Waiting for "the first image was drawn": the child writes a perf CSV under `PHOTOREVIEW_RS_PERF_TRACE` (the event names `RenderedFrame` and `Assign` are the C# ones; the porter checks them against `pr_core::diagnostics::perf` and the CSV row format `...,<name>,...` of `perf_csv`); the test cannot be told when the file grows, so it uses the bounded tick loop of the previous section (`loop { recv_timeout(200 ms) on the watcher channel; count events; stop at >= n or at the 60 s deadline }`). A test never touches the user's data: every path is under its `TempRoot`; every child is killed (`Child::kill`, then `wait`) in a guard `Drop` if still alive.
8. **STA apartment**: see the stub doc. Tests: a spawned thread gets a guard (`enter()` is `Ok`); two nested guards on one thread both drop without panic; a thread that first called `pr_platform_win::wic::interop::ensure_com_initialized()` (MTA) gets `Err(ChangedMode)`; the `Display` texts are the two in the stub doc.

## Traps checklist (docs/MULTI-AGENT-PLAN.md section 7)
- T1 (COM apartment): C# `[STAThread]` is silent; Rust has no such attribute. Anything that touches COM before `StaApartment::enter()` on the main thread (WIC, Explorer COM) would make the thread MTA and break `RegisterDragDrop` and the Shell dialogs. `main_entry` has no code before the `enter()` call except `fn main` itself.
- T2 (no console): `windows_subsystem = "windows"` means a panic message on stderr is lost; the panic hook installed by `ShellStartup::run` (D-W8B6-25) writes the forced log. A panic BEFORE the hook (inside `args_from_os`, `StaApartment::enter`) is impossible by construction (no indexing, no `unwrap`); keep it so.
- T3 (unwind): `catch_unwind` in `ShellStartup::run` (D-W8B6-25) and `catch_step` need `panic = "unwind"`. `Cargo.toml` must never set `panic = "abort"` for any profile of this workspace. The PR checks `[profile.*]` by eye and says so.
- T4 (resources only on the exe): `cargo:rustc-link-arg` would also reach the test executables and `r0001-spike`; `cargo:rustc-link-arg-bin=PhotoReviewRs=..` reaches only the real exe. A test executable with a manifest would change the behaviour of every native test of the crate (comctl32 v6 is wanted there, but through `ActivationScope`, D-W8B3-8).
- T5 (build script robustness): no icon asset yet must not fail the build (warning + no icon); a bad `.ico` fails it with the `ResError` text. The build script reads `../pr-platform-win/src/win32/shell.manifest` by a path relative to `CARGO_MANIFEST_DIR` (build scripts may; tests may not, AGENTS.md).
- T6 (exit code width): `ExitCode::from(u8)` would truncate 256 to 0 (a success!). Use `std::process::exit(i32)`.
- T7 (R0002): the exe name `PhotoReviewRs.exe`, the manifest identity `PhotoReviewRs` and every env var of the tests use the Rust prefix; a process test must never set or read a C# variable (`PHOTOREVIEW_DATA_ROOT`) or touch `%LOCALAPPDATA%\PhotoReview`.
- T8 (process tests and the user's machine): the first process test of this crate that starts the real exe is the first test in the repository that runs the production composition. Each child has its own instance prefix, data root and WARP, and is killed on drop; a test that cannot kill its child fails loudly, never leaves it.
- T9 (smoke exit): `--smoke` with an image path exits 0 right after the first frame that has the image; with no path, after the first frame; the timeout is 30 s (`DEFAULT_SMOKE_TIMEOUT`); the process test bounds the wait at 60 s.
- T10 (assets): `assets/PhotoReviewRs.ico` is synced, never hand-copied; until it exists `exe_carries_the_application_icon_group` fails with the message "run tools/sync-from-csharp.ps1" (that is the correct red state, not a reason to weaken the test).

## Safety rules (`// SAFETY:` per `unsafe` block)
`unsafe` appears only in `pr-platform-win`: `apartment.rs` (`CoInitializeEx`, `CoUninitialize`: no pointers, balanced on the same thread), `exe_resources.rs` (`LoadLibraryExW` with a NUL-terminated UTF-16 copy of the path that outlives the call, `FindResourceW`/`LoadResource`/`SizeofResource`/`LockResource` on the module handle owned by the struct, the locked data is copied before `FreeLibrary`; `FreeLibrary` once in `Drop`), `ui_driver.rs` (`PostMessageW` with integer parameters only; `SendMessageTimeoutW` (`WM_GETICON`, `SMTO_ABORTIFHUNG`, 5 s) from the TEST thread, never from the UI thread; `ClientToScreen` on a `POINT` local; `EnumWindows` with a callback that receives `&mut` state through the `LPARAM` and does not outlive the call; `GetWindowThreadProcessId`, `IsWindowVisible`, `GetWindow(GW_OWNER)`). `pr-shell` (`entry.rs`, `build.rs`, `res_writer.rs`, all tests) contains no `unsafe`.

## Error mapping
| C# | Rust |
|---|---|
| `Main` returns `int` | `main_entry` -> `std::process::exit(i32)` |
| `[STAThread]` | `StaApartment::enter()`; failure logged, run continues |
| unhandled exception in `Main` | panic hook (17e) logs forced, process ends with 101 (`Different`, `X-exe-panic-exit`) |
| `ApplicationManifest` missing | the `exe_resources` tests fail |
| `ApplicationIcon` missing | warning at build, `exe_carries_the_application_icon_group` fails |
| `ShellStartup.Run` throws before the loop | impossible: `run` returns `EXIT_STARTUP_FAILED` (17e semantics 1 step 4) |
