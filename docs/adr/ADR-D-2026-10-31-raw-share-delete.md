## DV-22 RAW full decode: shared read into memory, then `libraw_open_buffer` (lane `fix-raw-share-delete`, INV-8)

- Context: INV-8 says a file under review must stay deletable and movable. `libraw_open_wfile` opens the file without `FILE_SHARE_DELETE` and keeps the handle until `libraw_close`, so while a RAW full decode runs, renaming or deleting that very file fails with sharing violation (`ERROR_SHARING_VIOLATION`, 32). Measured twice: with Python ctypes (`FIX-IMAGING-CACHE-2026-10-31.md` M4) and through the Rust `LibRawDecoder` (`native_path_open_blocks_rename_while_libraw_decodes`).
- C#: `PhotoReview.Imaging.LibRaw/LibRawDecoder.cs` `DecodeCore` calls `OpenFile` = `libraw_open_wfile` (long-path retry) when the request has no `Bytes`; RAW is never pre-read (`DecodeFromSource`). Same hole.
- Rust: `pr_libraw::decoder::read_file_shared` reads the whole file once through `PhysicalFileSystem::open_read_shared` (`FILE_SHARE_READ | WRITE | DELETE`, sequential scan; the C# `FileShare.ReadWrite | Delete` rule), closes the handle, and `LibRawDecoder::decode_core` calls `libraw_open_buffer` on the bytes (the session keeps them until after `libraw_close`). It is enabled by `LibRawDecoder::with_shared_file_read()`, called at the three production composition sites in `pr-shell` (`composition/decoders.rs`, `factories.rs`, `registry.rs`). `LibRawDecoder::new` keeps the C# path so the oracle and golden tests still describe C#. Failure mapping is the old one: every read failure becomes `LIBRAW_IO_ERROR` (same long-path retry, same text `LibRaw could not open RAW file: ...`, so the fallback chain classifies it the same way), an allocation or headroom failure becomes `LIBRAW_UNSUFFICIENT_MEMORY` ("Not enough memory to decode this RAW image."), cancel is checked before every 4 MiB chunk and wins over the error code. A request that already carries `bytes` is untouched.
- Reason: INV-8, with no change to any file, config or journal format.
- Cost, memory: the file size (25-100 MB for RAW) is resident for the length of the decode, plus one transient copy while the `Vec` becomes the shared `Arc<[u8]>`; the read is refused up front when `2 x length` does not fit `total_available - load` (the same `has_headroom` rule as `EnsureMemoryHeadroom`). Full decodes are serialised by the gate, so this is one file at a time (plus queued waiters that have not read yet). The admission estimate runs after the read and reads the memory probe then, so the buffer is already subtracted from the available memory; the estimate formula is unchanged.
- Cost, I/O and speed: still one read of the file, sequential and shared (INV-1 "read once" holds; the disk bytes equal what LibRaw read before); the read now happens up front, so the first decode work starts after the whole file is in memory (on a slow disk or share this moves the latency before `opened`; the previous path did the same reads on demand). The OS file cache is not bypassed.
- Hash and fingerprint (INV-1): decode does not hash or fingerprint; the cache key still comes from the earlier `stat`. The race "file replaced between `stat` and read" is the same as before (the decode result is still verified and cached by the existing `verify` step).
- Behaviour check: `native_shared_file_read_decodes_the_same_pixels_as_the_path_open` compares BGRA bytes, size, `downscaled`, `original_*` and orientation of the path open and the shared read on seven synthetic DNGs (plain, preview, subifd, swap, orient6, orient3, pair) with an unbounded box and a 64x64 box with the pinned `libraw.dll`: 14 of 14 identical. `native_shared_file_read_reports_the_same_errors_as_the_path_open`: same kind and text for a junk file and a missing file.
- Remaining risk: (1) not run on real camera RAW; `libraw_open_buffer` could differ from `libraw_open_wfile` for a vendor format that wants a sidecar or reads outside the main stream; run the corpus tests (`decoder_native`, `PHOTOREVIEW_RAW_CORPUS_DIR`) with `with_shared_file_read` before treating it as proven. (2) `read_info` and `read_jpeg_thumbnail` still use `libraw_open_wfile`: they hold the file only for the short header or thumbnail read, not for a decode; a delete during that instant can still fail. Converting them would read the whole file for a few KB, so it was not done. (3) A file larger than half the free memory cannot be decoded (clear "Not enough memory" instead of the old streaming decode that could succeed); with 32 GB machines this is not reachable by real RAW.
- Undo: remove the three `.with_shared_file_read()` calls (the decoder returns to `libraw_open_wfile`; nothing else depends on the flag), or revert the PR. No data migration.
- Tests: `crates/pr-libraw/tests/raw_share_delete.rs` (11 always-run tests with fakes and temp files: multi-chunk read, empty file, missing file, cancel before and between chunks, headroom boundary, `open_buffer` instead of `open_wfile`, same error text, memory error, cancel; 4 `#[ignore]` native tests with `libraw.dll` and python: baseline rename blocked (32), rename at `opened` and delete at `unpacked` succeed with the shared read, pixel equality, error equality). Report: `docs/reviews/FIX-RAW-SHARE-DELETE-2026-10-31.md`.
