# D9 implementation: FrameLog writes on a writer thread (P-301)

Date: 2026-11-03. Branch `feat/framelog-writer-thread`. Owner decision P-301: move the FrameLog writes off the UI path to a
dedicated writer thread fed by a bounded channel, so measuring does not bias the frame time. Deviates from C#
`StreamWriter` with `AutoFlush = true`.

## What changed

`crates/pr-platform-win/src/shell_viewing/frame_log.rs` (the decision text says `host/main_window/frame_log.rs`; the file is in
`shell_viewing/`, the frame loop only calls `frame_log.record(..)` at `host/main_window/frame.rs:320`, unchanged).

- `FrameLog::open` still opens the file on the caller thread (same `FileShare.Read` mode, same open errors), then moves the
  handle to a thread named `frame-log-writer` through `open_with_sink(sink, ticks_per_second, capacity)`.
- `record` does the gap arithmetic (state stays on the caller) and `try_send`s four numbers into a `sync_channel` of 1024
  records. It never blocks. A full queue drops the new record and increments an atomic counter (`dropped()`); the count is written
  once to stderr when the log closes. The writer formats the line and does one unbuffered `write_all` per line (CRLF, format
  unchanged, goldens unchanged).
- `close` / `Drop` drop the sender, the writer drains what is queued and ends, `close` joins it: no queued record is lost at
  shutdown and the file is released before `close` returns (keep-warm dispose test and the FileShare tests still hold). Idempotent.
- `flush()` is the new deterministic sync point (a `Flush` message answered by the writer); it returns at once when the log is off.
- Panic in the writer: the loop runs under `catch_unwind`; the thread marks the log failed and ends. A write error does the same
  (existing behaviour: the log switches off). The next `record` sees the flag and closes. Neither reaches the caller.
- Thread spawn failure leaves the log off (like a write error).

## Deviation from C# and proposed PARITY / ADR wording

C# writes each line synchronously with `AutoFlush = true`; Rust writes it on a writer thread. Line format, file mode and
close/dispose semantics are the same; only the timing of the write differs (a reader sees a line after the writer ran, or after
`flush`/`close`), and under extreme backpressure records may be dropped and counted.

PARITY `Different` row wording: "FrameLog (P-301): the line is written by a writer thread through a bounded queue (1024) instead
of synchronously on the UI path (C# AutoFlush); a full queue drops the new record and counts it (reported once at close); close
drains and joins; a writer panic or write error switches the log off."

ADR text: "Context: the C# FrameLog writes on the UI path with AutoFlush, so the measurement adds file-write time to the frame it measures.
Decision (P-301, owner 2026-11-03): the Rust FrameLog hands records to a writer thread over a bounded channel. record never blocks and
never grows memory: when full it drops the new record and counts it. Close drains and joins so nothing is lost at shutdown. Consequence:
a tool reading the file while the app runs may lag the UI by the queue; the format contract with the stall tooling is unchanged."
