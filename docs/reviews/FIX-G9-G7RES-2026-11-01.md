## G1 (modal holds the borrow): assessment only, no code

- Difficulty: **high**. Today `host/main_window/lifecycle.rs:326-348`, `shell_input/main_window.rs:705-718` and `shell_menus/main_window.rs:335-345` already degrade (borrow released before `apply_changes`, `try_borrow_mut` drops a command while busy, `lifecycle.rs:341` queues open). What remains is design: a command that runs a modal (nested message loop) keeps `&mut` main-window state for the whole loop, so every re-entrant message (paint, size, close, timer) either hits `try_borrow_mut` and is dropped silently or, where `borrow_mut` is used, panics.
- Suggested fix, in order of cost: (1) state split: keep only a few small `Cell`/`RefCell` fields the window procedure needs while a modal runs (busy flag, pending close, pending resize) outside the big `RefCell`, so re-entrant messages record intent instead of being dropped; (2) run modal commands as "take what you need under a short borrow, release, run the modal, re-borrow to apply the result" (the pattern of `lifecycle.rs:326-337`), enforced by one helper `run_modal(|| ..)` that asserts no borrow is held (debug assert) ; (3) after the modal returns, replay the recorded intents once. Tests: a fake dialog host whose callback calls paint/pump/`on_closing`: no panic, a dropped command leaves a visible state; un-ignore `closed_disposes_the_bars_once_and_unsubscribes` (`tests/host_main_window_frame.rs:507`) when it can run. Not code-verified in this lane.
