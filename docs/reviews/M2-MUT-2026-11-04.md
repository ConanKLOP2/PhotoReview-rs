| `:344:19` `\|\| -> &&` in `math_max` | **equivalent** through the public API. `math_max` is private and only `intersect` calls it. With `&&` a one-sided NaN falls through to `b`: if `b` is NaN the result is NaN as before; if only `a` is NaN, `a` is `a.x` or `a.y`, and then `a.x + a.width` (resp. y) is NaN too, so `right` (resp. `bottom`) is NaN and `right > x` is false: the default rect either way. |
| `:361:10` `< -> <=` in `math_min` | **equivalent**. It differs only for equal operands: equal non-zero values return the same value; `+0` vs `-0` returns `+0` instead of `-0`, and `intersect` only uses `right - x` with `right > x`, where the sign of a zero `right` does not change the width. |
| `:430:31` `< -> <=` in `is_unit` | **equivalent (unreachable)**. `\|\|v\| - 1\|` for a double `v` near 1 is an exact multiple of 2^-52 (or 2^-53 below 1); `1e-6` as a double has a full 53-bit mantissa (the 1e-6 = 2^-20 * 1.048576 mantissa is not dyadic), so the difference can never equal it bit for bit. |
| `:479:18` `< -> <=` in `try_snap_pixel_exact` (`det.abs() < EPSILON`) | **open**. Needs a device linear part whose f64 determinant is exactly `1e-6` (nearest double) while both diagonal products are unit after the destination/source scale; that is a contrived two-matrix search, not a behaviour anyone relies on. Not killed. Proposal text only: if the owner wants it closed, add a test with a searched f32 matrix pair (`m11 * m22 - m12 * m21 == 1e-6_f64`), which needs no production change. |
