# G29 evidence: preview cache read allocation order and I/O OOM (2026-11-03)

Source: `invariants-storage.md` M3, BACKLOG G29, W4-08b (`crates/pr-imaging/src/cache/preview_file.rs`), caller W4-14c. Code reading plus the existing unit tests; nothing here changed production code.

## Allocation before the check: already closed on master
- Commit a61cb3a (#474, ST-IMAGING-INV M1-M3) changed `read` (preview_file.rs ~l.347-353): `file.metadata().len()` goes through `check_entry_file_len` BEFORE any allocation. A file longer than `max_entry_file_len()` (24 + 2 + max EXIF block + `i32::MAX`) is `InvalidData("Preview cache entry payload is implausibly large.")`, the C# text. The buffer comes from `try_entry_buffer` (`try_reserve_exact`), so a failed allocation is `PreviewCacheError::OutOfMemory` (kept entry, `is_cache_entry_failure() == false`), not an abort.
- Existing tests in the same file (`mod tests`): `entry_file_longer_than_the_format_allows_is_invalid_data_before_any_allocation` (limit ok; limit+1, u32::MAX+1, u64::MAX rejected, no file) and `entry_buffer_that_cannot_be_allocated_is_out_of_memory_not_an_abort` (`usize::MAX`). Pixel-codec OOM: `tests/cache_preview_file.rs` `to_pixels_/from_pixels_out_of_memory_is_not_a_cache_entry_failure`.
- C# order (`PreviewCacheFile.Read`): stream-wise header, EXIF, then `payloadLength > int.MaxValue` rejected before `ArrayPool.Rent`. Rust now decides from the file length alone, before reading; same verdict and text, earlier. The review's "bad magic + huge declared length is InvalidData after the prefix" cannot differ in outcome: both are `InvalidData`, only the message differs (size message vs magic message) for a file above the cap.

## Still open (small, not C# observable)
- `file.read_to_end(&mut bytes)?` uses `From<io::Error>`, so an `io::ErrorKind::OutOfMemory` returned by the read itself becomes `PreviewCacheError::Io`, which IS a cache-entry failure (entry deleted, source decoded). Only the write path maps it (preview_file.rs ~l.476). C# `FileStream.Read` surfaces such an OS failure as `IOException`, which is also a cache-entry failure, so the current Rust behaviour is C#-equal. Mapping to `OutOfMemory` would be a behaviour change; see P-150 below.
- No test seam exists for the read (it opens a real file), and a real file cannot produce this error without OS fault injection. A test pinning it would need production changes, so none was added.

## Conclusion
Group G29 is mostly stale. Remaining: the read-time `ErrorKind::OutOfMemory` classification, an owner decision (P-150).
