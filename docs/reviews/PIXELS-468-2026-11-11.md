# PIXELS-468 (2026-11-11): remove the equivalent mutant `y * step_y` -> `y / step_y` in `copy_transposed`

Result: removed by refactor, bit-identical, not slower.

## Change
`crates/pr-imaging/src/pixels.rs` `copy_transposed`: the table now carries `rows_descend: bool` (false for orientations 5, 6; true for 7, 8)
instead of `step_y` (+1 / -1). The per-row source base is `origin - y` or `origin + y`, computed once per row (one predictable, loop-invariant
branch per row, none per pixel). The per-pixel index is `row_base + x * step_x`. No multiplication or division by a +/-1 step remains.

## Domain
`copy_transposed` is private; its only caller is `apply_orientation`, for `exif_orientation` 5..=8 (others return earlier or go to `copy_rows`).
So `(origin, step_x, step_y)` takes exactly the four table rows; `y` is `0..src.width` (`u32`).

## Proof
- `crates/pr-imaging/tests/pixels_row_base_diff.rs`: through `apply_orientation`, every orientation 5..=8 and every source size 1..=70 x 1..=70
  (all edge classes of the 32 pixel tile) plus 130x65, 65x130, 97x1, 1x97, 257x33, 33x257, 200x200, compared with the OLD formula
  `origin + x*step_x + y*step_y` copied as a reference fn. Source pixels carry their own linear index, so any offset error shows.
- Hand mutation `origin - y` -> `origin + y` (descending rows): the test fails (panic at pixels.rs:477), reverted.
- `mut3_pixels_step_proof.rs` stays (its closed-formula test is still valid; its ignored `y*step == y/step` test is now historical).
