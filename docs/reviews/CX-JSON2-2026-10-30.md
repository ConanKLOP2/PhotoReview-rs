## Survivor dispositions

- Writer `1687:34`, `< -> <=`: equivalent. This sign selection runs only
  in the scientific-notation branch, reached when exponent <= -5 or >= 17.
  The sole changed case, exponent == 0, is unreachable there. Both conditions
  select the same exponent sign for every reachable value.
- Error `1129:9`, return `Default::default()`: compile-unviable, rustc E0277,
  because `SettingsJsonError` has no `Default` implementation. This is a
  compiler verdict, not an infrastructure failure.
- Parser `1189:13`, `1210:13`, `1346:13`, `1426:9`, return `Ok(Default::default())`:
  compile-unviable, rustc E0277, because `JsonValue` has no `Default` implementation.
- Decimal `1487:9`, return `true`: equivalent at the public `to_f64` boundary.
  The private predicate's result is only used before `str::parse::<f64>()`
  and a finite-value filter. Rust's documented finite decimal grammar matches
  this predicate; the extra accepted inf/infinity/nan forms are rejected by
  the finite filter. Exact named C# specials are handled before this predicate.
  See [Rust FromStr grammar](https://doc.rust-lang.org/std/primitive.f64.html#impl-FromStr-for-f64).
- Decimal `1496:28`, `- -> +`: equivalent at that same boundary. Without a sign,
  int_start is zero and the expressions are identical. With a sign, the integer
  digit count becomes positive even if no integer digits occurred. This only
  relaxes the no-digit rejection; valid signed fractions still pass, while
  malformed signed inputs fail the subsequent Rust parser. It changes no
  returned finite value.
- Decimal `1494:15`, `1501:19`, `1516:19`, `+= -> *=`: three unresolved
  90-second test timeouts, respectively in the integer, fraction and exponent
  digit loops. Multiplying i by one never advances it, so a digit keeps the
  loop running. A timeout is not counted as caught or equivalent.
