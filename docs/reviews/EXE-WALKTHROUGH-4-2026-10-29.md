# Exe walkthrough 4, journal compaction, live marker, RAW+JPEG pairs, Recovery edge cases, failing destinations (2026-10-29, Machine A)

Status: evidence report. Fourth real-exe pass (debug build of branch `claude/exe-walkthrough-4`, master `5c7d8794` plus a merge of `origin/claude/exe-walkthrough-3`, PR #339, so the compare and Recovery-time fixes are present), driven like the earlier passes
([EXE-WALKTHROUGH-3-2026-10-29.md](EXE-WALKTHROUGH-3-2026-10-29.md)): `keybd_event`, `SetCursorPos` + `mouse_event`, `PrintWindow`, `EnumWindows`.
It covers the data-safety items the third pass listed under "Not checked". The C# baseline `7eaee2a2` was read with `git show` only (`RecoveryFileCheck.cs`, `RecoveryWindow.xaml.cs`, `FileActionController.cs`, `FileActionService.cs`); the Rust rules from `crates/pr-core/src/file_actions/` (`compaction.rs`, `journal.rs`, `reconcile.rs`, `transaction.rs`).
Every run set `PHOTOREVIEW_RS_DATA_ROOT` (fresh temp dir), `PHOTOREVIEW_RS_ISOLATE_CONFIG=1`, a unique `PHOTOREVIEW_RS_INSTANCE_PREFIX` and `PHOTOREVIEW_RS_WARP=1`. One UI session at a time; only PIDs started by the run were stopped (the exe was also closed gracefully with `Esc`, exit code 0, in the long sessions).
Photos: generated 800x600 JPEGs (System.Drawing); RAW: `tools/dev/make-synthetic-raw.py` (`pair.dng` + `pair.jpg`, plus a hand-made `pair.xmp`). Journal scenarios were crafted by writing `operations.jsonl` into a fresh data root while the exe was closed.

## Defects found

None. No production code was changed, so no mutation testing was needed (nothing in journal, recovery, transaction or compaction logic was touched).

Observations, none a defect:

- The Recovery header says "Checked 4 entries" after entries were cleared, until the next Re-check (same text source as C#).
- "Clear 1 entries" and "Checked 1 entries": plural nits of the catalog text, same as C#.
- The Recovery window of the group repeats the single-file sentence ("The source is unchanged and nothing exists at the destination ...") above the per-member blocks even though one member is already moved; the C# presentation takes the text of the aggregate verdict (CanRetry) the same way.
- A journal with 50 000 Committed lines keeps all of them after compaction (only the Prepared lines before a Committed line go): this is the C# rule (the latest line of an Id is never dropped), so a long-lived journal still grows by one line per operation.

## Not checked

- `Delete` / Recycle in any form, "Remove (1) copies", "Remove originals" (real Recycle Bin).
- A genuine slow cross-volume Move held mid-copy by the app itself (partial destination cleanup), a Move whose in-flight window is long enough for a second instance to start (item 2 used the same named OS event created by another process instead).
- Compaction racing a concurrent writer (`Busy`/`Changed` outcomes), a journal on a read-only or locked file, a journal larger than 28.7 MB, release-build timing (the 7 s compaction is a debug-build observation on this machine, not a performance statement).
- Recovery of a Delete (Recycle) group, "Remove" duplicates, Retry of a group whose destination exists.
- `InstanceMode` other than single window for the second instance (item 2 used a different prefix so B is a real second process).
- Drop of a RAW file, touchpad gestures, other DPI, multiple monitors.

## Harness notes (not product defects)

- Child processes inherit the caller's stdout: a `| tail` on a script that starts the exe never ends. Redirect to a file instead.
- `powershell -File x.ps1 -Delays 3,8` binds `38`-style text to an `[int[]]` parameter (comma list read as one number): pass one value per invocation.
- `Press` sleeps 150 ms after the key; the kill-after-`Enter` test used raw `keybd_event` and `Stop-Process` back to back to reach the 0 to 20 ms window.
- A REPL driver (a PowerShell loop reading commands from a file) kept one exe alive for the Recovery sequence; screenshots go through `PrintWindow` of the dialog's own handle (task dialogs are separate `#32770` windows).
- Gates: no source change in this PR (docs and images only), so `cargo fmt`, `clippy` and `test` were NOT run for it; the debug exe was built with `cargo build -p pr-shell --bin PhotoReviewRs` on the merged head.
