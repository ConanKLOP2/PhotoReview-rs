# D3 IMPL (2026-11-03): duplicate cleanup keeper pre-check restored as a Rust-only extra (P-191)

Status: implemented on branch `feat/duplicate-precheck-restore`, not pushed. Decision: P-191 (owner, 2026-11-03, "restore").
Context: PR #610 (C# #535 D2, commit 5db7b27) replaced the Rust-only D-07f-5 / DV-7 pre-check (FIX-DUPCLEAN-M1) with the C#
per-file re-check. The old pre-check could not stay as it was: it skipped a whole group when ANY file of it changed, but the
ported C# tests expect the unchanged sibling of an edited file to be recycled.

## Design (what conflicts, what does not)
The ported C# tests pin four things: (1) a removed copy that was edited or deleted is reported, its siblings are recycled;
(2) all keepers deleted -> per-file `core.duplicate.fileChanged` lines and `BatchDone(0, n)`; (3) one surviving keeper is enough;
(4) the check runs at every recycle. So a pre-check on the files to remove, or on a deleted keeper, always conflicts.

The only case no ported test pins is: a copy that stays was MODIFIED (still exists, size or write time differ from hash time)
and no copy that stays still matches. There the pre-check is restored:
- `RecycleGuard::keepers_modified(path)`: true when no keeper is `unchanged` AND at least one keeper has a hash-time stat and a
  current stat that differ.
- In `handle_hash_finished` after the review dialog and before `start_batch`: every file whose group qualifies is dropped from the
  batch and listed as `<name>: <core.undo.sourceOrDestinationChanged>`. Nothing left -> status `BatchCanceled` + one error dialog
  with the lines. Otherwise the batch runs for the rest and the lines are added to its failures (final summary dialog).
- The D2 per-file check stays in front of every recycle and is untouched.

## Deviation vs C#
Rust-only extra: for a group whose only remaining keepers were modified (not just deleted) while the review dialog was open, the
group is skipped before the first recycle with `sourceOrDestinationChanged` lines, and the status is `BatchCanceled` when
nothing else is left. C# #535 reports the same files with `fileChanged` lines and `BatchDone(0, n)`. Data safety is identical
(nothing of that group is recycled); only status and text differ. Honest note: the practical gain over D2 is small.

PARITY 'Different' row wording (proposal): "Duplicate cleanup: a group whose only remaining copies-to-keep were modified (size or
write time) while the review dialog was open is skipped up front with `core.undo.sourceOrDestinationChanged` and, if nothing else
is left, status `BatchCanceled` (C# #535: per-file `core.duplicate.fileChanged` and `BatchDone(0, n)`). Safety identical. ADR:
restore of D-07f-5 as a Rust-only extra on top of D2, narrowed to modified keepers so that the ported C# tests stay green."
