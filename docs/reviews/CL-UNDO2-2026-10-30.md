## Single-Recycle stat difference (C# throw vs Rust `CoreUndoFailed`)

C# `UndoLastAsync` (`UndoService.cs:351-387`): the Recycle branch calls `_fileSystem.GetFileStat(action.Source)` at 373 inside `try { .. } finally { End(); }`.
A stat exception escapes the method and faults the returned task; the gate is released by `finally`, `_lastUndoAction` is kept, no journal line is written.
The only caller, `FileActionController.UndoLastAsync` (`FileActionController.cs:889`), awaits it without a catch, so the user sees an unhandled error, not an `UndoResult`.

Rust `UndoService::undo_single_recycle` returns `UndoResult { success: false, message: core_undo_failed(<io error text>) }`, with the gate released (`GateHold`), the action
retained, no journal line, and no second shell restore of a file already restored (`w3_undo_stat_parity`). Observable data-safety state (INV-4 gate, INV-6 journal) is identical to C#;
only the channel differs: an error result shown as a failed undo instead of an exception. `undo_last() -> UndoResult` is called by `pr-app` and the
viewmodels; adding an `Err` channel would change every call site and the UI contract for a case where the C# behaviour is an unhandled exception.

**Verdict: accepted-as-is DIVERGENCE** (recorded in the PARITY row as Different, same family as the D5 OS-error-text precedent). Public API unchanged.
