# D2-IMPL (P-74 option C: prefetch lookup pool), 2026-11-03

> Status: current. Decision: owner, 2026-11-03, P-74 option C (BACKLOG G14 L3, review `main-window-input-overlay-viewing.md` L3). Branch `fix/prefetch-lookup-pool`. Not pushed.

## What changed

- New `crates/pr-platform-win/src/host/main_window/lookup_pool.rs`: `LookupPool`, a small pool of named worker threads (`prefetch-lookup-0..`) fed by one channel. Each job runs inside `catch_unwind`; a panic is written to the window log as an error ("Prefetch lookup job panicked; the lane keeps running") and counted (`panic_count()`); the lane keeps running. `Drop` closes the queue (queued jobs still run) and joins every worker. `LookupPool::shared()` starts the process-wide pool on first use; a failed start is not cached.
- Lane count: `min(max(cpus / 2, 1), 4)` with `cpus = std::thread::available_parallelism()` (1 when unknown), function `lane_count_for`. Lookups are short cache reads; half the CPUs stay free for decoders and the UI thread.
- `MainWindowPrefetchHost::start_lookup` (`viewing.rs`) no longer spawns a thread per `navigated()`. It builds the job with the new seam `lookup_work(request, lookup, post)` (same body as before: per path `try_get_cached_preview_path(..).and_then(as_pixels)`, then `post_with_priority(.., UiPriority::Background)` of `apply_prefetch_lookup`) and submits it to the shared pool. Early returns (window gone, disposed, view model borrowed) are unchanged.
- Differs from the local candidate `d646739` (`fix/g14-l3`, one shared lane): N lanes instead of one, per-job error log, joining shutdown.

## Review speed

- Nothing is added on the navigation path except a channel send. The workers start once (first lookup of the process), so later navigations no longer pay a thread start (the old code paid one `CreateThread` per navigation). Before: one thread per navigation, unbounded under rapid switching. After: at most 4 threads, jobs of a rapid switch run concurrently up to the lane count; they are NOT serialized to 1 (`jobs_run_concurrently_up_to_the_lane_count` would time out on a single lane, because its jobs wait for each other).
- Measurement note: no wall-clock benchmark was run. Reasoning: one lookup is a handful of in-memory cache probes (microseconds to low milliseconds), the generation check in `apply_lookup` drops stale results, and on a 4-CPU machine 2 lanes run in parallel, on 8+ CPUs 4 lanes. Only a 1 or 2 CPU machine gets a single lane, where the old design also had no real parallelism for CPU-bound work.

## Tests (crate `pr-platform-win`, lib, all in `lookup_pool::tests`)

- `lane_count_is_half_the_cpus_between_one_and_four`, `jobs_run_concurrently_up_to_the_lane_count`, `more_jobs_than_lanes_all_run_on_at_most_the_lane_threads` (no thread per request), `panicking_job_does_not_kill_a_lane_and_is_logged_and_counted`, `drop_runs_the_queued_jobs_and_joins_the_workers`, `submit_after_shutdown_is_false_and_zero_lanes_still_start_one`.
- Window-path test: `panicking_lookup_does_not_break_the_next_navigation` drives `lookup_work` (the exact job builder `start_lookup` uses) through a one-lane pool: navigation 1 panics in its lookup, navigation 2 still posts its result (generation 2, 3 results), panic counted and logged once. `lookup_work_posts_the_results_in_request_order` covers the builder.
- Red check: with `catch_unwind` replaced by a direct call the two panic tests FAIL (the worker thread dies, the next job never runs); restored afterwards. The tests were written together with the module, so "red on master" is a compile failure (module absent) rather than a behavioural failure; the mutation above is the behavioural red evidence.
- No existing test changed.

## Deviation vs C#

C# runs the lookup on the .NET thread pool (`Task.Run`-style, unbounded by design of the pool). The Rust port now uses a bounded pool of at most 4 named lanes. Observable behaviour is the same (result posted to the UI thread at `Background` priority, stale generations dropped by the prefetcher). Intentional, so needs a `Different` row and an ADR.

Suggested PARITY `Different` row wording: "Prefetch lookup: C# runs cache lookups on the thread pool; Rust runs them on a fixed pool of `min(max(cpus/2,1),4)` named lanes (`lookup_pool.rs`), jobs wrapped in `catch_unwind` (error log + panic counter). Same observable result and priority. Test: `lookup_pool::tests::*`. ADR P-74."

Suggested ADR text (P-74): "Decision: replace the thread-per-navigation prefetch lookup by a small pool of named lanes sized `min(max(available_parallelism/2,1),4)`; each job is isolated with `catch_unwind`, logged as an error and counted. Why: R0003 forbids a thread per request, a panic in the old thread was uncaught, and a single lane (candidate `d646739`) would serialize lookups during rapid photo switching, which review speed (priority 1) rules out. Consequences: at most 4 threads, no per-navigation thread start; behaviour visible to the user unchanged."
